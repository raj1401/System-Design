Consistency Models: Linearizability, Sequential, Causal, and Eventual

What “consistent” actually means when replicas disagree, and which guarantee you are really buying.

November 5, 2026 · 5 min read

Summary

When two clients talk to a replicated store, they can disagree about what just happened. A consistency model is the contract that says which of those disagreements are legal. Formally it is a set of allowed histories of operations: if every execution your system can produce lands in that set, it satisfies the model (Jepsen Consistency Models).

For single-object operations the hierarchy is well known: linearizability implies sequential consistency, which implies causal consistency, and weaker still is eventual consistency — a convergence promise rather than an ordering one. Stronger models give programmers a simpler mental model; weaker ones survive partitions and cross-region latency that stronger ones cannot (Jepsen; Vogels, 2009).

Rule of thumb: pick the weakest model that still makes your invariants hold without heroic application logic. Linearizable locks and leader election need real-time order; a social feed usually does not. Paying for stronger consistency than you need costs availability and latency under partitions.

Linearizability: one instant, real time

Herlihy & Wing (1990) defined linearizability so that each operation appears to take effect at a single point between its invocation and its response, and that point respects real-time order: if A finishes before B starts, A comes before B in the equivalent sequential history. Reads never return a value older than a write that already completed. Compare-and-swap and mutexes rely on this atomicity.

Linearizability is local (composable per object) and non-blocking in theory: pending operations need not wait on others to complete for a legal linearization to exist. In an asynchronous network it cannot be totally available — under a partition some clients must stall (Jepsen: Linearizability).

Sequential consistency: drop real time, keep a total order

Lamport (1979) required that the result of any execution match some sequential order of all operations, and that each process’s operations appear in its program order. There is still one global order — everyone agrees on the sequence of writes — but that order need not respect wall-clock timing across processes. A write that finished on machine A can appear after a later write from machine B in the agreed sequence, as long as each client’s own ops stay in order.

That relaxation is why sequential consistency still cannot be totally available on asynchronous networks, yet it is strictly weaker (more permissive) than linearizability (Jepsen). Multiprocessors historically targeted sequential consistency; many distributed stores that advertise “strong consistency” without mentioning real time are closer to this model.

Linearizability

  • Single total order of ops
  • Respects real-time precedence
  • No stale reads after a completed write
  • Composable across objects (locality)

Sequential consistency

  • Single total order of ops
  • Only preserves per-process program order
  • Cross-client real-time stale reads allowed
  • Not local / not freely composable

Causal consistency: order what actually depends

Often you do not need a total order of every write on the planet — only that causally related writes stay ordered. Using Lamport’s happens-before idea: writes from the same client stay ordered; a write that a client has already observed is a cause of its later writes; and the relation is transitive. Concurrent (causally unrelated) writes may be applied in different orders at different replicas (XDN formal definitions).

Lloyd et al., SOSP 2011 (COPS) argued that causal+ — causal consistency plus convergent conflict handling — is the strongest model that still allows always-on, low-latency geo-replication: local ops complete in the local datacenter, and cross-region replication preserves causal dependencies without waiting for a global lock. Social graphs, messaging, and collaborative apps fit this sweet spot: if Alice comments on Bob’s post, no replica should show the comment before the post.

Causal order vs. concurrent writes

Eventual consistency: converge, eventually

Vogels (2009) popularized the operational definition: if no new updates are made to an object, eventually every access returns the last updated value. That is a liveness / convergence property. It says almost nothing about what a read may return while updates are still in flight — no monotonicity, no causal order, no recency. DNS is the classic example: TTLs and caches mean the world converges, but not on a schedule you control.

Production systems usually bolt session guarantees on top — read-your-writes, monotonic reads, monotonic writes — so a single client does not see its own world rewind (Vogels). Conflict resolution (last-writer-wins, CRDTs, application merge) is what makes “the same set of writes ⇒ the same state” true everywhere. Without convergent conflict handling, replicas can permanently diverge even after updates stop.

Causal (+)

  • Preserves happens-before on writes
  • Available under partitions (sticky clients)
  • Low latency geo-local reads/writes
  • Needs dependency tracking / metadata

Eventual

  • Only promises eventual convergence
  • Totally available; any replica can serve
  • Transient anomalies are application’s problem
  • Cheap to implement; hard to reason about

Choosing a level

Ask what breaks if a read is stale, reordered, or missing a causal dependency. Coordination services (etcd, ZooKeeper), leader leases, and inventory decrements usually need linearizability. A globally ordered feed can live with sequential consistency. Messaging and social graphs often land on causal+. CDN caches, analytics counters, and shopping-cart merges thrive on eventual consistency with explicit merge rules. Jepsen’s hierarchy also reminds you that models stronger than sequential cannot be totally available on asynchronous networks — CAP is not optional once you pick your row in the chart (Jepsen Consistency Models).

Real-world use cases

etcd / ZooKeeper
Linearizable reads and writes for leader election, config, and fencing tokens — stale leadership is catastrophic.
Spanner / CockroachDB
External consistency / strict serializability via synchronized clocks or consensus so multi-key transactions look real-time ordered.
COPS / geo KV stores
Causal+ across datacenters: local latency with causal dependency checks before exposing remote writes.
Dynamo / Cassandra / DNS
Eventual (or tunable) consistency: prefer availability and partition tolerance; resolve conflicts with quorums, LWW, or CRDTs.
