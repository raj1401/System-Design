Load Balancing Strategies: L4/L7 Algorithms, Health Checks & Sticky Sessions

Spreading traffic so no single machine becomes the bottleneck — and failing over when one does

September 15, 2026 · 5 min read

The Concept, Briefly

A load balancer sits in front of a pool of backends and decides, for each connection or request, which healthy server should handle it. Done well, this multiplies capacity, hides individual failures, and unlocks rolling deploys. Done poorly, it concentrates load, breaks sessions, or sends traffic to dead hosts.

The design space has three axes: where you balance (Layer 4 vs Layer 7), how you pick a backend (round-robin, least connections, weighted, consistent hash), and how you stay correct under failure (health checks, sticky sessions / affinity).

Why this matters: Horizontal scale only works if the front door can spread work fairly and stop routing to unhealthy nodes. L4 gives raw speed; L7 gives content-aware routing. Algorithm choice and health checks decide whether your cluster actually stays balanced when load, latency, and membership change.

Underlying Ideas & Mechanisms

Layer 4 vs Layer 7

Layer 4 (transport) balancers forward TCP/UDP flows using connection metadata — typically a hash of the 5-tuple (protocol, source/destination IP and port). They do not inspect HTTP. Latency is minimal and any protocol works. AWS Network Load Balancer and Google's Maglev are classic L4 designs; Maglev combines ECMP to LB machines with consistent hashing and connection tracking for connection-oriented protocols.

Layer 7 (application) balancers terminate TLS, parse HTTP, and route on host, path, headers, cookies, or gRPC metadata. They enable path-based microservices routing, A/B and canary splits, and WAF integration — at the cost of more CPU. AWS Application Load Balancer defaults to round robin (or least outstanding requests) per target group after evaluating listener rules. NGINX, HAProxy (HTTP mode), Envoy, and Traefik dominate the software L7 space.

L4 Flow Forwarding vs L7 Content-Aware Routing

Core Selection Algorithms

NGINX's upstream module documents the industry defaults clearly. By default, requests use weighted round-robin: each server gets a share of traffic proportional to its weight. With equal weights this is classic round-robin — simple, fair for homogeneous short requests, and the right default for most stateless HTTP pools.

Least connections (least_conn) sends each request to the server with the fewest active connections (respecting weights). It shines for long-lived or variable-duration work — WebSockets, streaming, uneven RPC costs — where round-robin can pile up on a slow node.

Envoy's weighted least request policy goes further: when weights are equal it uses power of two choices (P2C) — sample two random healthy hosts and pick the one with fewer active requests — which resists herding and stays O(1).

IP hash / source affinity (ip_hash in NGINX) maps client IP to a backend so the same client usually lands on the same server without cookies. It is a blunt stickiness tool and can skew when many clients share NATs.

Consistent hashing (NGINX hash … consistent / ketama; Envoy ring hash and Maglev) hashes a key — URI, cookie, header, user id — onto a ring or lookup table so only a small fraction of keys remaps when a backend is added or removed. Critical for cache pools and stateful shards. Google's Maglev paper and Envoy's Maglev policy use a fixed-size table (65537 in Envoy) for fast lookup with good balance; ring/ketama is often slightly more stable under membership churn.

How Algorithms Place the Next Request

Health Checks: Active and Passive

Without health checks, every algorithm will cheerfully send traffic to a crashed process. Passive checks watch real traffic — NGINX's max_fails / fail_timeout mark a peer unavailable after repeated errors. Active checks periodically probe a dedicated endpoint (e.g. /healthz). Managed balancers (ALB/NLB) and Envoy active health checking remove unhealthy targets from the selection set until they recover. Prefer both: active for fast detection of silent failures, passive for catching request-path errors active probes miss.

Sticky Sessions (Session Affinity)

Affinity keeps a client's requests on the same backend for the life of a session — needed when servers hold in-memory state. Mechanisms include cookie stickiness (NGINX Plus sticky cookie, ALB stickiness), application-learned cookies, and IP hash. Stickiness fights even distribution and complicates failover when a node dies, so prefer externalizing session state (Redis, DynamoDB) and keeping the LB mostly affinity-free.

Prefer for most APIs

  • L7 balancer (ALB / NGINX / Envoy)
  • Round-robin or least-request
  • Active + passive health checks
  • Stateless apps; shared session store
  • Weighted targets for canaries

Prefer when constraints bite

  • L4 (NLB / Maglev) for raw TCP/UDP latency
  • Least connections for long-lived streams
  • Consistent hash for caches / shards
  • Sticky sessions only if state is local
  • IP hash as a last-resort affinity hack

Real-World Use Cases

AWS ALB + NLB
ALB routes HTTP by host/path with round robin or least outstanding requests; NLB preserves source IP and uses flow hash for ultra-low-latency TCP/UDP.
NGINX Upstream
Default weighted round-robin, plus least_conn, ip_hash, and ketama-compatible consistent hash — the workhorse reverse proxy for web fleets.
Envoy / Istio
Sidecar and gateway LB with round robin, least request (P2C), ring hash, Maglev, and locality-aware policies for service meshes.
Google Maglev
Software L4 LB serving Google and GCP since 2008: ECMP to Maglev machines, consistent hash tables, and connection tracking for resilient flows.
Cache / CDN edges
Consistent hashing keeps a content key on the same cache node across membership changes, protecting hit rates when the pool scales.
Canary & blue-green
Weighted target groups (ALB) or weighted upstream peers (NGINX/Envoy) shift a small percent of traffic to a new version before full cutover.

Trade-offs to Keep in Mind

Algorithm beauty cannot fix bad capacity planning. Round-robin on heterogeneous machines needs weights. Least connections without max connection limits can still overwhelm a recovering node — combine with slow-start and connection caps where available. Consistent hashing is not free under churn: Maglev remaps more keys than ketama when hosts change, though it is often faster. And sticky sessions are a smell that state should probably live outside the app process.

Pick L7 unless you have a clear L4 requirement. Start with round-robin (or least-request for variable RPCs), turn on health checks on day one, and reach for consistent hashing only when cache locality or shard affinity demands it.
