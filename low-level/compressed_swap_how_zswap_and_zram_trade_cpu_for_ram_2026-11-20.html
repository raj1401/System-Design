Compressed Swap: How zswap and zram Trade CPU for RAM

Before a page hits the disk, compress it and keep it in memory. Two Linux designs, one allocator, very different plumbing.

November 20, 2026 · 5 min read

Summary

When Linux runs short of memory, reclaim pushes cold anonymous pages out to swap. Even on fast NVMe, a swap-in costs orders of magnitude more than a DRAM access; Seth Jennings put the RAM-vs-swap latency gap at roughly four orders of magnitude when he introduced zswap (LWN, 2013). Compressed swap closes much of that gap by spending CPU cycles instead: compress the outgoing 4 KiB page with a fast codec such as LZ4, LZO or zstd, and store the result in RAM. A later fault decompresses it in microseconds rather than issuing block I/O.

Linux ships two mechanisms for this. zswap is a write-behind cache that sits in front of a real swap device. It catches pages on their way out and writes them to disk only when its pool is full or cold (kernel zswap docs). zram is a compressed RAM block device (/dev/zramN) that you can mkswap and use as the swap device itself, with no disk required (kernel zram docs). Both now store their data in the same allocator, zsmalloc.

The core trade-off: compressed swap turns an I/O problem into a CPU and fragmentation problem. It pays off when pages compress well (often 2:1 to 3:1 for typical desktop memory, per Fedora’s measurements) and when decompression is much faster than reading from the backing store.

Deeper Dive: Where Each One Sits

Swap-out path: zswap cache vs zram device

zswap: a write-behind cache for the swap subsystem

zswap hooks directly into the swap path. When reclaim decides to swap out a page, it has already been given a swap slot (a swap entry: device type plus offset). Before any I/O is issued, zswap_store() tries to compress the page. On success the I/O is skipped entirely, and zswap records the mapping from swap entry to compressed object in an xarray per swap type, keyed by swap offset. On a later fault against that swap PTE, the swap-in code calls zswap’s load function, which decompresses straight into the newly allocated page. When the swap entry’s reference count in swap_map drops to zero, zswap’s invalidate hook frees the compressed copy.

Originally zswap used the generic frontswap API (LWN), and the zpool layer let it choose among zbud, z3fold and zsmalloc. Both are history now. z3fold and zbud were removed in Linux 6.15, and the zbud removal commit measured zbud using about 32% more memory than zsmalloc for a 2–3% speed gain. A follow-up series then removed zpool and made zswap call zsmalloc directly, as zram always had.

The policy surface is small on purpose. max_pool_percent caps the pool as a share of RAM. When the cap is hit, zswap evicts on an LRU basis: it decompresses the oldest entries and writes them to the real swap slot they already own. accept_threshold_percent adds hysteresis so a full pool does not thrash pages in and out. An optional shrinker_enabled mode writes cold entries back proactively under memory pressure. Same-value pages, such as all-zero pages, are detected before compression and stored as just the repeated value (zswap docs). With cgroup v2, each cgroup’s compressed footprint is charged and capped via memory.zswap.current and memory.zswap.max. memory.zswap.writeback=0 forbids any disk swapping for that cgroup, covering both zswap writeback and store failures (cgroup-v2 docs).

zram: a compressed block device

zram works one layer lower. It is a block driver: you set comp_algorithm, write a disksize, then mkswap and swapon it (or put a filesystem such as /tmp on it). The swap code thinks it is doing ordinary block I/O. Each 4 KiB write is compressed and stored in zsmalloc, and a per-device table maps sector index to handle plus state flags. Because zram is the final destination, nothing has to exist behind it. That is ideal for phones and small VMs without a disk you would want to swap to, but it also means that when zram fills up, swap is simply full and the OOM path comes next.

zram has grown its own tiering. With CONFIG_ZRAM_WRITEBACK you can attach a backing_dev partition and write idle, huge (incompressible) or huge_idle slots to it, with a writeback_limit budget to protect flash endurance. Pages become “idle” when you write all or an age in seconds to the idle attribute. With CONFIG_ZRAM_MULTI_COMP, up to three secondary algorithms (for example zstd or lz4hc) can recompress idle or huge slots for a better ratio, trading speed only on cold data (zram docs). /sys/block/zram0/mm_stat exposes orig_data_size, compr_data_size and mem_used_total, so you can compute both the compression ratio and the allocator overhead.

zswap

  • Front-end cache; requires a real swap device
  • Kernel-managed LRU writeback when full
  • Per-cgroup limits: memory.zswap.max / writeback
  • Compressor switchable at runtime; old pools drain
  • Fits servers with SSD swap (Meta TMO, Google)

zram

  • Is the swap device; works with no disk at all
  • Writeback to backing_dev only when admin triggers it
  • Fixed algorithm after init, plus optional recompression
  • Also usable as a general compressed ramdisk
  • Fits phones, laptops, small VMs (Android, Fedora)

zsmalloc: why a special allocator

Compressed pages are awkward allocations: anything from a few dozen bytes to almost a full page, and needed exactly when memory is scarce. The slab allocator would need high-order contiguous pages to back large size classes, and those allocations are the first to fail under pressure. Slab objects also cannot cross page boundaries, so a 2,049-byte object would waste nearly half a page (LWN). zsmalloc avoids both problems. It only ever allocates order-0 pages and chains them into a zspage through struct page fields, so an object can straddle a page boundary. Its dense size classes keep internal waste low. Because zspages are not permanently mapped, zs_malloc() returns an opaque handle rather than a pointer, and that indirection is also what lets zsmalloc compact and migrate objects behind its users’ backs (zsmalloc docs).

zsmalloc: objects spanning non-contiguous order-0 pages

Pitfall: incompressible data. Encrypted, already-compressed or quantized data (TMO calls out quantized ML model weights) barely compresses. zram stores such pages uncompressed as “huge” objects that take a full page; zswap rejects them and lets them go to disk. In both cases you paid CPU for nothing, which is why zram supports writing incompressible slots back to its backing device and zswap exposes rejection counters in debugfs.

Real-World Use Cases

Android
zram swap is the standard low-RAM configuration; the newer mmd daemon sets it up (default size 50% of RAM) and drives recompression.
Fedora & desktops
Since Fedora 33, installs create swap-on-zram via systemd’s zram-generator instead of a swap partition (Changes/SwapOnZRAM).
Meta datacenters
TMO uses PSI-driven reclaim to offload cold memory to zswap or SSD swap per application, saving 20–32% of memory fleet-wide (ASPLOS ’22).
Google fleet
The TMO paper cites Google’s zswap-based far memory (“g-swap”) as an early large-scale swapping deployment for latency-sensitive services (TMO paper).
Overcommitted VMs
Guests that share storage cut swap I/O and avoid hypervisor I/O throttling (zswap docs).
SSD endurance
Absorbing swap writes in RAM extends flash life; zram’s writeback_limit caps daily writes to its backing device.

Choosing between them

If you already have a swap device and want the kernel to manage a hot compressed tier with overflow to disk, use zswap. If you have no suitable disk, or want the simplest memory-only swap, use zram. Don’t stack them: zswap in front of a zram swap device compresses pages twice for no gain. Whichever you pick, watch PSI memory pressure along with compression ratios. Compressed swap only helps if the faults it serves are cheaper than the stalls it prevents.
