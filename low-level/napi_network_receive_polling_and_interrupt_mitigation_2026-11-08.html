NAPI: Network Receive Polling and Interrupt Mitigation

How the Linux networking stack lets the first packet wake the CPU, then polls the rest under a budget so a busy NIC cannot drown the machine in interrupts.

November 8, 2026 · 5 min read

Summary

A NIC that interrupts on every packet will, past a point, spend the CPU answering the device instead of doing useful work. Jamal Hadi Salim, Robert Olsson and Alexey Kuznetsov described the failure mode in their 2001 paper Beyond Softnet: interrupt livelock, in which packets are copied into a backlog only to be dropped because the processing thread never runs. On the Pentium-II router they measured, Linux 2.3.99 collapsed around 60K packets per second and its maximum loss-free forwarding rate was about 27K pps [1].

Their fix, which they called NAPI ('New API,' for lack of a better name), mixed interrupts with polling. A device may interrupt on the first packet of a burst; it then turns off further receive interrupts and leaves subsequent packets sitting on its DMA ring until a softirq polls it, up to a quota. Today the kernel documentation notes that the name no longer stands for anything in particular, but the contract is the same: napi_schedule() takes ownership of a struct napi_struct, the driver's poll method drains Rx and Tx under a packet budget, and IRQs stay masked until that work is done [2]. Later extensions let a user process or a dedicated kernel thread be the poller, and let administrators defer or suspend IRQs across short idle gaps so a loaded server can batch packets without burning a core waiting for the next one [2][3][4].

Why not poll all the time? Pure polling wastes CPU when the wire is quiet and adds a wait until the next poll interval. Pure interrupts are cheap when packets are rare and disastrous when they are not. NAPI's hybrid — interrupt to start a burst, poll to finish it — was an explicit design goal in Beyond Softnet: stay interrupt-driven below the system's maximum loss-free rate, and flatten into polling as load climbs [1].

Deeper Dive: How It Works

1. Livelock, DMA rings, and the original quota

Beyond Softnet credits Mogul and Ramakrishnan's 1996 work on receive livelock: given a high enough interrupt rate, the IP processing path never gets to dequeue anything useful. Hardware flow-control tricks that simply shut the IRQ off when a shared software backlog filled were chip-specific and still collapsed once enough NICs shouted at once [1].

NAPI's answer was to treat the NIC's DMA ring as the queue. After the first packet of a batch raises an interrupt, the driver registers that it has work and masks further packet-arrival IRQs. New frames keep landing in the ring; once the ring is full they are dropped in hardware, without waking the CPU. A later softirq walks every registered device and lets each send up a configurable quota of packets. If the quota is exhausted and the ring is still occupied, the device goes back to the end of the work list; if the ring is empty, the device is removed from the list and allowed to interrupt again [1]. Leaving packets on the ring also serialized a flow onto one CPU and removed the SMP reordering that softnet's per-CPU backlog queues had introduced.

2. Ownership, budget, and the poll method

The modern unit of work is a struct napi_struct: a poll function pointer, a weight, Generic Receive Offload state, software-coalescing timers, and flags such as NAPI_STATE_SCHED and NAPI_STATE_THREADED [5]. Drivers add an instance with netif_napi_add() (or netif_napi_add_config(), which ties it to a persistent per-index config so IDs and tunables survive queue reallocation) and then napi_enable() it. napi_disable() waits until whoever currently owns the instance releases it; calling it twice in a row can hang [2].

On the datapath, a successful napi_schedule() takes ownership. The core later invokes poll(napi, budget). Tx completions may be processed without a limit, because they are usually cheap; Rx is capped at budget packets, because it is expensive. Page-pool and XDP APIs are forbidden when budget is 0 — that value means the core only wants skb Tx completions. The poll method returns the work it did. Return exactly budget to say 'I still have work'; the instance is then polled again without another napi_schedule(). If the rings are empty, the driver must call napi_complete_done() before returning, which releases ownership [2].

Finish the burst

  • Processed fewer packets than budget
  • Call napi_complete_done(), then unmask IRQs
  • Next packet will raise a fresh interrupt

Stay scheduled

  • Return exactly budget if the ring still has work
  • Do not complete: the core will poll again
  • If you emptied the ring and used exactly budget, either skip complete and wait to be called again, or return budget - 1

That last corner case exists because there is no way to tell the stack 'I finished, but I also used the entire budget.' Completing on a full budget can race with a newly arriving packet and lose it; returning budget without completing keeps the instance live for one more (likely empty) poll [2].

3. Masking IRQs around the poll

Drivers should keep interrupts masked from the moment they schedule NAPI until polling finishes. Devices that auto-mask on IRQ can just call napi_schedule() from the handler. Devices that must mask in software should use the two-step form so a packet cannot sneak in between the decision to schedule and the mask [2]:

if (napi_schedule_prep(&v->napi)) { mask_irq(); __napi_schedule(&v->napi); }

IRQs are unmasked only after a successful napi_complete_done(). napi_schedule_irqoff() is a lighter variant for hard-IRQ context; it falls back to the regular helper if IRQs are threaded, as they are under PREEMPT_RT [2].

A NAPI Poll Cycle: IRQ, Budget, Completion

4. Two budgets: instance weight and CPU cycle

Each NAPI instance has a weight. netif_napi_add() defaults it to NAPI_POLL_WEIGHT, which is 64, and the header tells drivers not to pick a larger value [5]. That weight becomes the budget passed into a single poll. Separately, a CPU that is servicing several instances (several queues, several NICs, the per-CPU backlog) round-robins them in one polling cycle whose packet cap is net.core.netdev_budget and whose time cap is net.core.netdev_budget_usecs [6]. The kernel initializes those to 300 packets and two jiffies of microseconds [7]. Exhausting either limit ends the cycle; leftover instances are rescheduled rather than dropped. A related sysctl, net.core.dev_weight, defaults to 64 and describes the maximum packets the kernel will handle on a NAPI interrupt, counting a hardware-aggregated LRO/GRO_HW frame as one [6].

Most poll methods also feed Generic Receive Offload, which merges related frames so the rest of the stack sees fewer, larger packets — the receive-side complement of Generic Segmentation Offload [8].

5. Software coalescing, busy polling, and IRQ suspension

By default NAPI does not add its own interrupt coalescing; batching usually comes from the NIC. When software coalescing helps, gro_flush_timeout (a netdev sysfs knob reused for this purpose) arms a repoll timer instead of unmasking hardware IRQs the instant the rings go idle, and napi_defer_hard_irqs counts consecutive empty polls before NAPI gives up and re-enables IRQs. Both can also be set per instance through the netdev generic-netlink API [2].

Busy polling pushes that idea into user space. SO_BUSY_POLL on a socket, or the global net.core.busy_poll / net.core.busy_read sysctls, lets a process check for packets before a device interrupt fires, trading CPU for latency [2][6]. An io_uring API exists as well. High request-per-second paths, especially forwarding and AF_XDP, can go further with SO_PREFER_BUSY_POLL: the application pledges to keep polling, and the driver is supposed to leave device IRQs masked. If gro_flush_timeout passes with no busy-poll call, the pledge is revoked so a stalled application cannot silence the NIC forever [2].

That dual use of gro_flush_timeout — 'wait a bit for more traffic' versus 'the application forgot to poll' — cannot be tuned with one number. A patch set by Joe Damato and Martin Karsten, merged for Linux 6.13, split the roles by adding irq_suspend_timeout. While preferred busy polling is succeeding and actually retrieving events, the longer suspend timeout keeps IRQs off so user space can finish a batch without a competing softirq. The moment a poll finds nothing, the kernel falls back to napi_defer_hard_irqs empty polls plus the shorter gro_flush_timeout before re-enabling interrupts. LWN reported that the authors claimed data-center processing-efficiency (and thus power) gains of as much as 30% [4].

Three Loops That Can Drive napi->poll

The kernel documentation describes these three loops explicitly. Setting gro_flush_timeout and napi_defer_hard_irqs lets loop 2 take over from loop 1. Preferred busy polling then lets loop 3 wrestle with loop 2; during busy periods irq-suspend-timeout is the timer that tips the fight toward user-space polling. Without the two deferral knobs, loop 3 cannot take control from plain interrupts at all [2].

6. Threaded NAPI

NAPI processing usually runs in software-interrupt context, which steals time from whatever task happens to be on the CPU and is nearly invisible to the scheduler [3]. Threaded NAPI, discussed on LWN in 2020 and documented as a current operating mode, moves each instance into its own kernel thread named napi/${ifc-name}-${napi-id}. Administrators can pin that thread, change its priority, and see its CPU use like any other task. The mode is selected by writing 0 or 1 to the device's threaded sysfs file, or per instance via netlink; a further netlink mode, threaded: busy-poll, makes the kthread spin continuously, which is useful for forwarding or AF_XDP at the cost of a fully occupied CPU [2].

Most devices still map NAPI instances 1:1:1 to interrupts and queue pairs (one Rx queue plus one Tx queue). The ethtool 'channel' counts (rx, tx, combined) are best read as IRQ/NAPI units that service queues of that type. User space can discover instance IDs with SO_INCOMING_NAPI_ID or the netdev netlink API, which is how a busy-polling server keeps the sockets in one epoll set on the same NAPI [2].

Budget zero is not 'do nothing.' The core may call poll with budget == 0 when it only wants skb Tx completions. In that state the driver must not touch Rx, XDP, or page-pool APIs, and it must not call napi_complete_done() [2].

Real-World Use Cases

Multi-queue NIC drivers
Every modern Linux Ethernet driver schedules a NAPI instance from its IRQ handler, masks the queue, and polls Rx/Tx rings. Persistent config via netif_napi_add_config() keeps NAPI IDs stable across queue reallocations so SO_INCOMING_NAPI_ID stays meaningful [2].
Software routers and firewalls
NAPI was designed so a PC router would flatten at its maximum loss-free rate instead of collapsing into livelock, and so a greedy interface could not starve the others of a shared backlog [1]. The same budgeted poll is what keeps a busy host from spending the whole CPU in the NIC's interrupt handler.
Low-latency busy polling
Sockets set SO_BUSY_POLL (or applications use the epoll EPIOCSPARAMS ioctl) so incoming packets are harvested before an IRQ fires. Preferred busy poll plus irq-suspend-timeout aims at data-center efficiency: batch while traffic is present, sleep when it is not [2][4].
AF_XDP and isolated poller threads
Very high packet-rate paths can pledge to poll themselves (SO_PREFER_BUSY_POLL) or pin a threaded-NAPI kthread onto a dedicated core so packet processing no longer preempts random victims from softirq context [2][3].

Design Takeaways

NAPI separates noticing that a packet arrived (one interrupt) from processing what arrived (a budgeted poll of a DMA ring). The kernel, a user-space application, or a dedicated kthread can be the poller; IRQs stay masked for as long as someone is doing that work, and they come back when nobody is. The original paper's insight still holds: the right policy is not 'always interrupt' or 'always poll,' but a switch that tracks load, with quotas so no single queue can monopolize a CPU. The knobs that have grown around that core — software coalescing timers, preferred busy poll, IRQ suspension, threaded mode — are all ways of choosing who polls, and how long the interrupt is allowed to stay off.
