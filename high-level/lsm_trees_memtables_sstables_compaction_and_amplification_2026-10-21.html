LSM Trees: Memtables, SSTables, Compaction, and the Read/Write/Space Tradeoff

The write-optimized storage engine underneath Bigtable, Cassandra, HBase, RocksDB, and much of modern data infrastructure.

October 21, 2026 · 5 min read

Summary

A log-structured merge tree (LSM tree) is a storage engine design that never updates data in place. Writes land in a sorted in-memory buffer (the memtable) after being appended to a write-ahead log. When the memtable fills, it is frozen and flushed to disk as an immutable, sorted file (an SSTable). Background compaction continuously merges those files, discarding overwritten values and deletion markers. The idea dates to O'Neil et al.'s 1996 paper, which aimed to index fast-growing history tables without the random disk I/O a B-tree insert costs [1].

The payoff is cheap, sequential writes. The price is that a read may need to consult several files, and every byte gets rewritten several times during its life. Almost every design decision in an LSM engine is about where you pay that price.

The one-line intuition: a B-tree pays at write time to keep data in its final place; an LSM tree defers that work, batches it, and pays it later in large sequential merges, reminiscent of merge sort [1].

How It Works

The write path

Cassandra's documentation lists the sequence plainly: log the write to the commit log, write it to the memtable, flush the memtable, and store the result on disk as SSTables [2]. Because nothing on disk is read or modified during a write, the write path is free of read lookups. Bigtable describes the flush as a minor compaction: when the memtable hits a size threshold it is frozen, a new one takes its place, and the frozen one becomes an SSTable, which also shrinks how much commit log must be replayed after a crash [3].

Write path and level structure

The read path

Because the newest version of a key could be in the memtable or any SSTable, a point read checks the memtable, then L0 files newest-first, then at most one file per deeper level, stopping at the first hit. Deletes are written as tombstones, special entries that suppress older values until compaction can drop both [3].

Two tricks keep this affordable. A per-SSTable Bloom filter answers "might this file contain key k?" with no false negatives, so most files are skipped without touching disk; Bigtable notes that a small amount of memory spent on Bloom filters drastically reduces disk seeks [3], and Cassandra relies on them for the same reason [2]. Second, a block cache keeps hot SSTable blocks in memory [3]. Range scans cannot use Bloom filters, so they merge iterators across every overlapping run, which is where an LSM tree's shape matters most.

Point lookup: newest to oldest, Bloom filters first

Compaction and the three amplifications

Without compaction, reads would have to merge an unbounded number of files. Bigtable bounds this with merging compactions and periodic major compactions that rewrite everything into one SSTable with no deleted data left behind [3]. Every compaction policy is a bet across three costs, which the RUM conjecture formalizes: an access method that bounds two of read, update, and memory (space) overhead must accept a lower bound on the third [4].

  • Write amplification: bytes physically written per byte logically written. Cassandra notes every write is rewritten multiple times by compaction [2]; WiscKey measured LSM I/O amplification reaching 50x or more [7].
  • Read amplification: how many files or blocks a lookup touches.
  • Space amplification: disk used divided by live data, inflated by stale versions and tombstones.

Leveled compaction (LevelDB, RocksDB default, Cassandra LCS)

  • Each level is one sorted run split into non-overlapping files
  • Merges only the overlapping slice of Ln-1 into Ln (some-to-some)
  • Low read and space amplification
  • Per-level write amp up to the fanout, so higher total write amp
  • Good for read-heavy or update/delete-heavy data

Tiered / size-tiered (Cassandra STCS, RocksDB Universal)

  • Several similar-sized runs accumulate per tier, then merge together
  • Per-level write amp is about 1, much cheaper writes
  • More runs to check per read
  • Large transient space amp during big merges
  • Good for write-heavy ingest

These characterizations come from RocksDB's compaction taxonomy [5] and a VLDB Journal evaluation of merge policies [6]. Real engines blend them: RocksDB's level compaction is actually tiered at L0 and leveled below, and Cassandra offers Time Window Compaction for TTL'd time series plus a newer Unified Compaction Strategy whose single scaling parameter slides between read-favoring and write-favoring behavior [8] [9].

Design lever worth knowing: WiscKey keeps only keys (plus pointers) in the LSM tree and appends values to a separate log, so compaction stops dragging large values around. That cuts write amplification and shrinks the tree enough to cache better [7].

LSM tree vs B-tree, at a glance

B-trees update pages in place, giving predictable reads and cheap range scans, but small random updates turn into random writes and partially filled pages [7]. LSM trees convert those into sequential writes and pack data densely, which also compresses well, at the cost of background compaction I/O and occasional latency spikes when compaction falls behind. Picking between them is a workload question: write rate, read/scan mix, update and delete churn, and how much disk and SSD endurance you can spend.

Real-World Use Cases

Google Bigtable
Tablet servers buffer writes in memtables, persist SSTables on GFS, and use minor, merging, and major compactions plus Bloom filters [3].
Apache Cassandra
Commit log, memtables, and immutable SSTables, with pluggable STCS, LCS, TWCS, and UCS compaction [2] [8].
Facebook MyRocks
Moving the MySQL User Database from InnoDB to RocksDB cut instance size by 62.3% and more than halved the server count [10].
Embedded KV engines
RocksDB and LevelDB sit underneath many databases and stream processors; WiscKey lists HBase, Riak, and PNUTS among LSM deployments [7].

When to reach for one

Choose an LSM-based store for high, sustained write rates such as event logs, metrics, time series, messaging, and wide-column data, or when storage efficiency matters. Lean toward leveled compaction when reads and overwrites dominate, tiered when ingest dominates, and time-window compaction when data expires by age. Watch compaction debt, tombstone buildup, and L0 file counts in production; they are the early warnings of read latency trouble.
