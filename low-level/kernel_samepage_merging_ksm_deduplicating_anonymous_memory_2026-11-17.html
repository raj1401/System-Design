Kernel Samepage Merging (KSM): Deduplicating Anonymous Memory in Linux

How ksmd finds identical pages, collapses them into one write-protected copy, and lets copy-on-write split them again.

November 17, 2026 · 5 min read

Summary

Kernel Samepage Merging (KSM) is a content-based memory deduplication feature, enabled with CONFIG_KSM=y and merged in Linux 2.6.32 [1]. A kernel thread, ksmd, periodically scans regions of user memory that have opted in, finds pages whose bytes are identical, and replaces them with a single write-protected physical page. If any process later writes to that page, the normal copy-on-write (COW) fault path gives it a private copy again [1].

KSM was originally built for KVM (where it was first called Kernel Shared Memory) to fit more virtual machines into the same RAM: dozens of guests booting the same OS image hold a lot of byte-identical memory [1][3]. It only merges anonymous (private) pages, never page-cache file pages, which are already shared through the page cache.

The core trade: KSM spends CPU time (scanning and comparing pages) and a little metadata memory to get back physical memory. Whether that trade pays off depends entirely on how much truly duplicate, rarely written memory your workload has.

Deeper Dive: How ksmd Finds Duplicates

Opting in

KSM never scans memory on its own initiative. A process marks candidate ranges with madvise(addr, len, MADV_MERGEABLE), and can undo it with MADV_UNMERGEABLE, which un-merges everything in that range and may suddenly need a lot of memory [1]. Since Linux 6.4, prctl(PR_SET_MEMORY_MERGE, 1, 0, 0, 0) turns on KSM for every compatible VMA in a process, and children inherit that setting across fork(). This requires CAP_SYS_RESOURCE [5][6]. DAX, hugetlb, and shared VMAs are excluded [4].

Two red-black trees: stable and unstable

Comparing every page against every other page would cost O(n²). Instead, KSM keeps pages sorted by content in red-black trees, so a lookup is a series of memcmps down a tree path [2]. The catch is that ordinary user pages can change at any moment, which would corrupt a content-sorted tree. KSM handles this with two trees:

Stable tree

  • Holds already-merged KSM pages, sorted by content
  • Every page is write-protected, so the ordering stays valid
  • Never flushed; once a page lands here it stays merged until written or unmapped
  • Each node carries reverse-map info back to every sharing virtual address

Unstable tree

  • Holds candidate pages that have not changed for a while
  • Pages are still writable, so the tree can become "wrong"
  • Thrown away and rebuilt after every full scan
  • Color-balanced rbtree, so corruption never unbalances it or slows it down

For each scanned page, ksmd first searches the stable tree. On a hit, the page is merged into the existing KSM page. On a miss, ksmd computes a checksum and compares it with the checksum it saved for that page on the previous pass. Only pages whose checksum is unchanged, and therefore probably not being written, are searched for or inserted into the unstable tree. If the unstable tree already holds an identical page, the two are merged into a new KSM page, which moves into the stable tree [2].

Merging and the COW split

To merge, KSM write-protects the page-table entries of both pages, confirms the contents are still identical, then points every sharer's PTE at one physical page and frees the rest. The merged page is a normal read-only anonymous mapping, so a later write takes a page fault and goes down the ordinary COW path, which copies the page and gives the writer its own copy. That event is counted as cow_ksm in /proc/vmstat [1]. KSM pages can be swapped out, but sharing is lost on swap-in and ksmd has to find the duplicates again [1].

Metadata and reverse mapping

Each scanned page gets a struct ksm_rmap_item that records its mm, virtual address, last checksum, and its place in a tree. Merged pages are represented by struct ksm_stable_node, whose list of rmap_items lets the kernel find every virtual address mapping that KSM page when it has to migrate, compact, or swap it [2]. That rmap walk costs O(N) in the number of sharers, so max_page_sharing caps sharers per KSM page. Past the cap, the stable node becomes a "chain" of "dup" KSM pages that all hold the same content [2]. With merge_across_nodes=0, KSM keeps separate stable and unstable trees per NUMA node so a merged page never forces remote-memory access [1].

Tuning and measuring profit

The daemon is controlled through /sys/kernel/mm/ksm/: run (0 stop, 1 run, 2 stop and unmerge all), pages_to_scan and sleep_millisecs (scan rate), plus use_zero_pages, smart_scan (skip pages that repeatedly failed to merge), and a scan-time advisor_mode that adjusts pages_to_scan automatically toward a target full-scan time [1]. Metadata is not free: an rmap_item is about 64 bytes on 64-bit, so the docs approximate profit as saved_pages × page_size − rmap_items × sizeof(rmap_item), exposed as general_profit and per-process in /proc/<pid>/ksm_stat. On 64-bit, a process whose ksm_rmap_items/ksm_merging_pages ratio is above about 64 is getting roughly zero or negative profit [1].

Security caveat: Writing to a merged page is measurably slower because it triggers a COW fault. An attacker can use that timing difference to learn whether a page with given contents exists elsewhere on the host, for example in another VM [8]. Flip Feng Shui (USENIX Security 2016) went further and combined deduplication with Rowhammer to flip bits in a victim's shared page, breaking OpenSSH and GPG targets [7]. That is why KSM is opt-in and why LWN describes it as "not generally enabled" [5].

Real-World Use Cases

KVM / VM density
The original use case. QEMU marks guest RAM mergeable, so guests running the same OS share kernel text, zeroed pages, and libraries [3][9].
Meta's fleet workers
Meta enabled KSM per process with prctl for interpreter-heavy workers and reported about a 20% capacity increase [5][10].
systemd services
The MemoryKSM= unit setting enables process-level KSM for a service and its children with no code changes [4].
GC'd runtimes
Languages that cannot easily call madvise() on their heaps can still opt in through prctl, systemd, or an LD_PRELOAD shim [4].

Takeaways

KSM is a neat systems design: it sorts mutable data by content without locking it, by keeping a trusted tree of write-protected pages and a throwaway tree of candidates, and it uses the existing COW machinery as its undo path. Turn it on where many processes or VMs hold the same, rarely written memory. Check general_profit and cow_ksm to confirm it is paying off, and keep it off wherever untrusted tenants share a host and the dedup side channel matters.
