False Sharing: When Adjacent Fields Fight Over a Cache Line

Independent variables, one 64-byte line — and why your counters still bounce between cores.

September 18, 2026 · 5 min read

The Concept

False sharing is what happens when two or more threads modify different memory locations that happen to sit on the same cache line. The hardware coherence protocol — typically MESI or a close relative — cannot tell that the bytes are unrelated. It only sees a write to a shared line: the writer's copy becomes Modified, every other core's copy is invalidated, and the next reader or writer pays for a cache-to-cache transfer. The logical data never overlapped; the line did.

On contemporary x86 and most Arm servers the coherence granule is 64 bytes. Pack a hot per-thread counter next to another thread's hot counter inside that window and you get the classic ping-pong: throughput collapses as core count rises, even though each thread only touches its own field. The academic framing goes back at least to Bolosky and Scott's shared-memory study; the Linux kernel's own false-sharing guide treats it as a first-class performance hazard on large SMP systems.

True vs false sharing: True sharing is when cores really do contend on the same logical datum (a lock word, a shared queue head). False sharing is when the conflict is an accident of layout — adjacent fields, packed globals, or misaligned array bases — and the fix is padding, alignment, or sharding, not a different algorithm.

Deeper Dive: Lines, HITM, and Why Layout Is Destiny

Coherence is line-grained, not field-grained

Caches move and invalidate data in whole lines. When Core A writes offset 0 of a line while Core B keeps reading offset 32 of the same line, Core B's copy is still invalidated on every store — even though Core B never needed Core A's bytes. Two conditions make the damage severe, as the kernel documentation summarizes: the datum is touched by many CPUs, and at least one of those accesses is a write (write/write or write/read).

Intel's scaling guidance puts the same idea in hardware terms: x86 server memory is organized as 64-byte lines with MESIF-style states; frequent multi-core modification of one line causes cache-line contention ("ping-pong"). Contended_Accesses, Data_Sharing, and False_Sharing show up in Top-down Microarchitecture Analysis (TMA) metrics when PEBS is available.

Canonical layout traps

The kernel false-sharing guide lists patterns that keep biting production code:

  • A lock and the data it protects packed on one line — fine on dual-core boxes, lethal when hundreds of CPUs spin.
  • Small globals (flags, counters, atomics) glued together by the linker into one hot line.
  • Large structs (for example mem_cgroup) where unrelated hot members land on the same line by accident.
  • Array or allocator bases that are not 64-byte aligned, so even "one object per line" still straddles a boundary.

A real kernel regression came from mmap_lock layout inside mm_struct; Linus Torvalds walked the cache-line fallout on LKML. Networking and MM have since landed many dedicated padding and re-layout patches (for example cache-aligning tcp_memory_allocated, or re-laying out page_counter).

Detecting it: perf c2c, pahole, and Intel tooling

perf c2c (Cache-To-Cache) is the workhorse on Linux. It samples load-latency and precise-store events (Intel PEBS), IBS on many AMD CPUs (not Zen 3), or Arm SPE, then ranks cache lines by HITM — a load that hit a Modified line in another cache. The man page workflow is record then report; the kernel docs recommend something like:

perf c2c record -ag sleep 3
perf c2c report --call-graph none -k vmlinux

Look for high Local/Remote HITM, long average load latency, many CPUs touching one line, and — the smoking gun for false sharing — different offsets inside that line from different threads. Match those offsets to struct members with pahole (cache-line-delimited layouts) or addr2line for inlined call sites. Red Hat's performance guide walks the same Shared Data Cache Line Table: sort by remote HITM, then inspect the Pareto of offsets.

Joe Mario's original c2c write-up (the Red Hat prototype that landed in perf) is still the clearest tour of the report columns. On Intel platforms you can also start from VTune Memory Access / Contested Accesses, or aggregate L2 HitM / snoop-related counters via Intel Performance Counter Monitor (PCM), then drill into addresses with PEBS Data Linear Address (DLA) profiling as described in Intel's SDM Vol. 3B and practical guides such as Easyperf.

Caveat: On some Ice Lake / Tiger Lake generations, PEBS can conflate modified-line HITM with clean cross-core forwards, producing false positives in c2c. Always corroborate with source offsets and a before/after microbenchmark — do not pad blindly from a single HITM percentage.

Fixes that stick

Layout & padding

  • Put each hot write field alone on a line (____cacheline_aligned, alignas(64))
  • Use C++17 std::hardware_destructive_interference_size instead of hard-coding 64
  • Pad to 128 bytes where adjacent-line prefetch doubles the effective granule
  • Ensure array / allocator bases are line-aligned so elements do not straddle

Access & ownership

  • Shard into per-CPU or per-thread data; sync to a global less often
  • Prefer compare-then-write over unconditional stores to shared flags
  • Group read-mostly fields together; keep write-hot fields apart
  • Accept some false sharing on cold paths — padding costs cache and TLB

Real-World Use Cases

Kernel networking & MM
Linux patches regularly cache-align hot atomics (TCP memory/socket counters) and re-layout structures like page_counter after perf-c2c finds shared-line HITMs under will-it-scale and similar workloads.
Per-thread metrics & stats
Application counters, histograms, and rate limiters often start as a packed array of atomics — a textbook false-sharing bomb until each slot is line-padded or made thread-local.
Lock-free queues & rings
Producer and consumer indexes on one line thrash under load; separating them (and often the cached copies each side keeps) is standard ring-buffer hygiene.
Database & language runtimes
JVMs, Go runtimes, and DB engines spend serious effort on cache-line-padded structs for allocators and schedulers; Intel TMA Contested Accesses / False_Sharing metrics catch regressions in CI.
Complement to MESI: MESI explains why a write invalidates peer copies. False sharing is the software layout failure mode that weaponizes that mechanism against innocent fields. Fix the layout; do not try to outsmart the coherence protocol.
