Distributed ID Generation: Snowflake, Ticket Servers, and UUIDv7

Minting billions of unique, sortable keys without a single global counter in the way.

November 17, 2026 · 5 min read

Summary

On a single database, AUTO_INCREMENT hands you unique, ordered primary keys for free. Once data is sharded, replicated multi-leader, or moved between databases, that local counter breaks: two shards can both assign ID 42. Flickr hit exactly this when sharding MySQL, noting that it “can’t guarantee uniqueness across physical and logical databases” [1].

Every distributed ID scheme picks a point on three axes: coordination (does minting an ID need a network hop?), ordering (are IDs roughly time-sortable?), and size (64-bit integer vs 128-bit value). The main families are:

  • Centralized allocators — ticket servers and segment (range) allocation.
  • Coordination-free composite IDs — Snowflake: timestamp + worker ID + sequence in 64 bits.
  • Random / time-ordered 128-bit IDs — UUIDv4, and the newer UUIDv7 / ULID.

Deeper Dive

1. Ticket servers: one counter, made cheap

Flickr’s ticket server is a dedicated MySQL box holding a one-row table per ID width. Each request runs REPLACE INTO Tickets64 (stub) VALUES ('a'); SELECT LAST_INSERT_ID();, atomically bumping the auto-increment while the table stays one row [1]. To avoid a single point of failure, they ran two servers and split the space by parity — one with auto-increment-increment = 2, offset = 1 (odd IDs), the other offset 2 (even IDs) — and round-robin between them [1]. MySQL documents these variables as intended for circular (source-to-source) replication, with values from 1 to 65,535 [2].

The cost is a network round-trip per ID and only loose global ordering (the two servers drift apart). Meituan’s Leaf removes the per-ID hop with segment mode: each service instance claims a whole range (max_id advanced by step in a leaf_alloc table) and serves IDs from memory [3]. A double buffer fetches the next segment asynchronously before the current one runs out, so the service keeps issuing IDs through a short database outage, and the step size is adapted to traffic so a segment lasts roughly 15–30 minutes [4].

Segment allocation with a double buffer (Leaf-style)

2. Snowflake: pack time, machine, and sequence into 64 bits

When Twitter moved off MySQL toward Cassandra, which has no sequential ID facility, it built Snowflake and insisted on staying under 64 bits [5]. An ID is 41 bits of milliseconds since a custom epoch (about 69 years), a 10-bit configured machine ID (1,024 workers), and a 12-bit sequence (4,096 IDs per worker per millisecond) [5]. The top bit stays 0 so the value fits a signed 64-bit integer [6]. No coordination is needed per ID — only once, to hand each worker a unique machine ID.

Snowflake 64-bit layout

Variants re-slice the same 64 bits. Instagram generates IDs inside Postgres with a PL/pgSQL function: 41 bits of time, 13 bits of logical shard ID, and 10 bits of a per-table sequence mod 1024 — so the ID itself tells you which shard owns the row [7]. Discord uses its own epoch (the first second of 2015) and splits the machine field into 5-bit worker and 5-bit process IDs [8].

The clock is the hard part. Snowflake’s uniqueness assumes time never runs backwards on a worker. The original service tells you to run NTP and refuses to generate IDs until the clock passes the last timestamp it used [5]. Leaf’s implementation waits out a backward jump of up to 5 ms and returns an error for anything larger [9]. The other hard part is worker ID assignment: two nodes with the same ID will collide silently. Leaf leases worker IDs from ZooKeeper and caches them on local disk so a restart survives a ZooKeeper outage [4].

3. UUIDs: zero coordination, 128 bits

A random UUIDv4 needs no coordination at all, but Flickr rejected GUIDs because “they are big, and they index badly in MySQL” [1]: random keys scatter inserts across a B-tree, destroying cache locality. RFC 9562 (2024) fixes this with UUIDv7: a 48-bit big-endian Unix millisecond timestamp in the most significant bits, then version and variant bits, with the remaining 74 bits random — optionally replaced in part by a sub-millisecond fraction or a seeded counter for monotonicity within a millisecond [10]. The RFC says implementations should prefer v7 over the older time-based v1 and v6 [10]. ULID is the same idea predating the RFC: 48-bit timestamp plus 80 random bits, encoded as 26 Crockford Base32 characters that sort lexicographically [11].

Where new keys land in a B-tree index

That right-hand panel has a catch. On range-partitioned distributed databases, a monotonically increasing key funnels every insert into the same split. Google’s Spanner guidance explicitly warns against timestamp or auto-increment leading keys and recommends UUIDv4, a hashed/shard prefix, or a bit_reversed_positive sequence, which yields unique integers spread uniformly over the key space [12]. Locality is a feature on one B-tree and a bug across many ranges.

Centralized (ticket / segment)

  • Dense, compact, near-sequential integers
  • Needs an allocator service and HA plan
  • Segments amortize the DB hop; gaps on restart
  • No clock dependency

Snowflake-style (64-bit)

  • No per-ID coordination; fits a BIGINT
  • k-sortable; creation time decodable from ID
  • Requires unique worker IDs and sane clocks
  • Leaks creation time and rough volume

UUIDv4 (random 128-bit)

  • Zero coordination, generate anywhere (even clients)
  • Poor B-tree locality; 2× size of a BIGINT
  • Naturally spreads writes on range-sharded stores

UUIDv7 / ULID (time-ordered 128-bit)

  • Zero coordination plus index-friendly ordering
  • Standardized in RFC 9562
  • Can hotspot range-partitioned leading keys

Real-World Use Cases

X / Twitter
Snowflake IDs for tweets, users, DMs and more; the API returns string IDs too, because JavaScript numbers lose precision beyond 53 bits [13].
Instagram
Shard-aware 41/13/10 IDs generated by PL/pgSQL inside each logical-shard Postgres schema [7].
Flickr
Two odd/even MySQL ticket servers provide globally unique keys for a sharded, master-master MySQL fleet [1].
Meituan
Leaf offers segment and Snowflake modes as a shared ID service; its README reports ~50k QPS with 1 ms TP999 on a 4C8G VM [3].
Discord
Snowflakes with a 2015 epoch and worker/process subfields; timestamps can be decoded straight from any ID [8].
Google Spanner
Bit-reversed sequences give integer keys without the write hotspot of monotonic keys [12].
Choosing quickly. Need a 64-bit, sortable key at high rate with a stable fleet? Snowflake. Need dense integers and already run a reliable DB? Segment allocation. Generating IDs offline or on clients, on a single-node or hash-partitioned store? UUIDv7. Range-partitioned store with heavy insert rates? Avoid a monotonic leading key — use random, hashed, or bit-reversed IDs.
