Logical Clocks: Lamport Timestamps, Vector Clocks, and Hybrid Logical Clocks

How distributed systems decide what happened first when no two machines agree on the time.

October 6, 2026 · 5 min read

Summary

Every node in a distributed system has its own clock, and those clocks drift, jump, and disagree. If two replicas both accept a write to the same key, using wall-clock timestamps to pick a winner can silently throw away the newer update. Logical clocks sidestep the problem by ordering events by causality instead of by seconds: if event a could have influenced event b, then a must be ordered first.

Three designs dominate practice. Lamport timestamps give a single counter that respects causality and yields a cheap total order. Vector clocks (and their cousin, version vectors) carry one counter per node so a system can tell “happened before” apart from “concurrent”. Hybrid logical clocks (HLC) glue a logical counter onto physical time so timestamps stay causally correct while still reading like real dates, which is why modern distributed SQL databases use them for MVCC snapshots.

Key idea: Lamport defined the happened-before relation (→): a → b if they are on the same process and a came first, if a sends a message that b receives, or transitively through a chain of those. Two events with no such chain are concurrent. Every logical clock is a way to encode this partial order in a timestamp. (Lamport 1978)

Deeper Dive

Lamport timestamps

Each process keeps an integer C. It increments C before every local event and send, attaches C to outgoing messages, and on receipt sets C = max(C, msg.C) + 1. This guarantees the clock condition: if a → b then C(a) < C(b). Breaking ties with a process ID turns this into a total order that every node computes identically, which Lamport used to build a distributed mutual-exclusion algorithm (CACM, 1978).

The catch is that the converse is false. C(a) < C(b) does not mean a caused b; the two may be completely unrelated. A Lamport clock can order events, but it cannot detect a conflict.

Vector clocks

Fidge and Mattern independently proposed giving each of the N processes a vector V[1..N] in 1988 (Fidge; Mattern; see also this history of who invented them). Process i increments V[i] on each event; on receive it takes the element-wise max with the incoming vector, then increments its own slot. Now the comparison is exact:

V(a) ≤ V(b) element-wise (and not equal) if and only if a → b. If neither vector dominates the other, the events are concurrent. That “if and only if” is what lets a database say “these two writes conflict, keep both.” The price is metadata that grows with the number of participants.

Version vectors, siblings, and dots

Storage systems usually track causality per object rather than per process, using a version vector keyed by the replica that coordinated each write. Amazon’s Dynamo attached a list of (node, counter) pairs to every object version; if one version’s vector descends another’s, the older is discarded, otherwise both are returned to the client for semantic reconciliation (the famous shopping-cart merge). To bound size, Dynamo truncated the oldest pair once a vector exceeded a threshold such as 10 entries (DeCandia et al., SOSP 2007).

Version history of one key (after the Dynamo paper)

Riak followed the same model and learned a hard lesson: with per-vnode version vectors, interleaved writes from clients with stale context could produce false concurrency and an unbounded pile of duplicate siblings, a failure Riak calls sibling explosion (Riak, Vector Clocks Revisited). The fix was dotted version vectors, which tag each stored value with the single event (“dot”) that created it, so the server can tell exactly which siblings a new write supersedes (Preguiça et al., DVV; Riak, Part 2). Riak 2.0+ recommends DVVs over classic vector clocks (Riak docs: Causal Context).

Hybrid logical clocks

Vector clocks are precise but large, and pure logical counters drift arbitrarily far from real time, which makes “read the database as of 10:00:00” meaningless. Kulkarni, Demirbas, and colleagues proposed HLC: a timestamp (l, c) where l is the largest physical time the node has heard of and c is a small counter that breaks ties when l does not advance (Kulkarni et al., 2014).

On a local or send event: l = max(l, pt); if l didn’t change, c++, else c = 0. On receive, l becomes the max of the local l, the message’s l, and physical time, and c is bumped relative to whichever source(s) supplied that max. The result preserves e → f ⇒ hlc(e) < hlc(f), stays within the clock-sync error of NTP time, and fits in 64 bits: the paper keeps the top 48 bits of the NTP timestamp for l (roughly microsecond granularity) and 16 bits for c, which in experiments stayed in single digits (Demirbas, HLC explainer).

When physical clocks are good enough: TrueTime

Google Spanner goes the other way: GPS and atomic clocks let its TrueTime API return an interval [earliest, latest] whose width ε was typically 1–7 ms in production. A writer picks a commit timestamp no less than TT.now().latest and then performs commit wait, delaying visibility until TT.after(s) is true, which yields external consistency (Corbett et al., OSDI 2012). Systems without that hardware use HLC plus a configured bound on clock skew instead, trading commit waits for occasional read restarts (Cockroach Labs, Living without atomic clocks).

Lamport & HLC (scalar)

  • Constant-size metadata (one counter or one 64-bit value)
  • Respects causality: a → b implies ts(a) < ts(b)
  • Gives a total order for logs, MVCC, and snapshots
  • Cannot prove two events are concurrent
  • HLC additionally stays close to real time

Vector & version vectors

  • Metadata grows with the number of writers/replicas
  • Exactly characterizes happened-before vs concurrent
  • Lets stores keep siblings instead of losing writes
  • Needs pruning or dots to avoid size and sibling blow-up
  • Pushes conflict resolution to app logic or CRDTs
Clock skew still matters with HLC. CockroachDB gives every transaction an uncertainty interval of [commit_ts, commit_ts + max_offset]; the default max offset is 500 ms, and a node that measures itself more than 80% of that away from at least half its peers shuts itself down, because exceeding the bound can produce stale reads that violate single-key linearizability (Clock management in CockroachDB; CockroachDB transaction layer docs).

Real-World Use Cases

Amazon Dynamo
Vector clocks on each object version detect divergent shopping-cart updates; the client merges siblings on read (SOSP 2007).
Riak KV
Dotted version vectors per key keep only genuinely concurrent siblings, avoiding sibling explosion (Riak docs).
CockroachDB
HLC timestamps order MVCC versions and transactions; uncertainty intervals cover bounded clock skew (pkg/util/hlc).
MongoDB
A hybrid logical cluster time, gossiped and HMAC-signed, backs causally consistent sessions via afterClusterTime (driver spec; arch guide).
Google Spanner
TrueTime intervals plus commit wait give externally consistent timestamps without logical counters (OSDI 2012).
Mutual exclusion & logs
Lamport’s total order lets replicas agree on request order for locks and replicated state machines (Lamport 1978).

Choosing one

If you need a total order and compact timestamps (logs, MVCC, snapshot reads), reach for HLC, or Lamport clocks when real time doesn’t matter. If you accept writes on multiple replicas and must never silently drop one, you need version vectors (ideally dotted) or a merge-friendly data type. And whichever you pick, monitor clock synchronization: logical clocks protect causality, but anything that maps them back to wall time still depends on bounded skew.
