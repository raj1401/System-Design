Futexes: Fast Userspace Mutexes

How Linux makes uncontended locking almost free by keeping the kernel out of the way until it's actually needed

August 1, 2026 · 5 min read

The Concept in One Breath

A futex ("fast userspace mutex") is a Linux kernel facility that lets a program do the overwhelmingly common part of locking — acquiring and releasing an uncontended lock — entirely in userspace with a single atomic instruction, and only trap into the kernel when there's actual contention to arbitrate. The Linux kernel provides futexes ("Fast user-space mutexes") as a building block for fast user-space locking and semaphores, and futexes are optimized for the noncontended case. A futex consists of a kernel-space wait queue that is attached to an atomic integer in userspace.

Before futexes existed, every lock/unlock pair meant a system call, because the kernel was the only place that could safely coordinate sleeping and waking threads. Before futexes, every lock operation required a system call, and system calls are expensive because they require context switching from userspace to kernel space. Futexes flip that around: the kernel is invoked only on the unhappy path.

Why this matters: Locking primitives sit on the hottest path of nearly every multithreaded program. As applications became more concurrent, locking started showing up as a significant bottleneck in performance profiles, which is frustrating since locks don't do any actual work — they're just overhead for safety. A synchronization primitive that costs a syscall on every acquisition doesn't scale; futexes are the reason mutex/lock overhead on modern Linux is often just a few nanoseconds.

Deeper Dive: How the Fast and Slow Paths Actually Work

The futex word

In its bare form, a futex is an aligned integer which is touched only by atomic assembler instructions, and this integer is four bytes long on all platforms. That's the entire kernel-visible state: a plain 32-bit word sitting in a process's address space. Userspace libraries overlay meaning onto its bits — e.g. 0 = unlocked, a thread ID = locked, a high bit = "waiters present." Processes can share this integer using mmap, via shared memory segments, or because they share memory space, in which case the application is commonly called multithreaded.

FUTEX_WAIT and FUTEX_WAKE

The two workhorse operations are exposed through the futex(2) syscall. FUTEX_WAIT tests that the value at the futex word still contains the expected value, and if so, sleeps waiting for a FUTEX_WAKE operation; the load, the comparison, and starting to sleep are performed atomically and totally ordered with respect to other futex operations on the same word. This atomicity closes the classic wait/wake race: without it, a thread could check the value, get preempted right before sleeping, miss a wake-up that happened in between, and sleep forever.

On the wake side, FUTEX_WAKE returns the number of waiters that were woken up — typically the unlocking thread passes a count of 1 (wake one waiter) or a large number to wake everyone. Futex operation is entirely in user space for the noncontended case; the kernel is only involved to arbitrate the contended case.

The kernel side: a hash table of wait queues

The kernel maintains a hash table keyed by memory addresses, mapping to wait queues; when a thread calls FUTEX_WAIT, it's added to the appropriate queue and suspended, and FUTEX_WAKE removes threads from the queue and makes them runnable again. Crucially the kernel doesn't need to know anything about what the integer means — it just needs a place to park sleeping threads keyed by an address, and to compare the value at that address before committing to sleep. This is why futexes generalize to mutexes, semaphores, condition variables, and barriers: they are very basic and lend themselves well to building higher-level locking abstractions such as mutexes, condition variables, read-write locks, and barriers.

Because the same physical page can be mapped at different virtual addresses in different processes, the kernel resolves the futex identity through the underlying page/inode rather than the raw pointer value, which is what lets futexes work across process boundaries in shared memory as well as within a single multithreaded process.

Fast Path vs. Slow Path

A minimal three-state mutex

The classic userspace mutex built on a futex uses three states in the word: 0 (unlocked), 1 (locked, no waiters), and 2 (locked, with waiters). Lock does an atomic compare-and-swap of 0→1; if that fails, it atomically swaps in 2 and calls FUTEX_WAIT to sleep while the value is 2. Unlock atomically decrements/exchanges to 0 and, only if the previous value was 2, issues FUTEX_WAKE. This distinguishing of "locked, but nobody is waiting" from "locked, and someone is sleeping" is exactly what avoids a wake syscall in the common uncontended unlock, and it is the design popularized in glibc's NPTL implementation.

Priority inheritance and robustness

Two extensions solve real production problems. PI-futexes address priority inversion: priority inheritance is currently the only technique that enables good determinism for userspace locks, because without it a medium-priority task can preempt a low-priority lock holder and delay a high-priority waiter indefinitely. With PI-futexes, the userspace fastpath involves no kernel work at all — no registration, no extra kernel calls, just pure fast atomic ops — and even the slowpath's syscall and scheduling pattern closely resembles normal futexes.

Robust futexes solve a different problem: what happens if a lock holder dies mid-critical-section? There's a conceptual catch-22: it's the kernel that destroys the crashing owner task, but the kernel has no information to clean up the held lock, and userspace has no opportunity to clean up either since it's the one that crashed. The fix is a userspace-maintained linked list of held locks that the kernel walks at thread-exit time, which is much faster than the earlier VMA-based approach since there's no need to loop over every VMA — only a simple "is the list empty" check is done.

Note how two different userspace addresses (M1's word, waited on by threads B and C) hash into the same bucket as another lock in this illustration — a normal hash collision. The kernel simply walks the bucket's queue and compares the actual address of each waiter to decide who to wake, which is why FUTEX_WAIT re-validates the value atomically instead of trusting bucket membership alone.

Comparing Locking Strategies

Futex-based mutex

  • Zero syscalls when uncontended
  • Thread sleeps (no CPU burn) when contended
  • Scales from single-process to shared-memory IPC
  • Basis for glibc, Rust, Go, and JVM locks

Pure spinlock

  • No syscall ever, but busy-waits on failure
  • Wastes CPU cycles under contention
  • Only sane for very short critical sections
  • Dangerous if the holder is preempted mid-lock

Classic System V semaphore

  • Every wait/signal is a syscall, even uncontended
  • Every lock operation historically required a system call like semop, which is expensive due to context switching
  • Simple and portable, but heavy under load
  • Largely superseded by futex-backed primitives on Linux

Real-World Use Cases

glibc / NPTL pthreads
glibc uses futex-based syscalls as a means to implement higher level interfaces like pthreads, including mutexes, semaphores, and condition variables.
Language runtimes
Futexes are the secret sauce that makes modern Linux threading efficient, powering everything from pthread mutexes to Go's sync.Mutex.
Real-time schedulers
PI-futexes back priority-inheriting pthread mutexes used in real-time and safety-critical Linux systems to bound priority-inversion latency.
Package managers & daemons
Robust futex cleanup prevents scenarios like a crashed package manager leaving a held lock that would otherwise require a system reboot to release.

Semantics Under the Hood

It's worth stressing how narrow the kernel's job really is. A futex is identified by a piece of memory that can be shared between different processes, and need not have identical addresses in each; in its bare form it has semaphore-like semantics, a counter that can be incremented and decremented atomically, and processes can wait for the value to become positive. All of the policy — what values mean "locked," how many waiters to track, whether to prefer FIFO or LIFO wake order — lives entirely in userspace libraries. The kernel maps addresses internally so that the same memory mapped at different virtual addresses in different processes still corresponds to the same futex.

Modern kernels also expose futex2/futex_waitv, letting a thread wait on multiple futex words simultaneously in one call — useful for implementing things like select-style multi-object waits without extra polling threads. futex2 is a follow-up interface designed to overcome limitations of the original one; futex_waitv lets userspace set an array of futex descriptors, each with its own address, expected value, and flags for type and size.

Why does this matter: Almost no application developer calls futex(2) directly — and that's the point. Callers are expected to adhere to nonportable, architecture-specific semantics, which means most users will in fact be library authors, not general application developers. Understanding futexes explains why a pthread_mutex_lock() call on an uncontended lock is essentially free, while understanding the wake/sleep dance explains where thread contention costs actually come from when profiling multithreaded code.
