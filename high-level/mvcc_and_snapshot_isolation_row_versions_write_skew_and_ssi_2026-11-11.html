MVCC and Snapshot Isolation: Row Versions, Write Skew, and Serializable SI

Why readers never block writers in modern databases, and the one anomaly that sneaks through anyway.

November 11, 2026 · 5 min read

Summary

Multi-version concurrency control (MVCC) keeps several versions of each row instead of overwriting in place. A transaction reads from a consistent snapshot, the set of versions committed as of some point in time, while writers keep producing new versions. Readers therefore never wait on writers, and writers never wait on readers.

Snapshot Isolation (SI), formalized by Berenson et al. in A Critique of ANSI SQL Isolation Levels [1], is the isolation level MVCC naturally gives you: read a snapshot taken at your start timestamp, and commit only if no concurrent transaction already committed a write to the same items (first-committer-wins). SI prevents dirty reads, non-repeatable reads, and lost updates, but it is not serializable: it allows write skew. Serializable Snapshot Isolation (SSI) [3][4] closes that gap by detecting dangerous read-write dependency patterns at runtime and aborting one transaction.

Why this matters for system design: PostgreSQL REPEATABLE READ, InnoDB consistent reads, CockroachDB, and Spanner snapshot reads are all built on MVCC. Knowing exactly which anomalies your isolation level permits is the difference between a correct invariant and a production incident that only happens under concurrency.

Deeper Dive

1. Versions and visibility

Every write creates a new version stamped with the writing transaction. In PostgreSQL each row version (tuple) carries xmin, the ID of the inserting transaction, and xmax, the ID of the deleting or superseding transaction (zero if still live); an update is a delete of the old version plus an insert of a new one [5]. A reader compares those IDs against its snapshot, the set of transactions that had committed when the snapshot was taken, and sees a version only if its creator committed before the snapshot and its deleter did not [5][7].

InnoDB takes the opposite physical approach. The clustered-index row holds only the newest version plus a 6-byte DB_TRX_ID and a 7-byte DB_ROLL_PTR pointing into the undo log; a consistent read walks that roll pointer chain backward to rebuild the version its read view is allowed to see [8][9].

Version chain and snapshot visibility

2. Snapshot Isolation rules

Berenson et al. define SI precisely [1]: a transaction reads from the committed state as of its Start-Timestamp (plus its own writes). At commit it takes a Commit-Timestamp and succeeds only if no other transaction with a commit timestamp inside its [start, commit] interval wrote any item it also wrote. That first-committer-wins rule prevents lost updates. Because the snapshot is fixed, SI also avoids the read skew and predicate re-read anomalies that plague lock-based REPEATABLE READ, which makes SI incomparable to REPEATABLE READ and strictly weaker than SERIALIZABLE [1][2].

In practice, PostgreSQL READ COMMITTED takes a fresh snapshot per statement and REPEATABLE READ uses one snapshot for the whole transaction [6]; InnoDB REPEATABLE READ (its default) pins the snapshot at the first consistent read [10]. Concurrent writers to the same row get a serialization failure or block on the row lock, and the application must retry [6].

3. Write skew: the anomaly SI lets through

SI only checks write-write overlap. If two transactions read overlapping data but write disjoint items, both commit even when together they break an invariant. Berenson's history H5 is the canonical case: with the constraint x + y > 0 and both starting at 50, T1 reads x and y and sets y = -40, T2 reads the same snapshot and sets x = -40. Each transaction preserved the constraint against its snapshot; the combined result violates it [1]. Real-world variants: two on-call engineers each checking that someone else is on call before going off shift, or two bookings each confirming a room is free before inserting a reservation.

Write skew under snapshot isolation

4. Serializable Snapshot Isolation (SSI)

Fekete et al. proved that every non-serializable SI execution contains a dangerous structure: two consecutive rw-antidependency edges between concurrent transactions, T_in → T_pivot → T_out (an rw edge means one transaction read a version that the other overwrote) [3][11]. Cahill, Röhm and Fekete turned that theorem into a runtime algorithm: keep running transactions under SI, track rw-conflicts with non-blocking SIREAD markers, and abort a transaction when a pivot with both an incoming and an outgoing edge appears [3]. Readers still never block writers, at the price of occasional false-positive aborts [11].

PostgreSQL 9.1 shipped the first production SSI as its SERIALIZABLE level, with a purpose-built predicate lock manager, bounded-memory summarization of old transactions, and a read-only optimization; Ports and Grittner measured a cost under 7% relative to SI, and large wins over two-phase locking on read-heavy workloads [4].

SSI dangerous structure (rw-antidependencies)

5. The cost: garbage, long transactions, and wraparound

Old versions must stay as long as any snapshot might need them. PostgreSQL leaves dead tuples in the heap until VACUUM reclaims them, and must also freeze old rows because its 32-bit transaction IDs wrap around; a table must be vacuumed at least once every two billion transactions to avoid catastrophic invisibility [12][13]. InnoDB keeps update-undo records until no read view needs them and then purges them; MySQL explicitly warns that long-running transactions, even read-only ones, let the rollback segment grow until it fills the undo tablespace [8][14]. A forgotten idle transaction is therefore a classic MVCC outage cause.

Snapshot Isolation

  • Readers never block, writers conflict only on same item
  • First-committer-wins prevents lost updates
  • Permits write skew and read-only anomalies
  • Fix by hand: SELECT ... FOR UPDATE or materialized conflicts

Serializable SI

  • Same non-blocking reads as SI
  • Tracks rw-antidependencies with SIREAD markers
  • Aborts on dangerous structures, so clients must retry
  • Small overhead; some false-positive aborts

6. MVCC in distributed databases

MVCC generalizes nicely once versions are keyed by timestamps rather than local transaction IDs. CockroachDB stamps each transaction with a hybrid logical clock timestamp, serves reads at that timestamp from MVCC history, and uses a timestamp cache to push or restart writers that would invalidate a read, giving serializable isolation by default [15][16]. Spanner assigns TrueTime commit timestamps, so a snapshot read at timestamp t returns a globally consistent view from any sufficiently up-to-date replica without taking locks; clients can even request bounded-staleness reads [17][18].

Real-World Use Cases

PostgreSQL
Heap tuples with xmin/xmax, per-statement or per-transaction snapshots, and SSI behind SERIALIZABLE [4][5][6].
MySQL InnoDB
Newest row in place, older versions rebuilt from undo logs for consistent nonlocking reads; purge threads collect history [8][10][14].
CockroachDB
HLC-timestamped MVCC keys plus a timestamp cache to keep distributed transactions serializable [15][16].
Google Spanner
TrueTime-stamped versions enable lock-free, globally consistent snapshot and stale reads [17][18].
Consistent backups
A long-lived snapshot lets pg_dump-style exports or analytics scans read a coherent state while OLTP writes continue (at the cost of retained versions).
Booking and scheduling
Room, seat, and on-call invariants are the textbook write-skew victims; use SERIALIZABLE or explicit locking for them.
Design checklist: (1) Know which level your database calls REPEATABLE READ versus SERIALIZABLE, because the names are not portable. (2) If an invariant spans multiple rows, either run at SSI and retry on serialization failure, or lock the rows you read. (3) Alert on the oldest open transaction age; it governs version bloat.
