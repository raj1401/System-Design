Change Data Capture (CDC): Log-Based Streaming

How to stream row-level database changes from the transaction log without dual writes or brittle polling

October 9, 2026 · 5 min read

The Concept, Briefly

Modern systems rarely keep their truth in a single store. Search indexes, analytics warehouses, caches, fraud engines, and sibling microservices all need to stay current with the primary database. The naive fix—have the application write the row and publish an event—is the dual-write problem: a crash between those two steps loses or invents updates. Polling with SELECT … WHERE updated_at > ? is safer but laggy, misses deletes unless you soft-delete, and hammers the primary under load.

Change Data Capture (CDC) takes a different route. Databases already write every committed change to a durable transaction log—MySQL’s binary log (binlog), PostgreSQL’s write-ahead log (WAL) via logical decoding. CDC tools such as Debezium subscribe to that log, emit ordered row-level events (insert, update, delete), and stream them to Kafka or another broker. Only committed changes appear; rolled-back transactions never become events. Application code keeps writing to the database alone.

Key idea: CDC does not invent a second write path. It reuses the log the database already maintains for crash recovery and replication, turning that append-only history into a durable change stream for downstream consumers.

Underlying Ideas & Mechanisms

Three Ways to Capture Changes

Teams historically used three CDC styles. Query-based CDC polls tables on a timestamp or version column—simple, but high lag, no reliable delete capture, and extra index/load cost. Trigger-based CDC fires database triggers on DML to write into a change table—accurate, but every write pays trigger overhead and you maintain trigger code per table. Log-based CDC reads the transaction log as a replica would: near-real-time, minimal primary impact beyond what replication already requires, and complete coverage of inserts, updates, and deletes in commit order.

CDC Capture Strategies Compared

Binlog, WAL, and Logical Decoding

On MySQL, the binlog records committed operations in order. For CDC you want binlog_format=ROW and usually binlog_row_image=FULL so each event carries before/after images. Debezium registers as a replica, consumes the same stream a read replica would, and emits Kafka records per row change. Because binlogs are purged on a schedule, connectors take an initial snapshot, then stream from the binlog position recorded at snapshot time.

On PostgreSQL, physical WAL describes storage-level changes. Logical decoding turns those into row-level tuples via an output plugin. Debezium typically uses the built-in pgoutput plugin (PostgreSQL 10+) and a logical replication slot—a crash-safe cursor that prevents WAL removal until the consumer advances. Slots are both a safety net and a footgun: an idle or stuck slot retains WAL indefinitely and can fill disk. Monitor slot lag and pg_replication_slots as first-class SLO signals.

Ordering, Offsets, and Delivery

Log-based CDC preserves commit order within a single log stream. Debezium records offsets (MySQL binlog filename+position, PostgreSQL LSN) in Kafka Connect so a restart resumes without gaps from the last acknowledged position. PostgreSQL docs note that after a crash a slot may re-send recent changes—clients must tolerate duplicates. In practice delivery to the broker is at-least-once: design consumers around primary keys, event ids, or upsert/delete semantics, not “exactly once because CDC.”

Kafka partitioning usually keys by primary key so a given row’s updates stay ordered within a partition. Cross-table or cross-shard global order is not free; if you need it, use a single partition (throughput cost) or application-level sequencing.

Schema Evolution

Tables change. MySQL connectors parse DDL from the binlog and keep an in-memory schema plus a schema-history topic so later row events decode correctly. PostgreSQL logical decoding does not stream DDL the same way; Debezium refreshes schema metadata over JDBC and has limitations around DDL during incremental snapshots. Pair CDC with a schema registry (Avro/Protobuf) and prefer additive, backward-compatible migrations. Breaking column renames or type changes need coordinated consumer upgrades—treat the change stream as a public API.

CDC vs Dual-Write vs Transactional Outbox

These three patterns address related but different problems. Dual-write is the anti-pattern: app writes DB and broker separately. The transactional outbox keeps intentional domain events in an outbox table inside the same DB transaction, then relays them—great when you want curated, versioned business events. Log-based CDC captures every row change on selected tables without application cooperation, ideal for caches, search, analytics, and legacy systems you cannot easily instrument. You can combine them: write outbox rows in-app, then let Debezium’s Outbox Event Router stream only those rows as clean domain events.

Log-Based CDC

  • No app dual-write code
  • Captures all row ops incl. deletes
  • Near-real-time via WAL/binlog
  • Needs Connect + slot/binlog ops
  • Best for data fan-out & sync

Transactional Outbox

  • Intentional domain event contracts
  • Atomic with business commit
  • Poller or CDC relay
  • Devs can forget the outbox write
  • Best for service-to-service events

When CDC Wins

  • Legacy apps you cannot change
  • Search, cache, warehouse sync
  • Audit / activity streams from tables
  • Multi-consumer fan-out from one log
  • You already run Kafka Connect

Watch-outs

  • Stuck replication slots fill disk
  • Still at-least-once to consumers
  • Schema breaks hurt all consumers
  • Not a substitute for domain events
  • PII in the log becomes a stream risk

Real-World Use Cases

Search Index Sync
Stream product or document table changes into Elasticsearch/OpenSearch so search stays fresh without dual writes from the write API.
Cache Invalidation
Invalidate or upsert Redis entries from primary-key CDC events instead of TTLs alone or scattershot delete calls.
Analytics & Warehouses
Feed Snowflake, BigQuery, or a lakehouse with continuous inserts/updates/deletes for near-real-time dashboards.
Microservice Integration
Legacy monolith tables become event sources for new services; optionally filter to an outbox table for curated payloads.

Trade-offs to Keep in Mind

Log-based CDC is the production default when you need the database’s truth elsewhere without teaching every write path to publish. You trade application simplicity for operational work: replication privileges, snapshot strategy, connector monitoring, WAL retention, schema compatibility, and consumer idempotency. Prefer CDC for wholesale data movement and sync; prefer an explicit outbox when the contract is a domain event, not a raw row image. Never treat the change stream as exactly-once magic—design for duplicates, late schema changes, and the day a replication slot stops advancing.

If this series already covered transactional outbox, CQRS, and message delivery guarantees, CDC is the missing piece that turns the database log itself into an integration bus—powerful, operationally real, and distinct from application-level event publishing.
