Multi-Gen LRU (MGLRU): Generational Page Reclaim in Linux

Instead of two lists and a guess, Linux sorts memory into a sliding window of generations and lets refaults tell it when it guessed wrong.

October 12, 2026 · 5 min read

Summary

When RAM runs out, the kernel has to pick pages to throw away: clean file pages it can drop, dirty ones it must write back, anonymous pages it must push to swap or zram. That choice is page reclaim, and it decides both how much CPU kswapd burns and how often your app stalls on a major fault. For decades Linux made the choice with two LRU lists per memory cgroup and node, active and inactive. Google engineer Yu Zhao's Multi-Gen LRU (MGLRU), merged in Linux 6.1, replaces that pair with up to four generations of pages ordered by access recency, finds hot pages by walking page tables rather than reverse maps, and uses a refault-driven feedback loop to choose between file and anonymous memory (kernel design doc, LWN 6.1 merge window).

Headline numbers: before merging, Google rolled MGLRU out to tens of millions of Chrome OS users and about a million Android users, and reported a 40% drop in kswapd CPU usage fleet-wide, 85% fewer low-memory kills at the 75th percentile, and 18% faster app launches at the median (v14 cover letter).

What was wrong with two lists

The classic scheme puts recently used pages on the active list and lets cold ones slide to the inactive list, a purgatory where a second touch promotes the page back and no touch means eviction (LWN, 2021). Zhao's patches named the problems with that model. Two buckets are too coarse to rank pages, and pages often sit on the wrong list. Each cgroup has its own lists, so the kernel cannot easily compare page age across cgroups. A long-standing bias toward evicting file pages can toss useful page cache while idle anonymous memory stays put, which hurts most on cloud machines with little local storage.

The deepest cost is how the kernel learns that a mapped page was used. The hardware sets an accessed bit in the page table entry (PTE), but reclaim walks physical pages, so for each candidate it must use the reverse map (rmap) to find every PTE that maps it. Those PTEs live in unrelated page tables, so each lookup is a string of cache misses. On a server with 99% of memory mapped, Zhao showed a proactive-reclaim profile where page_vma_mapped_walk alone took 41% of the CPU (LKML discussion).

Two lists versus a sliding window of generations

Generations: a sliding window of age

Each lruvec (one per memory cgroup per NUMA node) carries a struct lru_gen_folio. Its max_seq counts the youngest generation and is shared by anon and file pages so they age on equal footing; min_seq[] tracks the oldest generation separately for each type, because clean file pages can be evicted even when swap is unavailable. All three only ever increase (design doc). Pages live on folios[MAX_NR_GENS][ANON_AND_FILE][MAX_NR_ZONES] lists, and each generation records a birth timestamp in jiffies (mmzone.h).

Sequence numbers are unbounded, but each folio stores only a small gen counter in spare bits of folio->flags, which is seq % MAX_NR_GENS + 1 (zero means not on an MGLRU list). Upstream sets MIN_NR_GENS to 2 and MAX_NR_GENS to 4, so the kernel keeps between two and four live generations at a time. The two youngest act like the old active list and are never evicted; only older generations are candidates (mmzone.h, admin guide).

The clever part is that demotion is free. Making a new generation is just incrementing max_seq; every page not explicitly promoted is now one generation older without being touched. Lists are also lazily sorted: when aging finds a page accessed, it updates the gen counter in the folio flags, and the page is only physically moved to the right list when eviction reaches it.

Tiers for file-descriptor access

Pages read with read() are never mapped, so no accessed bit exists for them. MGLRU splits each generation into tiers: a page accessed N times through file descriptors sits in tier order_base_2(N), up to MAX_NR_TIERS (4). Moving between tiers is an atomic update to folio->flags, not a list move under the LRU lock. Zhao's reasoning was that promoting a page to a new generation on its second read would burn through old generations too fast; with a random buffered read of a file twice the size of RAM, he measured shrink_active_list() at over 6% of kswapd CPU doing work that made no better decisions (LKML discussion).

Aging and eviction: a closed loop

Reclaim is two independent procedures that form a producer and consumer pair (design doc).

Aging produces young generations. When the window shrinks toward MIN_NR_GENS, aging walks each process on the cgroup's mm_struct list with walk_page_range(), scanning PTEs in virtual-address order. That is cache friendly, since one 4 KiB page table holds 512 adjacent PTEs. On each young PTE it clears the accessed bit and sets the page's gen counter to the youngest generation. Several walkers can run in parallel because each takes a different mm_struct, and processes that have not run since the last pass are skipped. After the walk, max_seq increments.

Eviction consumes the oldest generation. It picks the type (anon or file) whose min_seq is older; on a tie it takes the one whose first tier refaults less. Pages whose gen counter shows they were promoted are moved instead of evicted. When the oldest list empties, min_seq increments.

Aging, eviction, and the feedback between them

Spatial locality and Bloom filters

Page table walks are cheap per PTE but wasted on sparse address spaces; rmap walks target one page but learn nothing about its neighbors. MGLRU uses both. When eviction does go through the rmap and finds a young PTE, lru_gen_look_around() scans the adjacent PTEs in the same table and promotes their hot pages too. If that table turned out densely hot, the PMD entry pointing to it goes into a Bloom filter, and the next aging pass only descends into PTE tables the filter says may be hot (design doc). On x86 the hardware also sets accessed bits in non-leaf entries, which lets aging skip whole untouched regions; these behaviors are controlled by bits 0x0002 and 0x0004 of /sys/kernel/mm/lru_gen/enabled (admin guide).

The PID controller

Choosing between anon and file memory is where the old LRU had a built-in bias. MGLRU instead runs a feedback loop modeled on a proportional-integral-derivative (PID) controller. It tracks moving averages of how many pages from each type and tier were evicted and then refaulted (brought back soon after, a sign of a bad choice), with the first tier as the baseline, and protects tiers whose refault rate stands out. The goal is to keep refault percentages of anon and file balanced in proportion to swappiness. Its clock is generations rather than wall time, because scan rate varies wildly with memory pressure (design doc).

Classic active/inactive LRU

  • Two ages per list: active or inactive
  • Accessed bits gathered page by page through the rmap
  • Hard to compare age across cgroups
  • Heuristic bias toward evicting file pages
  • Decades of tuning across many workloads

Multi-Gen LRU

  • Two to four generations with birth timestamps
  • Page table walks plus look-around and Bloom filters
  • Generations are a shared time base across cgroups
  • Refault feedback balances anon and file
  • About 500 bytes per memcg and node, about 50 per process

The memory overhead figures come from Zhao in the LWN comment thread, where he also noted the extra per-page state lives in spare bits of the page flags.

Knobs worth knowing

MGLRU builds with CONFIG_LRU_GEN, and CONFIG_LRU_GEN_ENABLED decides whether it is on at boot; upstream leaves that default off, so the choice is up to each distribution or device vendor (mm/Kconfig). At runtime, echo n > /sys/kernel/mm/lru_gen/enabled is the kill switch that falls back to the classic lists, a safety valve memory-management maintainers asked for before merging (LWN, LSFMM 2022).

Because every generation is timestamped, MGLRU can also protect a working set by time. Writing N to min_ttl_ms prevents pages used in the last N milliseconds from being evicted, and triggers the OOM killer if that set cannot fit. The admin guide suggests 1000 to eliminate intolerable desktop jank from thrashing, aimed at laptop and desktop users without oomd (admin guide).

Real-world use cases

Phones and Chromebooks
Android and Chrome OS shipped MGLRU first; fewer low-memory kills means fewer apps and tabs reloading from scratch (v14 cover letter).
Desktop distros and kernels
The cover letter lists Arch Linux Zen, Armbian, Liquorix, XanMod and others as users of the patches before they reached mainline.
Datacenter bin packing
Reading /sys/kernel/debug/lru_gen yields a per-memcg, per-node histogram of page ages that a scheduler can use to estimate working sets before placing a job (admin guide).
Proactive reclaim to zram
The - command evicts generations older than a chosen one with no memory pressure, using page table walks instead of the rmap scans that made this costly on mostly mapped systems (admin guide).
Memory overcommit at scale
A later memcg LRU, an LRU of per-cgroup LRUs, makes global reclaim pick cgroups in O(1) best case instead of walking them all (Phoronix).
Jank-free laptops
min_ttl_ms turns thrashing into a quick OOM kill of a likely idle app instead of a frozen UI.
Design lesson: MGLRU wins less by a smarter eviction rule than by gathering the evidence differently. Scanning page tables in address order, and letting one hot PTE pull in its 511 neighbors, turned the most expensive part of reclaim into a mostly sequential sweep, and the refault feedback loop corrects the cheap guesses that remain.
