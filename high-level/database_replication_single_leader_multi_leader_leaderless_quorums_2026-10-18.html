Database Replication: Single-Leader, Multi-Leader, and Leaderless Quorums

Copying data to more machines is easy. Deciding who accepts writes, and when a write counts as done, is the whole design.

October 18, 2026 · 5 min read

Summary

Replication keeps a copy of the same data on several machines so the system survives node failures, serves reads closer to users, and scales read throughput. Almost every design answers two questions. First, who accepts writes? One leader, several leaders, or any replica. Second, when is a write acknowledged? After the leader alone has it (asynchronous), after at least one replica confirms it (semi-synchronous), or after a set number of replicas confirm it (synchronous or quorum). Kleppmann's Designing Data-Intensive Applications (chapter 5) organizes the field the same way, and most production databases are one point on these two axes.

The answers determine what can go wrong. Asynchronous followers can lag, so a user may not see their own write. Multiple leaders can accept conflicting writes that must be merged later. Leaderless systems trade a single point of ordering for quorum math, plus background repair to bring stale replicas back in line (DeCandia et al., 2007).

Core rule: Every replication scheme balances write latency against what you can lose or read stale when a node fails. Choose the acknowledgement rule first, then the topology.

How it works

1. Three topologies

Single-leader (primary/replica): every write goes to one node, which streams its change log (WAL, binlog, oplog) to followers in order. Reads can go to any follower. PostgreSQL streaming replication, MySQL replication, and MongoDB replica sets all work this way. Multi-leader: several nodes, often one per region, accept writes and replicate to each other asynchronously, so concurrent writes to the same item can conflict. DynamoDB global tables in their default mode replicate item changes between Regions "typically within a second or less" and resolve concurrent writes with "last writer wins" on an internal timestamp (DynamoDB global tables). Leaderless: the client or a coordinator sends each write to N replicas and waits for W acknowledgements, and reads ask R replicas. This is the Dynamo model, used by Cassandra and Riak.

Who accepts writes: three replication topologies

2. Sync, async, and semi-sync acknowledgement

PostgreSQL's docs state the default plainly: "streaming replication is asynchronous by default," so if the primary crashes, some committed transactions may never reach the standby. Synchronous replication makes each commit wait until the commit record is on disk on both primary and standby. The synchronous_commit setting lets you choose how far the standby must get: remote_write (received and written), on (flushed), or remote_apply (replayed, so reads on the standby see it). synchronous_standby_names accepts FIRST num_sync (...) for priority-based waits or ANY num_sync (...) for quorum-based waits (PostgreSQL high availability, replication settings).

MySQL's semi-synchronous mode is the common middle ground. The source waits until at least one replica has written the transaction to its relay log and flushed it to disk. Under the default rpl_semi_sync_source_wait_point = AFTER_SYNC, the source syncs its binlog, waits for that acknowledgement, and only then commits to the storage engine. If no replica answers within rpl_semi_sync_source_timeout (default 10,000 ms), "the source reverts to asynchronous replication" until a replica catches up (MySQL semisync, source options). That fallback keeps the database available, but it also means the durability guarantee quietly lapses exactly when replicas are in trouble.

3. Replication lag and session guarantees

With asynchronous followers, a read routed to a lagging replica can return old data. Terry et al. named the anomalies users actually notice and defined four session guarantees to prevent them: Read Your Writes (reads reflect your earlier writes), Monotonic Reads (successive reads never go back in time), Writes Follow Reads, and Monotonic Writes (Terry et al., PDIS 1994; see also Jepsen's consistency models). Common implementations: read your own recently written data from the leader, pin a user's session to one replica, or have the client carry the log position of its last write and wait until a replica has caught up to it. MongoDB packages this as causally consistent sessions. With "majority" read and write concern, a session gets all four guarantees, even across a primary failover (MongoDB causal consistency).

4. Quorum math: R + W > N

In a leaderless store with N replicas per key, a write succeeds after W acknowledgements and a read after R responses. If R + W > N, every read set overlaps every write set in at least one replica, so a read sees the latest acknowledged write. Dynamo calls this "a quorum-like system," and the common Dynamo configuration was (N, R, W) = (3, 2, 2) (DeCandia et al.). Cassandra exposes the same knob per request through consistency levels: QUORUM is a majority of replicas, and LOCAL_QUORUM is a majority within the coordinator's datacenter, which only guarantees seeing the latest write from that datacenter (Cassandra Dynamo architecture).

Many deployments deliberately run partial quorums (R + W ≤ N, e.g. R = W = 1) for latency. Bailis et al. measured how stale those reads really get with Probabilistically Bounded Staleness. Using production latency data, they found such systems "frequently return consistent data within tens of milliseconds," and in one LinkedIn environment, moving from spinning disks to SSDs cut the wait for a 99.9% chance of a consistent read from 45.5 ms to 1.85 ms (Bailis et al., VLDB 2012).

N = 3, W = 2, R = 2: the read set must overlap the write set

5. Sloppy quorums, hinted handoff, read repair, anti-entropy

A strict quorum becomes unavailable when too many of a key's home replicas are unreachable. Dynamo instead uses a sloppy quorum: reads and writes go to "the first N healthy nodes from the preference list." If node A is down, its replica goes to node D with a hint naming A, and D delivers it once A recovers (hinted handoff). The price is that during the failure, R and W sets may not overlap, so the overlap guarantee is suspended (DeCandia et al.). Cassandra retains hints for up to max_hint_window, 3 hours by default (Cassandra hints).

Two mechanisms clean up what handoff misses. Read repair: if a read sees stale versions, the coordinator writes the newest version back to those replicas, which Dynamo describes as repairing replicas "at an opportunistic time." Anti-entropy: replicas exchange Merkle tree roots per key range and walk down only the branches that differ, so they sync mismatched keys without shipping whole datasets. Cassandra treats read repair and hints as best-effort and relies on anti-entropy repair to guarantee eventual consistency, adding sub-range and incremental repair on top of Dynamo's design (Cassandra, read repair, repair).

Trade-offs

Single-leader

  • One write order, so no write conflicts
  • Simple read scaling with followers
  • Failover needs election and fencing; async lag means lost writes on failover
  • All writes funnel through one node and one region

Multi-leader

  • Local-latency writes in every region
  • Keeps accepting writes during inter-region partitions
  • Concurrent writes conflict; LWW silently discards one
  • Hard to support unique constraints and counters correctly

Leaderless quorums

  • No failover step; a slow node just stops being in the quorum
  • Consistency is tunable per request via R and W
  • Sloppy quorums and concurrent writes still allow stale or conflicting reads
  • Needs versioning (vector clocks) plus ongoing repair

Ack mode

  • Async: lowest latency, can lose recent commits
  • Semi-sync: survives a single crash, degrades to async on timeout
  • Sync / quorum: no acknowledged loss, but tail latency follows the slowest required replica
Quorums are not linearizability: Even with R + W > N, a sloppy quorum, a write that failed after reaching only some replicas, or concurrent writes resolved by clock timestamps can all produce reads that look out of order. If you need compare-and-set or strict ordering, use a consensus-backed leader (Raft or Paxos) rather than quorum reads alone.

Real-world use cases

PostgreSQL HA
A primary streams WAL to hot standbys. Setting synchronous_standby_names = 'ANY 1 (s1, s2)' means a commit needs one of the two standbys to confirm (PostgreSQL).
Amazon Aurora
The storage layer keeps six copies of the data across three AZs, with a write quorum of 4 and a read quorum of 3. Up to 15 replicas share the cluster volume, with lag "usually much less than 100 milliseconds" (Aurora quorums, Aurora replication).
DynamoDB global tables
The default multi-Region eventual mode is multi-leader with last writer wins. The strong mode (MRSC) replicates synchronously and must be deployed in exactly three Regions, or two replicas plus a witness (DynamoDB).
Cassandra / Dynamo
Leaderless replication with per-query consistency levels, hinted handoff, read repair, and Merkle-tree repair. Amazon's shopping cart was the original motivating workload (Dynamo).

Design checklist

Decide what an acknowledged write must survive (one node, one AZ, one region), and pick the acknowledgement mode to match. Watch for silent fallbacks such as semi-sync timeouts. Measure replication lag and alert on it. Route read-after-write traffic to the leader, or wait on a log position, wherever users would notice stale data. Avoid multi-leader unless you need local writes in every region, and if you do, choose a conflict strategy deliberately. For leaderless stores, keep R + W > N where correctness matters, know when sloppy quorums suspend that guarantee, and schedule anti-entropy repair to finish within your tombstone or hint retention windows.
