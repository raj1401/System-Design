Idempotency Keys: Making Retries Safe in Distributed APIs

Why a client-generated token is the difference between “retry until it works” and “charge the customer twice.”

October 24, 2026 · 5 min read

Summary

In a distributed system a client that sends a request and hears nothing back cannot tell whether the request never arrived, failed halfway, or succeeded and the response got lost. Retrying is the obvious fix, but retrying a POST /charges can move money twice. HTTP already defines GET, PUT, and DELETE as idempotent, meaning that several identical requests have the same intended effect as one, while POST and PATCH are not (RFC 9110 §9.2.2, IANA method registry). RFC 9110 says a client should not automatically retry a non-idempotent request unless it has a way to know the semantics are actually idempotent or that the original was never applied.

An idempotency key is that way. The client generates a unique value (usually a UUID) per logical operation, sends it with every attempt, and the server uses it to recognize retries and return the original outcome instead of repeating side effects. The IETF HTTPAPI working group is standardizing this as the Idempotency-Key request header (draft-ietf-httpapi-idempotency-key-header-08), and it is how Stripe, AWS, and many payment APIs make writes retry-safe.

The core contract. AWS describes the goal as letting clients assume that any error that is not a validation error can be overcome by retrying the request until it succeeds. The complexity moves from every client into the service, once (Amazon Builders’ Library).

How It Works

1. The client owns uniqueness

The draft spec requires the key to be unique and never reused with a different payload, and recommends a UUID or similar random identifier, sent as a Structured Field string such as Idempotency-Key: "8e03978e-40d5-43e8-bc93-6894a57f9324" (draft §2.1–2.2). The key identifies the intent, not the bytes. AWS explains why it prefers a caller-provided identifier over hashing request parameters: two identical requests to create a DynamoDB table are probably duplicates, but two identical RunInstances calls might genuinely mean “I want two instances” (Builders’ Library). Stripe also warns against putting sensitive data like email addresses into keys (Stripe API reference).

2. The server records key and effect atomically

On the first request the server inserts a row keyed by (account, key), performs the work, and stores the response. The critical property, as AWS puts it, is that recording the token and all the mutating operations together must be ACID: if you could record the token but fail to create the resource, a retry would wrongly report success. A unique index on (user_id, idempotency_key) is the usual enforcement point, as in Brandur Leach’s reference Postgres design (Implementing Stripe-like Idempotency Keys in Postgres).

3. Retries are matched, compared, and replayed

A later request with the same key falls into one of four cases:

Same key, same payload, finished

  • Return the stored status and body
  • No side effects run again
  • Stripe v1 even replays stored 500s

Same key, still in flight

  • Reject with 409 Conflict
  • Client backs off and retries later
  • Prevents two workers racing

Same key, different payload

  • Reject as client misuse
  • Draft spec suggests 422
  • EC2 returns IdempotentParameterMismatch

Key missing or expired

  • 400 if the endpoint requires a key
  • After expiry, treated as a new request
  • Expiry window must be documented

To detect a changed payload the server keeps an idempotency fingerprint, such as a checksum of the whole body or of selected fields (draft §2.4). Stripe’s idempotency layer compares incoming parameters to the original and errors if they differ (Stripe); EC2 does the same with client tokens of up to 64 ASCII characters (EC2 idempotency guide).

Idempotent retry after a lost response

4. Multi-step requests need recovery points

Atomicity is easy when everything lives in one database transaction. It breaks when the request calls an external service (a card network, an email provider) that cannot be rolled back. Brandur’s design splits the request into atomic phases: local mutations committed in one transaction between each foreign call. After each phase the key row’s recovery_point advances (for example started, ride_created, charge_created, finished), so a retry resumes just before the step that failed instead of starting over (brandur.org, rocket-rides-atomic). Ideally the external call is itself idempotent, so you pass your own key downstream.

Idempotency key lifecycle with recovery points

5. Keys expire on a published schedule

Key stores cannot grow forever. The draft lets servers define a time-based expiry and says they should publish it (draft §2.3; see also MDN). Stripe API v1 can prune keys once they are at least 24 hours old, and a key reused after pruning becomes a new request; Stripe API v2 widens the replay window to 30 days and, instead of replaying a stored error, retries failed work to completion where possible (Stripe API v2 overview). The window should comfortably exceed the client’s total retry budget.

Not every failure should be retried. Stripe v1 does not save a result when validation fails or a concurrent request with the same key is still running, so those can be retried (Stripe). The EC2 guide recommends not retrying 4xx client errors but retrying 5xx server errors with backoff (EC2). For connection errors, Stripe advises treating the outcome as indeterminate and reconciling it before issuing a brand-new operation (Stripe error handling).

Design Pitfalls

Check-then-act races. Reading “does k1 exist?” and then inserting lets two concurrent retries both proceed. Rely on a unique constraint or conditional write and a lock column so exactly one attempt owns the key. Scoping. Scope keys per account, so one tenant’s UUID never collides with another’s. Regenerating keys on retry. A key must be created once per user intent (for example when the checkout form loads), not per HTTP attempt; Stripe’s SDKs generate keys and reuse them on automatic retries (Stripe). Caching too little. Store the full status and body so replays are byte-identical to what the client would have seen.

Real-World Use Cases

Payments
Stripe accepts Idempotency-Key on every v1 POST and every v2 POST and DELETE, so a timed-out charge can be retried without double billing.
Cloud control planes
EC2’s ClientToken makes RunInstances and similar calls retry-safe, and the token is visible on the created resource for auditing.
Event streaming
Kafka’s idempotent producer applies the same idea at the protocol level: a producer ID plus per-partition sequence numbers let brokers discard duplicate retries (KIP-98).
Order and booking APIs
Checkout, ride-hailing, and reservation flows that call external providers use recovery-point state machines so a crash mid-request resumes rather than duplicates.

Kafka’s version is a useful reminder of scope: enable.idempotence dedupes retries within one producer session, and requires settings such as acks=all (Kafka producer configs, Confluent delivery semantics). End-to-end, application-level keys are still needed when the sender itself restarts. Idempotency keys pair naturally with the at-least-once delivery and transactional outbox patterns covered earlier in this series: those guarantee a message is delivered, and idempotency guarantees delivering it twice is harmless.
