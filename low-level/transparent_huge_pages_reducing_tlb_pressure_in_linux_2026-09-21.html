Transparent Huge Pages: Reducing TLB Pressure in Linux

How the kernel promotes base pages to 2MB (and larger) pages — and when that helps or hurts

September 21, 2026 · 5 min read

Summary

Every virtual address walk ends at a Translation Lookaside Buffer (TLB) entry. On x86-64 a base page is 4 KB, so a large working set can thrash a TLB that holds only a few thousand entries. Transparent Huge Pages (THP) let the kernel back anonymous (and tmpfs/shmem) mappings with larger pages — traditionally a PMD-sized 2 MB page, and on modern kernels also intermediate multi-size THP (mTHP) orders like 16 KB–1 MB — so one TLB slot covers far more virtual memory.

Unlike hugetlbfs, THP needs no reserved pool and no application rewrite. Promotion can happen at fault time or asynchronously via the khugepaged daemon, which collapses contiguous base pages into a huge page; demotion (split) happens under pressure, partial unmap, or when a THP looks underused. Controls live under /sys/kernel/mm/transparent_hugepage/, with per-range hints via madvise(MADV_HUGEPAGE) / MADV_NOHUGEPAGE / MADV_COLLAPSE.

Deeper Dive

Why huge pages help

Kernel docs emphasize two effects. The first is fewer page faults on first touch: one fault can populate a 2 MB region instead of 512 separate 4 KB faults. The lasting win is TLB reach — a single entry maps 512× more memory, and TLB misses themselves are cheaper (especially under nested page tables in KVM). That is why databases, JVMs, and VMs that walk large heaps often see clear gains when THP sticks.

Collapse and split

At fault time, if policy allows and a naturally aligned free huge page is available (after optional compaction/defrag), the kernel may install a THP immediately. Otherwise it falls back to base pages. Later, khugepaged scans eligible VMAs and tries to collapse runs of base pages into a huge folio, respecting knobs like max_ptes_none (how many empty/zero PTEs are tolerated), max_ptes_swap, and max_ptes_shared.

The reverse path is split: a huge page may be broken into base pages for reclaim, swapout failure, mprotect/munmap on a subrange (PMD split into PTEs), or because the underused shrinker finds too many zero pages. Partially unmapped THPs land on a deferred-split list and are split under memory pressure.

Base pages vs PMD-sized THP (x86-64)

Anon vs file/shmem THP

Classic THP targets anonymous mappings. File-backed THP today is mainly tmpfs/shmem (SysV SHM, memfds, shared anonymous maps, some DRM objects), controlled via shmem_enabled and per-size knobs — not arbitrary ext4/XFS pages. khugepaged may collapse file/shmem only to PMD size; anonymous memory can also collapse to other mTHP orders when those sizes are enabled.

Policy knobs

Top-level enabled is typically always, madvise, or never (per-size dirs under hugepages-<size>kB/ can inherit). defrag chooses how aggressively the allocator runs reclaim/compaction on fault (always, defer, defer+madvise, madvise, never). Boot parameters transparent_hugepage= and thp_anon= set defaults. Process-wide disable uses prctl(PR_SET_THP_DISABLE, …).

Latency trap: With enabled=always and aggressive defrag, a sparse touch can allocate a full 2 MB page and stall in compaction — classic “THP latency spikes” in Redis, MongoDB, and latency-sensitive services. Prefer madvise policy plus MADV_HUGEPAGE on dense heaps, or lower max_ptes_none so khugepaged is less eager to collapse sparse regions. Watch /proc/vmstat counters like thp_fault_alloc, thp_fault_fallback, and compact_stall.

madvise and alignment

madvise(2) MADV_HUGEPAGE marks a range as a THP candidate; MADV_NOHUGEPAGE opts out. MADV_COLLAPSE (Linux 6.1+) best-effort synchronously collapses the current mapping to PMD-sized THPs and can ignore some global “never” settings (though VM_NOHUGEPAGE still wins). For fault-time THP, hugepage-natural alignment (e.g. posix_memalign) matters.

When THP helps

  • Dense, long-lived heaps (DB buffers, JVM heaps)
  • Guest RAM under KVM with nested walks
  • Sequential scans over large anon/tmpfs regions
  • Enough free contiguous memory / light fragmentation

When THP hurts

  • Sparse touch patterns (1 byte → 2 MB waste)
  • Latency SLOs vs compaction stalls
  • NUMA: remote huge pages amplify cross-node cost
  • Heavy split churn under reclaim / partial munmap

Real-World Use Cases

Databases & caches
PostgreSQL shared buffers, Redis, or RocksDB working sets benefit from TLB reach; many operators set madvise-mode THP and hint only buffer arenas.
Virtual machines
Host THP backing guest RAM reduces nested page-walk cost; combine with guest hugepages for the full nested benefit described in the admin guide.
Language runtimes
JVM/Go heaps that are dense and aligned; some runtimes expose flags to request or disable THP for the managed heap.
HPC / analytics
Large scientific arrays and in-memory analytics pipelines cut TLB misses when data is contiguous and long-lived.

On NUMA systems, a 2 MB remote page is an expensive mistake: preference for local allocation still applies, and collapsing across nodes (or migrating later) interacts poorly with latency-sensitive workloads. Pair THP policy with explicit memory policy where locality matters.
