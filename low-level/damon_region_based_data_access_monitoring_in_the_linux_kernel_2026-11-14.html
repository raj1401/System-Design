DAMON: Region-Based Data Access Monitoring in the Linux Kernel

How the kernel learns which memory is hot or cold for a fixed overhead budget, then acts on it automatically.

November 14, 2026 · 5 min read

Summary

Memory management choices like what to reclaim, what to back with huge pages, and what to move to a slower tier all depend on one question: which memory is actually being used? Answering it precisely is costly. Tracking every page means overhead that grows with memory size. DAMON (Data Access MONitor) is a Linux subsystem, merged in v5.15, that answers it approximately with an overhead ceiling you choose, whatever the size of the workload. It groups pages into regions, checks one sampled page per region, and keeps splitting and merging regions so the samples stay meaningful. A companion engine, DAMOS, lets you write rules like “page out anything idle for two minutes” that the kernel then applies on its own [1].

Why not just use the LRU? The kernel’s LRU lists (and MGLRU) mostly update when memory is under pressure, and they order pages instead of measuring how often each is used. DAMON runs continuously and reports frequency and age per address range. That lets the system act early, before direct reclaim stalls a latency-sensitive thread.

Deep Dive

Three layers

DAMON has three layers [1]. The operations set layer knows how to find and check the target address space: vaddr (a process’s virtual address space), fvaddr (fixed virtual ranges) and paddr (physical memory). The core layer runs the sampling, region adjustment and DAMOS logic. Modules on top expose interfaces: the general sysfs interface under /sys/kernel/mm/damon/admin [2], plus single-purpose modules such as DAMON_RECLAIM and DAMON_LRU_SORT. Each monitoring context runs in its own kernel thread, kdamond.

The access check: PTE Accessed bits

The basic primitive is the hardware Accessed bit in the page table entry. DAMON clears the bit for a sampled address, waits one sampling interval, then checks whether the MMU set it again. vaddr walks the target task’s page table. paddr uses reverse mapping to walk every page table that maps the physical page. To avoid fooling reclaim, which also reads Accessed bits, DAMON borrows the PG_idle/PG_young page flags from idle page tracking [1].

Region-based sampling

Checking every page every interval would cost O(memory). Instead, DAMON assumes neighbouring pages in a region are accessed at similar rates. Each sampling interval it picks one random page per region. If that page was accessed, the region’s nr_accesses counter goes up by one. After each aggregation interval the counters are reported and reset. The cost now depends on the number of regions, which you cap with min_nr_regions/max_nr_regions, rather than on the number of bytes. LWN’s 2026 update gives defaults of roughly 5 ms sampling and 100 ms aggregation, with typical overhead under 0.1% [3].

Region-based sampling: one probe per region per sampling interval

Adaptive regions adjustment

Sampling only works if pages within a region really behave alike. Access patterns shift, so DAMON keeps reshaping regions [1]:

  • Merge: each aggregation interval, it merges adjacent regions whose nr_accesses are close, as long as the merged size stays under total size / min_nr_regions. If there are still more than max_nr_regions, it raises the similarity threshold and merges again.
  • Split: after reporting, it splits each region into two or three at random points, provided the total stays within max_nr_regions. If the pieces turn out to differ, they stay separate in the next round. If not, they merge back.
  • Age: each region tracks how many aggregation intervals its size and frequency have stayed roughly the same. Frequency plus age gives you both “how hot” and “for how long”.

For vaddr, the starting regions come from the VMAs. DAMON leaves out the two largest unmapped gaps, usually heap-to-mmap and mmap-to-stack, which is why min_nr_regions must be at least 3. This mechanism is the core idea of the Middleware’19 paper by Park, Lee and Yeom [4].

Adaptive split / merge across aggregation intervals

Picking intervals, or letting DAMON pick

If sampling is too coarse, every region looks equally hot or equally cold. If it is too fine, overhead goes up. Newer kernels can tune this automatically: you set a target ratio of observed to maximum-possible access events (access_bp, in basis points), and DAMON scales the sampling and aggregation intervals together until it hits that target. The docs suggest about 4%, applying the 80/20 rule twice: 20% of 20% of samples to capture 80% of 80% of real accesses [1].

DAMOS: from monitoring to action

Exporting results to user space and sending madvise() hints back costs extra work and adds latency. DAMOS (DAMON-based Operation Schemes) runs the policy in the kernel instead. A scheme is made of [1]:

  • Target access pattern: min/max ranges for region size, nr_accesses and age.
  • Action: pageout, cold, willneed, hugepage/nohugepage/collapse, lru_prio/lru_deprio, migrate_hot/migrate_cold, or stat. Which actions are available depends on the operations set.
  • Quotas: a cap on time or bytes per interval. When the cap applies, regions are ranked by priority (coldest first for pageout), with user-set weights for size, frequency and age.
  • Quota auto-tuning goals: feedback loops toward a metric, e.g. some_mem_psi_us (memory PSI), per-node free memory, or per-cgroup usage.
  • Watermarks: turn the scheme on only while a metric such as free memory is between the low and high watermarks.
  • Filters: include or exclude memory by type, e.g. anonymous vs. file-backed or a specific memcg.

DAMOS control loop inside kdamond

Page-granular tracking (idle page tracking, full scans)

  • Exact per-page answers
  • Cost grows linearly with memory size
  • Usually run as periodic snapshots driven from user space
  • Good for one-off working-set measurement

DAMON regions

  • Approximate, “DRAM-level” accuracy rather than cache-level
  • Upper bound on cost set by max_nr_regions
  • Continuous, online, in-kernel
  • Can feed DAMOS directly to act on the results

Real-World Use Cases

Proactive reclaim
DAMON_RECLAIM pages out regions that have been idle for a set time, under a speed limit, so overcommitted VM guests can return memory to the host before direct reclaim kicks in [5].
LRU sorting
DAMON_LRU_SORT uses lru_prio/lru_deprio to prioritize hot pages and deprioritize cold pages on their LRU lists, under a CPU quota and watermarks, so the kernel’s own reclaim picks better victims [6].
Memory tiering / CXL
migrate_hot and migrate_cold promote and demote between fast DRAM and slower NUMA nodes such as CXL memory. Tiering was a headline topic of the 2026 DAMON update [3].
Profiling & THP tuning
The user-space damo tool records heatmaps and working-set sizes. hugepage/collapse actions apply THP only to hot regions [7].
Tradeoffs to remember. DAMON’s output is statistical. A region that mixes hot and cold pages reads as warm until a split happens to separate them. Clearing Accessed bits can also interfere with idle page tracking, and the docs leave handling that to the sysadmin [1]. Bound actions with quotas and watermarks rather than trusting one snapshot.
