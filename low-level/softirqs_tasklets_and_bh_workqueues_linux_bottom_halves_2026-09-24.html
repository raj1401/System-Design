Softirqs, Tasklets, and BH Workqueues: Linux Bottom-Half Deferred Work

Hard IRQ vs softirq, why tasklets are deprecated, and how WQ_BH takes their place

September 24, 2026 · 5 min read

Summary

Hardware interrupt handlers (hard IRQs) must stay short: acknowledge the device, stash state, and get out so other interrupts can fire. The remaining work — packet processing, block completion, RCU callbacks — runs later as a bottom half: historically a softirq, then often a tasklet, and on modern kernels increasingly a BH workqueue item. Softirqs are statically numbered vectors raised with raise_softirq(); they run when hard IRQ exit (or ksoftirqd) drains pending work. Tasklets layered a dynamically registered, self-serialized callback on top of TASKLET_SOFTIRQ / HI_SOFTIRQ, but they are marked deprecated. BH workqueues (WQ_BH, plus the shared system_bh_wq / system_bh_highpri_wq) reuse the workqueue API while still executing in softirq context — with proper flush, cancel, and disable semantics that tasklets lacked.

Deeper Dive

Hard IRQ vs softirq

On interrupt entry, irq_enter_rcu() marks hard-IRQ context; the registered handler runs with local IRQs typically disabled. On exit, irq_exit_rcu() drops hard-IRQ accounting and then invokes softirq processing so bottom halves run in BH context, not with HARDIRQ_OFFSET still set — as documented in the kernel’s entry/exit guide. Softirqs (and anything built on them) cannot sleep: no mutexes that block, no pageable GFP allocations that wait, no schedule(). If deferred work must block, it belongs on a normal (threaded) workqueue, not in BH context.

Classic softirq vectors include HI_SOFTIRQ, TIMER_SOFTIRQ, NET_TX_SOFTIRQ, NET_RX_SOFTIRQ, BLOCK_SOFTIRQ, IRQ_POLL_SOFTIRQ, TASKLET_SOFTIRQ, SCHED_SOFTIRQ, HRTIMER_SOFTIRQ, and RCU_SOFTIRQ — the set Jonathan Corbet walked through in “Per-vector software-interrupt masking”. The same softirq can run concurrently on different CPUs, so handlers must be carefully synchronized; that concurrency is why drivers preferred tasklets for years.

Tasklets: serialized, now deprecated

A tasklet is a dynamically allocated softirq callback that guarantees a given instance never runs on two CPUs at once (different tasklets may still parallelize). Scheduling raises TASKLET_SOFTIRQ (or HI_SOFTIRQ for high-priority). The kernel hacking guide still describes them as the common softirq-facing API for drivers, but Tejun Heo’s BH-workqueue series states the case against them plainly: the only generic BH async interface was tasklets; they are deprecated, the execution path can touch the tasklet after completion (subtle UAF risk), and flush/cancel support is thin compared to workqueues.

Hard IRQ → softirq → BH work item

Why BH workqueues replace tasklets

workqueue: Implement BH workqueue and convert several tasklet users (merged for the 6.9 era) adds WQ_BH: a convenience interface to softirq. BH workqueues are always per-CPU; items run on the queueing CPU’s softirq context in queue order. Constraints from the Workqueue docs: max_active must be 0, the only allowed extra flag is WQ_HIGHPRI, and BH work items cannot sleep. Delayed queueing, flushing, and canceling work — the gaps that made tasklets painful.

Most conversions do not allocate a private queue. They use the system defaults: system_bh_wq for normal priority and system_bh_highpri_wq for the old tasklet_hi_schedule() path. The API map used across driver conversions is roughly:

tasklet_setup → INIT_WORK; tasklet_schedule → queue_work(system_bh_wq, …); tasklet_hi_schedule → queue_work(system_bh_highpri_wq, …); tasklet_kill → cancel_work_sync; disable/enable pair → disable_work[_sync] / enable_work. Early BH pools still piggybacked on tasklets to avoid priority inversion with tasklet_hi; once conversions finish, tasklet softirqs can go away entirely.

Cannot-sleep rule: Softirq, tasklet, and WQ_BH callbacks all run in BH context. Calling a sleeping lock, waiting for I/O, or allocating with GFP_KERNEL from them is a bug — use a normal workqueue (or irq_work / threaded IRQ) when the deferred path must block. local_bh_disable() / local_bh_enable() keep process-context code from racing softirqs on the same CPU.

Tasklets

  • Deprecated generic BH async API
  • Self-serialized; HI vs normal softirq
  • Thin flush/cancel; post-run UAF risk
  • Still present until conversions finish

WQ_BH / system_bh_wq

  • Workqueue API in softirq context
  • Per-CPU, ordered, max_active 0
  • Flush, cancel, disable supported
  • Cannot sleep; WQ_HIGHPRI for hi path

Real-World Use Cases

Networking
NET_RX_SOFTIRQ / NET_TX_SOFTIRQ drive NAPI and transmit cleanup; TCP small-queue (TSQ) and many ethernet drivers converted tasklets to BH workqueues.
Block & irq_poll
BLOCK_SOFTIRQ and IRQ_POLL_SOFTIRQ complete I/O and poll busy devices without staying in hard IRQ for long.
dm-crypt / dm-verity
Early BH-wq conversions moved crypto/verity deferred paths off tasklets onto system_bh_wq, keeping BH latency with better lifecycle control.
USB, Hyper-V, media
Subsystem-wide conversion series (USB HCD, Hyper-V, DMA, IB, MMC, and more) map tasklet schedule/kill to queue/cancel on BH workqueues.
Watch softirq load: Persistent softirq storms show up as elevated softirq time and busy ksoftirqd threads. Prefer keeping BH callbacks tiny; push heavier or sleepable work to process-context queues so networking and timers keep draining on time.
