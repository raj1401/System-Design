CFS to EEVDF: Fair Scheduling with Virtual Runtime

How Linux models an ideal multitasking CPU with vruntime, red-black trees, and — since 6.6 — earliest eligible virtual deadlines.

September 12, 2026 · 5 min read

The Concept

Every time a Linux process wakes, yields, or survives a timer tick, the kernel must answer one question: who runs next? For ordinary tasks — SCHED_NORMAL / SCHED_BATCH — that answer has lived in the fair scheduling class for nearly two decades. Ingo Molnar's Completely Fair Scheduler (CFS), merged in Linux 2.6.23, replaced jiffy-based timeslices and interactivity heuristics with a single idea: pretend every runnable task shares one ideal CPU equally, then approximate that fiction on real silicon by tracking virtual runtime.

Since Linux 6.6 the same fair class implements EEVDF (Earliest Eligible Virtual Deadline First) — still built on virtual time, but picking the eligible task with the earliest virtual deadline instead of always running the leftmost (lowest-vruntime) node. The data structures and accounting look familiar; the selection rule and latency story do not.

Why this matters: Fair scheduling is the invisible tax every userspace thread pays. Understanding vruntime, lag, and virtual deadlines explains why nice levels work, why short-slice interactive work feels snappy under EEVDF, and why cgroup cpu.shares can carve the same CPU among groups without inventing a second scheduler.

Underlying Mechanism

The ideal multitasking CPU

Kernel documentation summarizes CFS in one sentence: it models an ideal, precise multi-tasking CPU — hardware that could run every runnable task in parallel at 1/nr_running of full speed. On a dual-task system each would get 50% continuously. Real cores run one task at a time, so CFS invents virtual runtime (p->se.vruntime, nanosecond units): the amount of CPU a task has consumed, weighted so lighter (nicer) tasks advance faster through virtual time and therefore yield sooner.

Classic CFS pick logic follows directly: always try to run the task with the smallest vruntime — the one that has received the least fair service so far. After a tick or voluntary schedule, the time just spent is added to vruntime; when another task becomes sufficiently “leftmost,” the current one is preempted. A small granularity gap avoids thrashing the cache by over-scheduling.

The red-black timeline

Instead of the old O(1) scheduler's active/expired arrays, CFS keeps a per-CPU time-ordered red-black tree of runnable sched_entity nodes keyed by vruntime. Enqueue and dequeue are O(log n); picking the next task under classic CFS was effectively O(1) because the leftmost node was cached. Newly woken tasks are placed near the left of the tree (anchored historically by min_vruntime, now by EEVDF's zero-lag reference) so they cannot starve forever, yet do not instantly leapfrog everyone else.

Nice weights and accounting

Nice levels map to weights: a nice-0 task has weight 1024; nicer tasks get smaller weights, so each real nanosecond of CPU advances their vruntime by a larger amount. That is how CFS isolates interactive and batch work without a separate heuristic engine. Policies under the fair class are SCHED_NORMAL, SCHED_BATCH (less aggressive preemption, better for cache-friendly batch jobs), and SCHED_IDLE (weaker than nice 19, carefully designed to avoid priority-inversion deadlocks). Real-time SCHED_FIFO/SCHED_RR live in a different scheduling class entirely.

From leftmost to EEVDF

Classic CFS had one parameter per entity: weight (nice). Latency-sensitive work had to fight through heuristics — including “latency nice” experiments — because the picker only cared about who was owed the most virtual time. Peter Zijlstra's EEVDF, committed for Linux 6.6, adds a second parameter: request size (slice). Virtual deadline is:

vd_i = vruntime_i + slice_i / weight_i

Selection becomes: among eligible entities (lag ≥ 0 — owed service relative to the weighted average virtual time), pick the one with the earliest virtual deadline. Short-slice tasks therefore get preferential latency without stealing long-term fairness. The runqueue tree is augmented so eligibility pruning and deadline heaps stay O(log n).

Classic CFS (≤ 6.5)

  • One parameter: weight / nice
  • Pick leftmost (min vruntime)
  • Anchored by min_vruntime
  • Latency tuned via heuristics and granularity knobs

EEVDF (6.6+ fair class)

  • Weight plus request/slice length
  • Pick eligible entity with earliest virtual deadline
  • Zero-lag reference via avg_vruntime / zero_vruntime
  • Natural latency control; custom slices via sched_setattr()

Scheduling classes and group fairness

The modular scheduler core dispatches through sched_class hooks — enqueue_task, dequeue_task, pick_next_task, task_tick, and friends — so fair, RT, and deadline policies coexist without the core encoding policy details. With CONFIG_FAIR_GROUP_SCHED, the same machinery applies recursively to task groups: cgroup cpu.shares weights entire groups the way nice weights individual tasks, which is how containers and multi-user systems divide a core fairly at the group layer before dividing within a group.

Lag and sleep: Positive lag means “owed CPU”; negative lag means “ran ahead.” EEVDF must not let tasks game the system by briefly sleeping to erase negative lag, nor punish a task forever after a long sleep. Current designs decay lag over virtual time (including deferred dequeue while sleeping) so fairness and exploit-resistance stay aligned.

Real-World Use Cases

Desktop interactivity
Short-slice UI and audio threads become eligible with earlier virtual deadlines under EEVDF, improving responsiveness without a separate interactive heuristic.
Container CPU shares
Fair group scheduling turns cgroup cpu.shares into hierarchical weights on the same virtual-time machinery used for nice levels.
Batch vs latency workloads
SCHED_BATCH and longer base slices favor cache locality; latency-sensitive apps can request tailored slices through sched_setattr().
Kernel / systems tuning
Debugfs knobs such as base_slice_ns (formerly granularity/min_granularity naming) slide the fair class between desktop and server batching behavior.

Trade-offs at a Glance

Strengths

  • Nanosecond accounting independent of HZ
  • Deterministic progress: every runnable entity eventually becomes eligible
  • Extensible scheduling classes and cgroup hierarchy
  • EEVDF encodes latency in the deadline rather than brittle heuristics

Costs & caveats

  • RB-tree updates on every enqueue/dequeue (O(log n))
  • Lag placement and sleep decay are subtle and still evolving
  • Cross-CPU load balancing remains a separate, hard problem
  • Docs historically lag code — always check kernel/sched/fair.c
