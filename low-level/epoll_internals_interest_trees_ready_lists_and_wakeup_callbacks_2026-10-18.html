epoll Internals: Interest Trees, Ready Lists and Wakeup Callbacks

A red-black tree of interests, a list of the ready, and a callback hooked into every socket's wait queue: the machinery behind Linux's event loop.

October 18, 2026 · 5 min read

Summary

epoll is how Linux event loops watch thousands of descriptors without rescanning them on every call. The epoll(7) man page describes an epoll instance as two lists: an interest list of registered descriptors and a ready list of the ones with pending I/O. Inside the kernel, the interest list is a red-black tree of struct epitem, and the ready list is a linked list that a wakeup callback, ep_poll_callback(), appends to whenever a watched file signals readiness (fs/eventpoll.c). epoll_wait() doesn't poll every file. It drains the ready list, so the cost tracks how many descriptors are ready, not how many are registered.

That design is fast, but the details leak into userspace. Level- and edge-triggered modes differ in one line of the delivery code. EPOLLONESHOT and EPOLLEXCLUSIVE exist to tame multi-threaded wakeups. Registrations follow the open file description, not the descriptor number. And the lock protecting the ready list went from a spinlock to an rwlock in 5.1, then back to a spinlock in 2025.

The objects: eventpoll, epitem, eppoll_entry

Each epoll_create1() returns an anonymous [eventpoll] file whose private_data is a struct eventpoll. It holds a sleepable mutex mtx, an IRQ-safe spinlock lock, a wait queue wq for threads in epoll_wait(), a second queue poll_wait for when the epoll fd itself is polled, the ready list rdllist, the overflow list ovflist, and the tree root rbr (an rb_root_cached) (eventpoll.c).

Each EPOLL_CTL_ADD allocates a struct epitem from a dedicated slab cache. Its tree key is the pair (struct file *, fd number): ep_cmp_ffd() compares the file pointer first and the fd number second, so ep_find() is an O(log n) tree walk. epoll(7) documents the same thing from the user side: the key is "the combination of the file descriptor number and the open file description" (epoll(7)). That's why a dup()ed descriptor can be added to the same instance with a different event mask.

The link to the watched file is the interesting part. ep_insert() calls the file's f_op->poll() with a custom poll_table whose queue function, ep_ptable_queue_proc(), allocates a struct eppoll_entry, sets its wait function to ep_poll_callback, and adds it to the file's wait queue head. A socket, pipe or eventfd therefore has no idea epoll exists. It runs its normal wake_up(), and one of the entries on its queue happens to be epoll's callback. A file can expose more than one wait queue, so an epitem keeps a pwqlist of these hooks (eventpoll.c).

The wakeup path: ep_poll_callback()

When data arrives on a socket, the network stack wakes the socket's wait queue, which may happen in softirq or even hard-IRQ context. That's why ep->lock is a spinlock taken with spin_lock_irqsave() and why the sleepable ep->mtx is never taken here (eventpoll.c locking notes). Under the lock, ep_poll_callback():

  1. Returns early if the item's mask has no poll events left. That's how a fired EPOLLONESHOT item stays disabled.
  2. Returns early if the wakeup key carries event bits that the item doesn't want.
  3. If a harvest is in progress, pushes the item onto ovflist. Otherwise, if the item isn't already linked, appends it to the tail of rdllist. An item is never queued twice: a burst of packets is one entry, and epoll(7) confirms that events between calls "will be combined".
  4. Wakes ep->wq if threads are sleeping in epoll_wait(), and schedules a nested wakeup if someone is polling the epoll fd itself.

The callback does no I/O and computes no final event mask. It only records that an item is worth checking.

Harvesting: rdllist, ovflist and the re-poll

epoll_wait() lands in ep_poll(). If nothing is ready, the thread adds itself to ep->wq with __add_wait_queue_exclusive() and sleeps until the timeout (milliseconds for epoll_wait, a timespec with nanosecond resolution for epoll_pwait2(2), added in Linux 5.11). When events are available, ep_send_events() takes ep->mtx and runs the scan.

Copying events to userspace can fault and sleep, so it can't happen under a spinlock. ep_start_scan() solves this by briefly taking ep->lock, splicing the whole rdllist into a private scan_batch, and setting ovflist from the sentinel EP_UNACTIVE_PTR to NULL, which means a scan is active. While the scan runs without the spinlock, callbacks that fire are diverted onto ovflist, a singly linked LIFO. For each batched item, ep_deliver_event() calls the file's poll() again to get the current mask. Items that are no longer ready are dropped silently. The rest are copied out with epoll_put_uevent(). Afterwards, ep_done_scan() moves the ovflist items back onto rdllist (head insertion turns LIFO back into FIFO), resets the sentinel, splices back anything the caller left in the batch, and wakes another waiter if rdllist isn't empty (eventpoll.c).

LT, ET and EPOLLONESHOT are one branch apart

The three modes come down to a few lines at the end of ep_deliver_event(). With EPOLLONESHOT, the item's mask is cut down to its private bits, so later callbacks see "no poll events" and ignore it until EPOLL_CTL_MOD rearms it. Without EPOLLET (level-triggered, the default), the item goes back on the tail of rdllist, so the next epoll_wait() polls it again and reports it again while data remains. With EPOLLET, the item is just dropped and comes back only when the file's next wake_up() runs the callback again (eventpoll.c).

The rules in epoll(7) follow from this. Its pipe example shows ET epoll_wait() hanging after a reader consumed only 1 kB of a 2 kB write. The fix is nonblocking descriptors and waiting only after read/write returns EAGAIN. LT, by contrast, is "simply a faster poll(2)." epoll_ctl(2) lists EPOLLONESHOT since 2.6.2 and EPOLLWAKEUP since 3.5.

Why the re-poll matters: because harvest calls poll() again instead of trusting the callback's key, a stale wakeup costs one wasted poll and never produces a false event. It also explains the epoll(7) note that EPOLL_CTL_MOD on an item with collected but unreported events "will reread available I/O."

Thundering herds and EPOLLEXCLUSIVE

There are two kinds of sharing. First, many threads block on one epoll fd. Waiters join ep->wq exclusively, so a single wake_up() releases one thread, and epoll(7) promises that for an ET descriptor "just one of the threads" wakes. A level-triggered item, however, goes back onto rdllist, and ep_done_scan() wakes another waiter if the list is non-empty. That re-queue is one way the LT herd Marek Majkowski describes shows up, where two threads wake for one new connection and the loser's accept() returns EAGAIN (Majkowski, part 1).

Second, many epoll fds watch one file, such as one per worker on a shared listening socket. Each registration hangs its own eppoll_entry on the socket's wait queue, so every instance gets woken. Jason Baron's EPOLLEXCLUSIVE patch (merged for Linux 4.5 as df0108c) adds the entry with add_wait_queue_exclusive() instead. ep_poll_callback() then returns nonzero only if that instance has a thread blocked in epoll_wait() and the event matches its mask. The wakeup walk queues the event to each exclusive instance until one of them has an idle thread, so "one or more" instances receive it (epoll_ctl(2)). The flag is allowed only on EPOLL_CTL_ADD, only with EPOLLIN, EPOLLOUT, EPOLLWAKEUP, EPOLLET (plus EPOLLERR/EPOLLHUP), and never on a nested epoll target. Baron's test workload dropped from 860 s to 24 s.

Majkowski's conclusion: use LT plus EPOLLEXCLUSIVE to spread accept() across workers, and use EPOLLONESHOT with a manual rearm when many threads read() from a shared set, because otherwise two threads can each read part of one socket's byte stream and reorder it.

The fork and dup pitfall: descriptions, not descriptors

Since the tree key holds a struct file *, a registration lives as long as the open file description does. Removal on close happens in eventpoll_release_file(), which __fput() calls only when the last reference goes away (eventpoll.c removal paths). epoll(7) spells out the result: if dup(), dup2(), fcntl(F_DUPFD) or fork() created another descriptor for the same description, closing the registered fd doesn't remove it, and "events may be reported for that file descriptor" afterwards. Majkowski's part 2 walks through the worst case: after rfd2 = dup(rfd); close(rfd), epoll_wait() still reports rfd, and neither EPOLL_CTL_DEL on rfd (now closed) nor on rfd2 (a different key) can remove it. His rule is to always call EPOLL_CTL_DEL before close().

Locking history: spinlock, rwlock, spinlock

The current lock order is epnested_mutex (global, only for nested-epoll loop checks), then ep->mtx, then ep->lock. Nesting is capped at EP_MAX_NESTS = 4, and reverse_path_check() limits how many wakeup paths of each length can lead to a single file (1000, 500, 100, 50, 10) (eventpoll.c). The ready-list lock in the middle has changed twice.

Linux 5.1: rwlock + xchg

  • Roman Penyaev's a218cc4 replaced the spinlock with an rwlock
  • Callbacks took it for read and appended with an atomic xchg
  • The consumer took it for write to freeze the lists
  • stress-epoll, 8 producer threads: 6402 → 10038 events/ms (LKML v2)

2025: back to a spinlock

  • Nam Cao's 0c43094: "Replace rwlock with spinlock"
  • Readers can't be priority-boosted, even on PREEMPT_RT, so a low-priority producer could block a high-priority consumer
  • stress-epoll on 12 x86 CPUs drops 31 to 47%; perf bench epoll wait improves slightly
  • In v6.18, with stable backports to 6.17 and 6.6 (stable review)

Cao's commit message is blunt: "spinlock was used originally for years, and the commit which converted to rwlock didn't mention a real workload, just that the benchmark numbers are nice" (v4 patch). Current mainline also wraps the rdllist/ovflist switch in a seqcount_spinlock_t, so the lockless ep_events_available() check can't miss a scan in progress.

Busy polling from epoll_wait()

With CONFIG_NET_RX_BUSY_POLL, each callback on a socket records the socket's sk_napi_id in ep->napi_id. Before sleeping, ep_poll() calls ep_busy_loop(), which runs napi_busy_loop() on that NIC queue and pulls packets in the waiting thread's context instead of waiting for an interrupt (eventpoll.c). The NAPI docs say this works only if every fd in the epoll context has the same NAPI ID. Applications arrange that with SO_INCOMING_NAPI_ID plus an acceptor thread, or with a SO_REUSEPORT BPF program. It can be turned on system-wide with net.core.busy_poll. Since Linux 6.9 and glibc 2.40, it can also be set per instance: ioctl(epfd, EPIOCSPARAMS, &params) sets busy_poll_usecs, busy_poll_budget (capped at NAPI_POLL_WEIGHT without CAP_NET_ADMIN) and prefer_busy_poll (ioctl_eventpoll(2), Joe Damato's series). prefer_busy_poll keeps device IRQs masked while the app keeps polling, and the newer per-NAPI irq-suspend-timeout extends that into IRQ suspension, where interrupts stay off as long as epoll_wait() keeps finding events.

Real-world use cases

Event-loop servers
The epoll(7) example pattern: a level-triggered listener, accepted sockets added with EPOLLIN | EPOLLET, and each one drained until EAGAIN.
Scaling accept()
One epoll per worker on a shared listening socket with EPOLLEXCLUSIVE, so only a worker with an idle thread is woken.
Thread-pool readers
A shared epoll set with EPOLLONESHOT, rearmed with EPOLL_CTL_MOD after each request, so only one thread owns a socket at a time.
Low-latency networking
Per-epoll busy poll with EPIOCSPARAMS and NAPI-ID-aligned workers trades CPU for lower receive latency without a global sysctl.
Mobile wakeups
EPOLLWAKEUP holds a wakeup source from the moment an event is queued until the next epoll_wait(), so autosleep can't suspend before it's handled.
Nested loops
An epoll fd is itself pollable, so a library can expose one fd that an outer loop watches, up to the nesting and path limits.
Design lesson: epoll's speed comes from separating registration (an O(log n) tree touched only by epoll_ctl) from notification (an O(1) list append in the wakeup path). Its sharp edges come from the same place: the callback lives on the open file description, waits are shared, and the ready list behaves differently per mode. That's why you have to deregister before close(), pick LT, ET or ONESHOT on purpose, and know which lock your wakeups contend on.
