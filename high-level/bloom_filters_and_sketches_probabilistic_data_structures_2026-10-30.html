Bloom Filters and Sketches: Probabilistic Data Structures at Scale

Trading a little certainty for a lot of memory: membership, cardinality, and frequency in kilobytes.

October 30, 2026 · 5 min read

Summary

Some questions get very expensive to answer exactly once the data is huge. Is this key in this file? How many unique users visited today? Which URLs are hot right now? An exact answer needs memory that grows with the data. Probabilistic data structures answer the same questions in fixed or tiny space, and accept a small, mathematically bounded error in exchange.

Three of them show up all over production systems. A Bloom filter answers set membership with no false negatives and a tunable false-positive rate (Bloom, 1970). HyperLogLog estimates the number of distinct elements using a few kilobytes (Flajolet et al., 2007). The Count-Min sketch estimates how often each item appears in a stream (Cormode & Muthukrishnan, 2005).

The design rule: use a sketch as a cheap first check in front of an expensive exact one, or wherever an answer that is off by about 1% is just as useful as a perfect one. Bloom's original paper framed it exactly this way: a small in-memory hash area plus a slower secondary test to catch the rare errors (Bloom, 1970).

Bloom filters: definitely not, or probably yes

A Bloom filter is a bit array of m bits and k hash functions. To insert a key, hash it k times and set those bits to 1. To look it up, check the same k bits. If any bit is 0, the key was definitely never inserted. If all of them are 1, it probably was, because other keys may have set those bits. Cassandra's docs describe the two outcomes the same way: the data definitely does not exist in the file, or it probably does (Apache Cassandra docs).

Sizing the filter

With n keys, the false-positive rate is roughly (1 - e^(-kn/m))^k. It is lowest when k = (m/n) · ln 2, which gives m/n = -ln(p) / (ln 2)^2 bits per key for a target rate p. That works out to about 9.6 bits and 7 hashes per key for 1%, and about 14.4 bits for 0.1% (CQLite SSTable notes). The striking part is that the size depends only on p and n, not on how big the keys are: a 200-byte URL costs the same 10 bits as an 8-byte integer.

The returns diminish fast. RocksDB's wiki points out that 4.9 bits per key (10% false positives) already gets 90% of the benefit of 100 bits per key, and 9.9 bits (1%) gets 99% (RocksDB wiki). Cassandra notes that a 1% filter takes about three times the memory of a 10% one (Cassandra docs).

Limits and variants

You can't delete from a standard Bloom filter, because clearing a bit might erase other keys. Counting Bloom filters fix that with small counters, but typically use 3 to 4 times the space. A filter also degrades once you insert more than the n it was sized for, so rebuild it rather than letting it saturate. Cuckoo filters store short fingerprints in a cuckoo hash table, support deletes, and use less space than Bloom filters when the target false-positive rate is under about 3% (Fan et al., CoNEXT 2014). RocksDB also keeps all of a key's probes inside one CPU cache line, so each lookup costs at most one cache miss per filter (RocksDB wiki).

HyperLogLog: counting distinct things in 12 KB

Counting unique items exactly means remembering every item you've seen. HyperLogLog avoids that with a neat observation about hashing. If you hash items uniformly, a hash that starts with many leading zeros is rare: a run of r zeros shows up about once every 2^r distinct values. So the longest run you've seen hints at how many distinct values went by.

One observation like that is noisy. HLL splits the hash: the first bits pick one of m registers, and each register keeps the largest leading-zero position it has seen. The estimate combines the registers with a harmonic mean, which tames outliers, and the relative standard error comes out to about 1.04 / √m (Flajolet et al., 2007). Redis uses 16,384 registers, which gives 1.04 / 128, or a 0.81% standard error, in at most 12 KB per key (Redis HyperLogLog docs).

HyperLogLog: bucket by prefix, keep max leading zeros

HLL sketches have one more property that matters in distributed systems: they merge. Take the element-wise max of two sketches and you get the sketch of the union, so every shard or every hour can keep its own sketch and you combine them later. Redis's PFCOUNT does exactly that when you pass it several keys (Redis PFCOUNT). Google's HyperLogLog++ added bias correction and a sparse encoding that improve accuracy and memory for small cardinalities (Heule et al., EDBT 2013).

Count-Min sketch: how often, approximately

A Count-Min sketch is a grid of counters with d rows and w columns, one hash function per row. To count an item, increment one counter in each row. To estimate its count, read those d counters and take the minimum. Collisions only ever add, so the estimate never undercounts. With w = e/ε and d = ln(1/δ), the overcount is at most ε times the total stream size with probability at least 1 - δ, and plain pairwise-independent hashes are enough (Cormode & Muthukrishnan).

Count-Min sketch (d = 3 rows): estimate = min of the row counters

Exact structures

  • Hash set or map, memory grows with every key
  • Zero error, deletes are easy
  • Hard to merge across shards cheaply
  • Right choice when answers feed money or correctness

Probabilistic sketches

  • Fixed or near-fixed memory set by the error target
  • Bounded, one-sided or statistical error
  • HLL and Count-Min merge cell by cell
  • Right choice for filtering, analytics, and monitoring

Real-world use cases

LSM storage engines
RocksDB and Cassandra keep a Bloom filter per SSTable so a point read skips files that cannot hold the key, saving disk I/O (RocksDB, Cassandra).
Tunable per table
Cassandra defaults bloom_filter_fp_chance to 0.01, or 0.1 with leveled compaction, and lets operators trade RAM for I/O per table (DataStax).
Unique visitors and queries
Call PFADD for every search query and PFCOUNT for the day's distinct count, in about 12 KB (Redis).
Database cardinality estimates
Google built HyperLogLog++ for production systems that need fast, mergeable distinct counts (Heule et al.).
Heavy hitters
Count-Min tracks hot keys, top URLs, or abusive IPs in a stream, and supports frequent-item and quantile queries (Cormode & Muthukrishnan).
Sets with deletes
Cuckoo filters suit caches and dedup sets where entries expire, keeping Bloom-like space while allowing removal (Fan et al.).
Pitfalls: size filters for the real final n, since an overfilled Bloom filter quietly drifts above its target rate; never let a "probably yes" skip the exact check when correctness matters; and use well-mixed hashes, because every error bound assumes uniform hashing.
