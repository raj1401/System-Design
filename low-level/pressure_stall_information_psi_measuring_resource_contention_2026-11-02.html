Pressure Stall Information (PSI): Measuring Resource Contention in Linux

How the kernel turns per-CPU task states into some/full stall percentages, and why OOM daemons, Android and container autoscalers poll them.

November 2, 2026 · 5 min read

Summary

Utilization tells you how busy a resource is; it does not tell you whether anyone is suffering. A box at 95% memory usage may be perfectly healthy, while one at 70% may be thrashing on refaults. Pressure Stall Information (PSI), merged in Linux 4.20 and written by Johannes Weiner at Facebook (polling support by Suren Baghdasaryan at Google), measures the thing operators actually care about: the share of wall-clock time in which work could not make progress because tasks were waiting on CPU, memory, or IO (kernel docs, LWN).

The kernel exports it in /proc/pressure/{cpu,memory,io} (plus irq on kernels with IRQ time accounting) and per cgroup v2 as cpu.pressure, memory.pressure, io.pressure and irq.pressure (cgroup v2 docs):

some avg10=1.53 avg60=0.87 avg300=0.22 total=2390457
full avg10=0.41 avg60=0.12 avg300=0.03 total=518304

The averages are percentages over 10 s, 60 s and 300 s windows; total is cumulative stall time in microseconds.

Deeper dive

SOME vs FULL

For each resource the kernel defines two contention states. SOME means at least one task is delayed on the resource while others may still run: the workload is slowed down. FULL means every non-idle task is delayed, so nobody advances and CPU cycles go to waste: the workload is thrashing (kernel/sched/psi.c). In code terms, SOME = nr_delayed != 0 and FULL = nr_delayed != 0 && nr_productive == 0.

"Productive" depends on the resource. For IO it is any running task. For CPU it is the task actually on the CPU. Memory is subtle: a task doing direct reclaim is running but is itself a victim of the shortage, so the kernel tracks it separately as NR_MEMSTALL_RUNNING and does not count it as productive (psi_types.h). System-wide CPU FULL is undefined (some task is always on a busy CPU) and is reported as zero since 5.13 for compatibility; at the cgroup level it is meaningful, showing a group starved by outsiders or throttled by cpu.max.

Task states to stall states on one CPU

Scaling to many CPUs

Naively aggregating task states breaks on big machines. With 257 CPU-bound tasks on 256 CPUs, somebody is always queued, yet only 1/256 of capacity is lost. With 4 tasks on 4 CPUs where one is always waiting on memory, FULL would read 0% even though a quarter of execution potential is gone. PSI therefore measures lost potential against threads = min(nr_nonidle_tasks, nr_cpus), which yields about 0.4% and 25% respectively for those two cases (psi.c header comment).

Freezing the whole system to time that precisely would not scale, so PSI tracks state per runqueue. On every task state change the scheduler calls psi_task_change(), which updates per-CPU counters (NR_IOWAIT, NR_MEMSTALL, NR_RUNNING, NR_MEMSTALL_RUNNING, plus the on-CPU flag) and accumulates how long that CPU spent in SOME, FULL and NONIDLE. Memory stalls are bracketed explicitly with psi_memstall_enter()/psi_memstall_leave() around reclaim, compaction, refaults of recently evicted pages and similar paths. The counters live in each cgroup ancestor too, so one state change updates the whole hierarchy.

From scheduler hooks to userspace

Averages and triggers

A deferrable worker wakes roughly every 2 seconds (PSI_FREQ), folds the per-CPU times into group totals weighted by each CPU's non-idle time, and updates the three running averages with the same fixed-point exponential decay used for load average (EXP_10s, EXP_60s, EXP_300s). When the system is idle the worker stops re-arming itself, so PSI costs nothing on a quiet box.

Averages are too slow for an OOM killer, so PSI also offers triggers. You open a pressure file, write <some|full> <stall us> <window us>, for example some 150000 1000000 (150 ms of stall in any 1 s window), then wait for POLLPRI with poll(), select() or epoll. Windows range from 500 ms to 10 s, and the psimon kernel thread samples 10 times per window only while the group is actually in a stall state. Each trigger needs its own file descriptor, notifications are rate-limited to one per window, and unprivileged users may create triggers only with windows that are multiples of 2 s (kernel docs).

Why not just watch free memory? Free memory and page-cache size say nothing about whether the working set fits. PSI memory pressure rises only when tasks really wait on reclaim or refault evicted pages, which is exactly the signal that latency is about to degrade. Android replaced its older vmpressure signal with PSI monitors in lmkd for this reason (AOSP lmkd).

Utilization metrics

  • How busy a resource is (CPU %, MemFree, disk util)
  • High values can be perfectly healthy
  • Blind to queueing and thrashing
  • Sampled snapshots, easy to miss spikes

Pressure (PSI)

  • How much time work could not progress
  • Directly maps to added latency
  • SOME vs FULL separates slowdown from thrashing
  • Cumulative total plus event-driven triggers

Real-world use cases

systemd-oomd
Kills cgroups whose memory pressure exceeds ManagedOOMMemoryPressure= limits before the kernel OOM killer fires (man page).
Android lmkd
Uses PSI memory monitors to decide when to kill background apps, replacing vmpressure (AOSP).
Meta oomd
The original userspace OOM daemon that acts on cgroup pressure in production fleets (oomd).
Senpai / TMO
Shrinks container memory limits until a small pressure target is hit, offloading cold pages to zswap or SSD (Senpai, Meta TMO).
Load shedding
Services read cpu.pressure or io.pressure to back off, reroute traffic or pause batch jobs (kernel docs).
Capacity planning
Fleet dashboards chart pressure total deltas to size workloads to hardware instead of guessing from utilization.

Design takeaways

PSI is a good example of cheap, precise kernel telemetry: hook the state transitions the scheduler already performs, keep counters per CPU to avoid shared cache lines, aggregate lazily, and push only rare threshold events to userspace. The SOME/FULL split turns a vague "the box is slow" into a measurable question of whether work is merely delayed or completely stalled, and per-cgroup accounting makes that question answerable per container.
