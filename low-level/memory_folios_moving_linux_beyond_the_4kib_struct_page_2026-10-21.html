Memory Folios: Moving Linux Beyond the 4 KiB struct page

How one small type turned the kernel's page-at-a-time memory management into variable-sized, power-of-two chunks.

October 21, 2026 · 5 min read

Summary

For decades, Linux described every physical page frame with a struct page, and most memory-management code assumed one page meant 4 KiB. When the kernel needed bigger, physically contiguous chunks (huge pages, DMA buffers), it glued pages together into compound pages: the first struct page (the head) carries the metadata and every following one (a tail) points back to it. Any function handed a struct page * could not know which kind it got, so it had to call compound_head() defensively, over and over.

A folio, introduced by Matthew Wilcox and merged in Linux 5.16, is a struct page that is guaranteed not to be a tail page. It represents either a single base page or a whole power-of-two compound allocation, so functions that take a folio operate on the entire unit with no ambiguity and no head lookups [1][2]. That type-system cleanup became the foundation for large folios in the page cache, multi-size THP for anonymous memory, and filesystem block sizes larger than the page size.

The one-line definition. In the original “Ottawa interpretation,” a folio is simply a non-tail page. The planned “New York interpretation” makes the folio its own separately allocated structure that refers to one or more pages [5].

Deep dive

The problem with compound pages

The kernel keeps an array of struct page (the memmap), one entry per physical frame. A compound page of order n spans 2^n contiguous frames. Code that wants the reference count, the LRU linkage, the mapping or the index of the whole allocation must read them from the head, and since any page pointer might be a tail, helpers such as PageLocked() or get_page() quietly called compound_head() internally. LWN noted the cost was not just runtime: the inline helper was expanded in many call sites, inflating kernel text [1]. The very first folio series removed about 6 KB of kernel code purely by eliminating tail-to-head conversions [3], and Oracle reports an early, untuned version gave a 7% speedup on kernel builds [4].

The type as a contract

struct folio overlays the head page's fields, so converting is free at runtime: page_folio(page) resolves a possibly-tail page to its folio once, at the API boundary, and everything downstream uses folio functions such as folio_lock(), folio_get(), folio_mark_dirty(), folio_size() and folio_nr_pages(). Because the compiler enforces the type, a function signature now documents whether it works on whole allocations or on individual pages. Wilcox's page-cache conversion shows the pattern: add_to_page_cache_lru() became a thin wrapper over folio_add_to_page_cache(), which stores mapping and index on the folio and inserts it into the file's XArray [6].

Compound page vs folio view of the memmap

Large folios in the page cache

Once the page cache spoke folios (5.17), it could hold large folios of any power-of-two size, not just CPU huge-page sizes. XFS was the first filesystem to use them, initially for read() and mmap() faults in 5.18 [7][8]. A filesystem opts in with mapping_set_large_folios(), after which readahead and the write path allocate folios sized to the I/O, falling back to order-0 under memory pressure [8]. In 6.6, iomap gained large folios on buffered writes plus per-block dirty tracking, so dirtying 4 KiB inside a 2 MiB folio no longer forces the whole folio to be written back [9][10].

The wins compound: fewer XArray entries per file, fewer LRU list operations and lock acquisitions during reclaim, and larger bios sent to the block layer [4].

Anonymous memory: multi-size THP

Classic THP only knew one size, the PMD (2 MiB on x86-64), which is often too big to allocate or to waste. Ryan Roberts' multi-size THP (mTHP), merged in 6.8, lets anonymous faults allocate intermediate-order folios (for example 16 KiB to 1 MiB) that are still mapped by ordinary PTEs [11][12]. Each size is opt-in under /sys/kernel/mm/transparent_hugepage/hugepages-<size>kB/enabled [13]. The kernel saves work through fewer faults and batched PTE and rmap updates. On arm64, the 6.9 contpte work goes further: when 16 aligned PTEs map a physically contiguous 64 KiB folio, the kernel sets the contiguous bit and the TLB can cache the range as a single entry [14][15].

Folio sizes across the stack

Larger-than-page filesystem blocks

Linux historically capped a filesystem's block size at the host page size. The large block size (LBS) work merged for 6.12 lets a filesystem declare a minimum folio order through mapping_set_folio_min_order(), and the page cache promises never to hold a smaller folio for that file, even when a large folio is split under pressure; that relies on 6.8's ability to split a folio into any lower order [8]. XFS was first, and the same plumbing underpins its initial atomic-write support.

Page-centric (before)

  • Any struct page * might be a tail
  • compound_head() hidden in hot helpers
  • Page cache and reclaim work 4 KiB at a time
  • THP is one size: the PMD
  • Block size capped at page size

Folio-centric (after)

  • Type guarantees a whole allocation
  • Head resolved once via page_folio()
  • Variable power-of-two units per I/O
  • mTHP orders between base page and PMD
  • Min folio order enables large blocks

Trade-offs and what comes next

Large folios are not free. Partially used folios can waste memory, reclaim and splitting become more complex, and fragmentation can make high-order allocations fail, which is why every path keeps an order-0 fallback. Accounting is also subtler: per-folio mapcounts and dirty state must stay correct when only some pages are mapped or dirtied.

The longer-term “memdesc” plan finishes the job. Wilcox's January 2025 State of the Page proposes allocating struct folio, slab, page-table and other descriptors separately and shrinking struct page to about 32 bytes, halving memmap overhead, with an eventual 16-byte target [5][16]. LSF/MM/BPF discussion flagged page migration and the long tail of drivers poking at struct page fields as the hardest remaining work [17].

Practical takeaway. If you write kernel code today, take and return struct folio * wherever you handle file or anonymous memory, use folio_size() instead of PAGE_SIZE, and never assume one page equals one cache entry.

Real-world use cases

Streaming file I/O
XFS and other large-folio filesystems issue bigger bios and touch fewer cache entries for sequential reads and buffered writes.
Android and arm64 servers
64 KiB mTHP plus contpte gives near-huge-page TLB reach without 2 MiB fragmentation or fault latency.
16 KiB and larger block devices
LBS lets XFS format with block sizes above 4 KiB to match device sector and atomic-write units.
Reclaim efficiency
Fewer, larger LRU entries reduce list churn and lock traffic when memory pressure forces eviction.
