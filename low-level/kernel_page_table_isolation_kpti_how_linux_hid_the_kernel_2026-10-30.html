Kernel Page-Table Isolation (KPTI): How Linux Hid the Kernel from Meltdown

Two page tables per process, a CR3 switch on every kernel entry, and PCIDs to keep the TLB alive.

October 30, 2026 · 5 min read

Summary

For decades, x86 operating systems mapped the whole kernel into the upper half of every process's address space. User code could not touch those pages, because the page-table entries lacked the user bit, but the translations were present, so a syscall never had to change page tables. In January 2018 Meltdown showed that out-of-order execution on many CPUs would transiently load kernel data before the permission check retired, leaking it through a cache side channel. A permission bit was no longer a wall.

Kernel Page-Table Isolation (KPTI, called pti in the kernel and originally KAISER) answers by removing the translations themselves. Each process gets two top-level page tables: a full one used while running in the kernel, and a stripped one used in user mode that maps only the tiny trampoline needed to enter and leave the kernel. If no translation exists, there is nothing for speculation to load. It was merged in Linux 4.15 and backported to 4.14.11, 4.9.75 and 4.4.110 (overview).

Deeper dive: the mechanism

From KASLR defence to Meltdown fix

KAISER was published by Gruss et al. at Graz in 2017 to stop hardware side channels (page-fault timing, prefetch, TSX) that revealed where the randomized kernel lived; the paper reported a 0.28% overhead on its prototype (Gruss et al.). When Meltdown surfaced, the same authors noted in the Meltdown paper that KAISER inadvertently blocked it too, since neither kernel memory nor the direct physical map is resolvable from user mode. Dave Hansen's port, reworked by Thomas Gleixner, Peter Zijlstra, Andy Lutomirski and Hugh Dickins, went through 163 internal revisions before landing (LWN, Dec 2017).

Two PGDs, one set of user page tables

Per the kernel PTI documentation, each process's PGD becomes an order-1 allocation (two adjacent 4 KiB pages, costing an extra 4 KiB per process). The kernel half maps everything; the user half maps user memory plus only struct cpu_entry_area, a per-CPU fixmap region holding the entry/exit stubs, the IDT, and the TSS. Crucially, only the top level is duplicated: whenever the kernel sets a user PGD entry it mirrors it into the user copy, so both PGDs point at the same lower-level tables. There is one PTE to lock and one set of accessed and dirty bits.

A safety trick: the user portion of the kernel PGD is marked NX at the top level. If an exit path ever forgets to switch back to the user CR3, userspace crashes on its first instruction instead of silently running with the kernel mapped.

One process, two top-level page tables

The CR3 dance on every entry and exit

Because the user PGD lacks most of the kernel, the very first instructions of a syscall, interrupt, exception or NMI must run from the mapped trampoline and switch CR3 to the kernel PGD before touching anything else; the exit path switches back just before sysret/iret. In the entry assembly (arch/x86/entry/calling.h), the SWITCH_TO_KERNEL_CR3 and SWITCH_TO_USER_CR3 macros flip a single page-sized bit in CR3 to move between the two halves of the order-1 PGD, plus a PCID bit described below. The docs put a CR3 write at "on the order of a hundred cycles," paid twice per kernel round trip (PTI docs).

A syscall under KPTI

Why PCID matters so much

On x86 a CR3 write normally flushes all non-global TLB entries. Without help, every syscall would wipe the TLB. Classic kernels avoided this by marking kernel pages global, but under PTI most kernel pages can no longer be global, because a global entry would remain usable after switching to the user tables. Process Context Identifiers (PCIDs) tag TLB entries with a 12-bit ID, so setting the no-flush bit on a CR3 write keeps entries cached. Linux gives each address space a kernel PCID and a paired user PCID, so kernel and user translations coexist in the TLB. The patch posting described PCIDs making syscalls "roughly 2x faster" than without them under KAISER (KAISER v2 on LWN), building on Andy Lutomirski's PCID work merged for 4.14. Remaining wrinkles from the docs: user-PCID flushes are deferred until exit to userspace, and CPUs with PCID but no INVPCID must defer kernel-address flushes to the next use of every PCID.

PTI without PCID

  • Every CR3 write flushes the TLB
  • Each syscall, interrupt or exception starts cold
  • Large working sets pay repeated page walks
  • Worst-case microbenchmarks over 800% slower

PTI with PCID

  • CR3 write with no-flush bit keeps TLB entries
  • Kernel and user PCIDs coexist per address space
  • Cost dominated by CR3 cycles, not misses
  • Netflix-style 50k syscalls/s: about 1.1% overhead
Residual surface. The x86 architecture still forces some kernel state into the user tables (entry text, IDT, TSS). The Meltdown authors warn that while this contains no secrets, leaking even one pointer can defeat KASLR (Lipp et al.). That is why cpu_entry_area is kept as small as possible.

What it costs

Brendan Gregg's analysis found overheads ranging from about 1% to over 800% depending on syscall rate, context switches, page faults, working-set size and cache behaviour; at 50k syscalls per second per CPU, overhead was around 2%, and PCID plus huge pages could reduce it further or even produce a net gain on his benchmark (Gregg, 2018; Gruss et al., ;login: 2018). Memory costs are modest: 4 KiB extra per process for the order-1 PGD and about 2 MB for the aligned cpu_entry_area (PTI docs).

Real-world use cases

Meltdown mitigation
On affected Intel CPUs, /sys/devices/system/cpu/vulnerabilities/meltdown reports Mitigation: PTI; Windows and macOS shipped KAISER-style equivalents (Lipp et al.).
Cloud fleets
Operators measured syscall rates per service, moved to PCID-capable kernels, and adopted huge pages to keep overhead low (Gregg).
Trusted workloads
On unaffected CPUs or fully trusted single-tenant boxes, nopti or pti=off disables it at boot (PTI docs; LWN).
KASLR hardening
Its original purpose: hiding the kernel layout from timing and prefetch side channels, still relevant where the CPU is not vulnerable to Meltdown (KAISER).

Newer CPUs that report immunity to rogue data cache load are not flagged as Meltdown-affected, and the kernel leaves PTI off on them by default, which is why most current AMD and recent Intel systems run without it (overview).
