sched_ext: Pluggable CPU Schedulers Written in BPF

How Linux learned to hot-swap its CPU scheduler without a reboot, and without trusting the new one.

October 27, 2026 · 5 min read

Summary

For two decades the Linux answer to “can I plug in my own scheduler?” was no: the community argued that one general-purpose fair scheduler, tuned by everyone, beats a zoo of special-purpose ones (LWN, 2023). sched_ext changes that. It is a new scheduling class whose policy is defined entirely by a set of BPF programs, the BPF scheduler, loaded from user space at runtime (kernel docs). It was merged for Linux 6.12 (LWN, LPC 2024).

The trick that made it acceptable is safety: the BPF verifier guarantees the scheduler code can’t crash the kernel, and a kernel-side watchdog guarantees it can’t starve the machine. If a runnable task stalls, the BPF program hits an error, or an operator presses SysRq-S, every task is reverted to the fair-class scheduler and the system carries on (kernel docs).

Deeper dive

A scheduling class, not a replacement

Linux already has a stack of scheduling classes (stop, deadline, realtime, fair, idle) that the core walks in priority order. sched_ext slots in as SCHED_EXT below the fair class, so a BPF scheduler can never starve realtime work or, in partial mode, an ordinary shell running as SCHED_NORMAL (LWN). Tasks opt in with sched_setscheduler(). If no BPF scheduler is loaded, SCHED_EXT tasks simply run as SCHED_NORMAL. Once one is loaded without SCX_OPS_SWITCH_PARTIAL, it takes over all normal, batch, idle and ext tasks; with that flag it only takes the tasks that asked for it (kernel docs).

The callback table: struct sched_ext_ops

A BPF scheduler is a struct sched_ext_ops filled with BPF programs and registered through BPF’s struct_ops mechanism. Only ops.name is mandatory; every callback is optional and has a sane default (kernel docs). The important ones are:

  • select_cpu(): called when a task wakes; returns a CPU hint and wakes that CPU if idle. The hint isn’t binding.
  • enqueue(): decides where the runnable task waits: a built-in queue, a custom queue, or the scheduler’s own BPF maps.
  • dispatch(): called when a CPU runs dry; refills its local queue.
  • runnable(), running(), stopping(), quiescent(): state notifications used for accounting such as virtual runtime.
  • cpu_acquire() / cpu_release(): tell the BPF side when a higher class takes or returns a CPU (LWN).

Dispatch queues (DSQs)

The core scheduler and a BPF program think about time very differently, so sched_ext puts dispatch queues between them. A DSQ can be a FIFO or a vtime-ordered priority queue. There is one global DSQ (SCX_DSQ_GLOBAL), one local DSQ per CPU (SCX_DSQ_LOCAL), and as many custom DSQs as the scheduler creates with scx_bpf_create_dsq(). The invariant is simple: a CPU only ever runs tasks from its own local DSQ. Everything else is about moving tasks into the right local DSQ at the right moment (kernel docs).

When a CPU needs work it checks its local DSQ, then tries to move a task from the global DSQ, then calls ops.dispatch(), which can insert tasks with scx_bpf_dsq_insert() or pull from a custom DSQ with scx_bpf_dsq_move_to_local(). If that still yields nothing and the previous task is runnable, it keeps running; otherwise the CPU goes idle.

Custody and the watchdog

Because enqueue() is allowed to stash a task in a BPF map and not queue it anywhere visible, the kernel tracks which tasks are in the “BPF scheduler’s custody” and calls ops.dequeue() exactly once when a task leaves it, for example on dispatch, sleep, or an affinity change (kernel docs). It also watches the clock: a runnable task left waiting too long (30 seconds by default in the original design) gets the BPF scheduler unloaded (LWN). That is what turns “a buggy policy” from an outage into a log message.

Class stack and the fail-safe path

Why BPF and not a kernel module? A module can scribble anywhere; a BPF scheduler passes the verifier, can only call approved kfuncs like scx_bpf_dsq_insert(), and can be detached at any moment. That is what lets a fleet operator try a new policy on live machines and roll back instantly, which a pluggable-module design could never promise (scx overview).

A minimal scheduler

The in-tree scx_simple example is a global FIFO in a handful of lines: select_cpu() calls scx_bpf_select_cpu_dfl() and, if it found an idle core, inserts straight into SCX_DSQ_LOCAL; otherwise enqueue() inserts into SCX_DSQ_GLOBAL with the default slice. You check what is running with cat /sys/kernel/sched_ext/root/ops, and per-scheduler counters such as fallback CPU picks live in /sys/kernel/sched_ext/root/events (kernel docs).

Fair class (EEVDF)

  • One policy for every workload
  • Changes need a kernel patch, review, and reboot
  • Tuned for broad fairness and latency
  • Always present as the fallback

sched_ext

  • Policy is a BPF program loaded at runtime
  • Swap or roll back without rebooting
  • Can specialise for games, VMs, or one service
  • Watchdog reverts to fair on any failure

Real-world use cases

Fleet partitioning
scx_layered splits CPUs into layers per workload class; it was reported deployed on over a million machines (LWN).
Gaming
scx_lavd targets interactivity and steady frame rates and was headed for Steam Deck devices (LWN).
Desktop responsiveness
scx_bpfland minimises response time on personal machines; distributions such as Arch, Ubuntu, Fedora and CachyOS ship sched_ext packages (LWN).
VM hosting
A “central” design dedicates one CPU to scheduling decisions and runs the rest tickless; Google reported benefits for VM hosting with that approach (LWN).
User-space policy
scx_rustland forwards scheduling events to a Rust user-space process that makes the decisions, for observability and fast iteration (LWN).
Research and teaching
New ideas can be tried on a live machine in minutes; the sched-ext/scx repo collects many production and example schedulers.
Design takeaway. sched_ext is a pattern worth copying beyond kernels: expose a narrow, queue-based contract to untrusted policy code, keep the invariants (every runnable task eventually runs) enforced by the host, and make the fallback path always available.
