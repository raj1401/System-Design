Stream Processing Time: Event Time, Watermarks, and Windowing

How an unbounded, out-of-order stream decides when an hour is actually over.

November 23, 2026 · 5 min read

Summary

A batch job gets to see all of its input before it answers. A streaming job never does: the data is unbounded, it arrives out of order, and some of it shows up minutes or days late — a phone that was offline on a flight, a partition that lagged, a retry storm [1][2]. To compute something like “clicks per ad per minute” correctly, a stream processor needs three ideas. Event time (when the thing happened) is distinguished from processing time (when the system saw it). Windows slice the infinite stream into finite, event-time buckets. And watermarks are a monotonically advancing signal that says “event time has (probably) progressed to t,” telling operators when a window can be emitted and its state discarded [3][4].

Key idea: You cannot know when an unbounded, out-of-order stream is “complete.” Watermarks turn that unknowable fact into an explicit, tunable tradeoff between correctness (wait longer for stragglers), latency (emit sooner), and cost (state you must keep around) [1].

How It Works

Two clocks: event time vs processing time

The Dataflow model defines event time as the time at which an event actually occurred, and processing time as the time at which it is observed at some point in the pipeline. An event’s event time never changes; its processing time keeps moving as it flows through operators, and the gap between the two — skew — varies dynamically with network delay, scheduling, backlogs and outages [1]. Processing-time windows are simple and fast but not deterministic: an hourly processing-time window contains whatever happened to arrive that hour, and replaying the same data gives different answers [4]. Event-time windows give the same result regardless of arrival order or reprocessing — if you know when all the data has arrived.

Event time vs processing time skew

Windows: slicing the infinite stream

Windowing assigns each element to one or more finite buckets so aggregations and joins have boundaries [1]. The common shapes:

  • Tumbling (fixed) — non-overlapping, gap-less windows of size S; each record belongs to exactly one. Kafka Streams aligns them to the epoch as [N·size, N·size + size) [6].
  • Sliding / hopping — size S advancing by period P < S, so windows overlap and a record lands in S/P of them (e.g. “last 10 minutes, updated every 5”) [8].
  • Session — per-key, data-driven windows that close after a gap of inactivity; they are unaligned and windows merge when a new event bridges two sessions [1][6].

Tumbling, sliding and session windows

Watermarks: measuring progress in event time

A watermark is a timestamp W flowing through the pipeline that asserts no more records with event time ≤ W are expected. When an operator’s watermark passes the end of a window, it can fire the window and clean up its state [4]. Google’s MillWheel gave a precise recursive definition: the low watermark of computation A is min(oldest unfinished work in A, low watermarks of all upstream computations), seeded by the injectors that bring data in from external systems, and kept monotonic even when late data appears [3]. Flink similarly takes the minimum across an operator’s input streams, which is why one silent partition can stall the whole job unless it is marked idle [4][5].

Watermarks come in two flavours [2]. A perfect watermark is possible only when you fully know the input (e.g. ordered log files). Most are heuristic: the commonest is “bounded out-of-orderness,” W = max event time seen − allowed delay. Flink exposes this as WatermarkStrategy.forBoundedOutOfOrderness(...) [5]; Spark Structured Streaming’s withWatermark("ts", "10 minutes") computes max event time across partitions minus the threshold [8][9]. A heuristic watermark can be too slow (adding latency) or too fast (declaring data late that was merely delayed) [1].

A watermark closing a 12:00–12:10 window

Triggers, panes and allowed lateness

The Dataflow model separates what is computed (the transform), where in event time (windowing), when in processing time results are emitted (triggers) and how successive results relate (accumulation mode) [1][2]. A typical trigger emits a speculative early result every minute, an on-time result when the watermark passes the window end, and a late “pane” for each straggler. Panes can be discarding (each pane carries only new data — good when the sink sums), accumulating (each pane is the full value so far — good when the sink overwrites), or accumulating-and-retracting [1][10].

Allowed lateness bounds how long a window’s state is kept after the watermark passes its end. Beam’s withAllowedLateness, Flink’s allowedLateness [7] and Kafka Streams’ grace period all play this role. Kafka Streams has no separate watermark; instead it tracks stream time (the largest timestamp seen) and drops a record once stream time exceeds windowEnd + grace. TimeWindows.ofSizeWithNoGrace sets grace to zero, so any out-of-order record that arrives after the window ends is dropped [6][11].

Short delay / grace

  • Results emitted sooner
  • Less window state in memory
  • More events dropped as late
  • Good for alerting and dashboards

Long delay / grace

  • Higher completeness and correctness
  • Higher end-to-end latency
  • Larger state and checkpoints
  • Good for billing and reporting
Design tip: Never silently drop late data. Count it (MillWheel’s Zeitgeist pipeline dropped late records but tracked them, roughly 0.001% [3]), route it to a side output, or let downstream stores accept corrections. Spark exposes numRowsDroppedByWatermark in query progress for exactly this reason [8].

Real-World Use Cases

Anomaly detection
Google’s Zeitgeist used MillWheel low watermarks to tell whether a dip in search queries was real or just data delayed on the wire [3].
Ad and video analytics
The Dataflow paper is motivated by billing and video-session analysis on unbounded, out-of-order logs, using session windows and late-firing triggers [1].
Real-time metrics
Flink and Spark jobs compute per-minute tumbling or sliding aggregates with bounded-out-of-orderness watermarks and allowed lateness [5][8].
Kafka-native services
Kafka Streams apps use windowed aggregations and joins with grace periods, plus session windows for per-user activity [6][11].
Mobile and IoT telemetry
Devices buffer events offline and upload them later, so event-time windows and lateness policies keep aggregates correct [1].
Backfills and replays
Because event-time results do not depend on arrival speed, the same pipeline can reprocess history and produce the same answers [4].

Takeaways

Pick event time whenever results must be reproducible. Choose the window shape from the question (fixed periods, rolling averages, or user sessions). Then set the watermark delay and allowed lateness explicitly, since together they decide your latency, completeness and state cost. Finally, plan for late data, because heuristic watermarks will sometimes be wrong [1][2].
