Write-Ahead Logging and Crash Recovery: fsync, Checkpoints, and ARIES

How databases promise durability with one sequential log, and how they rebuild themselves after the power goes out.

November 14, 2026 · 5 min read

Summary

A database keeps hot pages in memory and writes them back to disk lazily, so at any instant the data files are a mix of old and new versions. Write-ahead logging (WAL) makes that safe with a single rule: describe every change in an append-only log, and force the log to stable storage before the changed data page may reach disk and before a commit is acknowledged. After a crash, the system replays the log to redo committed work that never reached the data files and undoes work from transactions that never committed. The log is sequential, so a commit costs one log flush (often shared by many transactions) instead of many random page writes. This is the core idea behind recovery in PostgreSQL, InnoDB, SQLite (in WAL mode), and the ARIES algorithm that shaped most commercial engines.

The two WAL invariants. (1) Log before data: a dirty page may be flushed only after the log is durable up to the last record that touched that page. (2) Log before commit: a transaction is reported committed only after its commit record is durable. Break either one and recovery can no longer reconstruct a correct state.

Deeper dive: the mechanisms

Log records and LSNs

Each change produces a log record tagged with a monotonically increasing LSN (log sequence number). Records may carry redo information (the after-image or an operation), undo information (the before-image), or both, as the Minibase ARIES notes describe. Every data page stores a pageLSN: the LSN of the last record applied to it. That single number is what makes recovery idempotent, because redo can skip any record whose LSN is not greater than the page’s pageLSN. In ARIES, records also carry a PrevLSN chaining a transaction’s records backwards, which undo follows (Mohan, Repeating History Beyond ARIES).

Steal / no-force: why both redo and undo are needed

WAL engines typically choose a steal buffer policy (an uncommitted transaction’s dirty page may be written to disk to free memory) and no-force (committed pages need not be flushed at commit). Steal means the disk can contain uncommitted changes, so recovery needs undo. No-force means the disk can be missing committed changes, so recovery needs redo. WAL pays for this flexibility with one cheap sequential write per commit.

Rollback journal (undo log)

  • Copy the original page to a journal, then overwrite the database in place
  • Commit requires the database pages themselves to be durable
  • Recovery restores old pages from the journal
  • SQLite’s default journal_mode=DELETE

Write-ahead log (redo-centric)

  • Append changes to the log; data pages are written later
  • Commit needs only the log flushed up to the commit record
  • Recovery replays the log forward from a checkpoint
  • Readers can keep using older pages while writers append

The write path: log first, pages later

fsync, group commit, and the durability knob

“Durable” means the log bytes survived an OS flush such as fsync or fdatasync (PostgreSQL defaults to fdatasync on Linux per its WAL settings docs). A flush costs anywhere from microseconds to milliseconds, so engines use group commit: concurrent committers piggyback on one flush. PostgreSQL exposes commit_delay and commit_siblings to deliberately wait for more company, and synchronous_commit=off to return before the flush at the cost of possibly losing the last few transactions, never corrupting the database (PostgreSQL asynchronous commit). InnoDB’s equivalent is innodb_flush_log_at_trx_commit, where 1 flushes at every commit and 0 flushes roughly once per second (MySQL log buffer docs).

fsyncgate. In 2018 PostgreSQL developers found that on Linux a failed fsync could mark pages clean and clear the error, so a retried fsync “succeeded” and a checkpoint completed over lost writes (LWN report, kernel follow-up). The fix: PANIC on fsync failure and rely on WAL replay, back-patched to 9.4 through 11 (PostgreSQL wiki). Lesson: a WAL is only as trustworthy as the flush semantics underneath it.

Checkpoints bound recovery time

Without checkpoints the log grows forever and recovery would replay it all. A checkpoint records how far the data files are known to be caught up. PostgreSQL flushes dirty pages, writes a checkpoint record, and stores its location in pg_control; recovery begins at that checkpoint’s redo point and older WAL segments can be recycled (WAL configuration, WAL internals). ARIES uses fuzzy checkpoints that just snapshot the active-transaction table and dirty-page table without stopping the world. Shorter intervals mean faster recovery but more page flushing, the core tuning trade-off.

Torn pages

An 8 KB page spans multiple 512-byte sectors, so power loss mid-write can leave half old and half new data, which a small row-level redo record cannot fix (PostgreSQL reliability). PostgreSQL’s full_page_writes logs a whole page image on its first modification after each checkpoint; since the log-before-data rule guarantees that image is durable before the page write starts, at most one of the two copies can be torn (PostgreSQL wiki). InnoDB instead writes pages to a doublewrite buffer first, then to their final location. WAL records themselves carry CRC-32C checksums, so a torn log tail simply marks where recovery stops.

ARIES: analysis, redo, undo

ARIES (Mohan et al., ACM TODS 1992) restarts in three passes. Analysis scans forward from the last checkpoint to rebuild the transaction table and dirty-page table, computing RedoLSN, the earliest record that might be missing from disk. Redo “repeats history”: it reapplies every logged update from RedoLSN, including those of uncommitted losers, whenever pageLSN < recordLSN, restoring the exact state at the crash. Undo then rolls back losers in reverse LSN order in a single backward sweep, writing compensation log records (CLRs) whose UndoNxtLSN ensures that a crash during recovery never undoes the same work twice (Mohan; Berkeley summary). Repeating history, rather than selectively redoing only winners as System R did, is what lets ARIES support record-level locking with WAL.

The file system is part of your protocol

Correct WAL code still depends on ordering and atomicity guarantees from the layer below. Pillai et al. built tools to test file-system persistence properties and found 60 crash vulnerabilities across 11 widely used applications, including databases and key-value stores, many caused by assuming writes persist in order or that appends are atomic (OSDI 2014). Checksummed records, explicit flushes of both files and directories, and treating flush errors as fatal are the defensive defaults.

Real-world use cases

PostgreSQL
WAL with checkpoints, full-page images and CRC-checked records; the same stream feeds point-in-time recovery and streaming replicas.
MySQL InnoDB
Redo log plus doublewrite buffer; innodb_flush_log_at_trx_commit trades durability for commit throughput.
SQLite
PRAGMA journal_mode=WAL appends to a -wal file and checkpoints back automatically at 1000 pages by default, letting readers run alongside a writer (SQLite docs).
LSM key-value stores
Writes hit a WAL before the memtable so unflushed data survives a crash; the log is dropped once the memtable becomes an SSTable.
Replication & CDC
Shipping the log is replication: replicas replay WAL, and change-data-capture tools tail it to publish row events.
Consensus logs
Raft and similar protocols persist log entries before acknowledging them, the same log-before-ack rule applied across machines.
Design takeaway. When you need durable state, start with an append-only, checksummed log flushed on commit, plus periodic checkpoints. Decide explicitly how much recent data you can afford to lose (per-commit flush, group commit, or async commit), and treat a failed flush as a crash, not a retry.
