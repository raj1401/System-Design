NUMA: Local Allocation, Memory Policy, and Cross-Node Latency

Why a page allocated on the wrong socket can cost more than a cache miss — and how Linux decides where your bytes live.

September 15, 2026 · 5 min read

The Concept

NUMA (Non-Uniform Memory Access) means DRAM is partitioned into nodes, each close to a set of CPUs (typically one socket or one chiplet cluster). A load from the CPU’s own node is local; a load that crosses the interconnect to another node’s memory is remote. Remote accesses pay higher latency and often lower effective bandwidth, even though the address space looks flat to userspace.

On a two-socket server, remote DRAM can easily add tens of nanoseconds versus local DRAM — enough that database buffer pools, JVM heaps, and HPC working sets that land on the wrong node silently lose a large fraction of throughput. The Linux kernel’s job is to keep allocations local by default, then give you policies when that default is wrong.

Key idea: Virtual addresses do not encode NUMA nodes. Placement is decided when a page is first faulted in (first-touch local allocation), then optionally steered with set_mempolicy, mbind, or numactl. A page that already lives on node 1 will not magically move when your thread migrates to a CPU on node 0 — unless you migrate it.

Underlying Mechanism

Nodes, distances, and zonelists

Each NUMA node owns a slice of physical memory and a set of CPUs. Firmware publishes a distance table (ACPI SLIT / SRAT on x86); Linux turns that into per-node zonelists ordered by how close each memory zone is. When a CPU on node 0 allocates, the kernel walks node 0’s zonelist first — that is local allocation.

If the local node is out of free pages, the allocator falls back to the next entry in the zonelist (a nearby remote node). That fallback is why a process can keep running under memory pressure, and also why remote pages appear without any explicit request.

First-touch local allocation

Linux’s system default after boot (once init starts) is local allocation: pages are taken from the node of the CPU that triggered the allocation — typically the first write that faults the page in after mmap or heap growth. Read-only mappings and pages only touched by another thread can still end up “wrong” relative to the eventual worker CPUs.

That is why NUMA-sensitive services often pre-touch memory on the intended node (or pin threads with sched_setaffinity / numactl --cpunodebind before allocating). Automatic NUMA balancing can later migrate pages toward the CPUs that fault them, but that is reactive and not free.

Memory policies: latency vs bandwidth

Linux exposes a small set of modes via set_mempolicy(2) (task-wide) and mbind(2) (per address range). The important ones:

  • MPOL_DEFAULT / MPOL_LOCAL — allocate on the CPU’s local node; fall back if it is empty.
  • MPOL_BIND — only allocate from the listed nodes (strict); fails if they cannot satisfy the request.
  • MPOL_PREFERRED — try a preferred node first, then fall back.
  • MPOL_INTERLEAVE — round-robin pages across nodes to maximize aggregate bandwidth when a working set is larger than one node’s DRAM or is accessed from many sockets.

By default, a new VMA policy affects future allocations only. Since Linux 2.6.16, mbind can also migrate existing pages (MPOL_MF_MOVE / MPOL_MF_MOVE_ALL) so the range physically matches the new policy.

Diagram 2 — Policy Choice: Local vs Interleave

Task policy (set_mempolicy)

  • Applies to future anonymous and private mmap allocations for the thread
  • Inherited across fork; typically set before workers allocate
  • CLI: numactl --membind=N ./app

VMA / shared policy (mbind)

  • Scoped to a byte range — ideal for one buffer or shm segment
  • Can migrate pages already faulted in with MOVE flags
  • Shared mappings can carry a shared policy visible to all attachers

Affinity is half the story

Memory policy without CPU affinity is incomplete. If threads bounce across sockets while pages stay put, every access becomes remote. Pair placement with sched_setaffinity(2), cpusets, or numactl --cpunodebind. Inspect live placement with numactl --hardware and /proc/<pid>/numa_maps.

Gotcha: Kernel boot-time structures often use interleave so no single node is overloaded with OS metadata. Once userspace starts, the default flips to local. Your app’s first page faults — not mmap itself — are usually when placement is decided.

Real-World Use Cases

Databases & in-memory stores
Pin buffer pools and worker threads to the same node (or shard pools per node) so index probes and page reads stay local.
JVMs and language runtimes
Large heaps allocated on the wrong socket show up as mysterious GC and mutator slowdowns; launchers often wrap the process in numactl.
HPC and scientific codes
OpenMP/MPI ranks bind to nodes; interleaved or per-rank bind policies keep multi-GB arrays near the cores that stream them.
Containers & cpusets
Cpuset memory nodes constrain which NUMA nodes a pod may use; local policy then allocates inside that allowed set.

Trade-offs at a Glance

Optimize for locality

  • Lower latency per load/store
  • Requires stable CPU↔memory affinity
  • Risk of underusing remote DRAM capacity

Optimize for bandwidth / capacity

  • Interleave or span multiple nodes
  • Better aggregate BW for shared data
  • Every access may pay some remote cost
