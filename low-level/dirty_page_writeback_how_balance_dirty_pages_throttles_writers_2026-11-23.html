Dirty Page Writeback: How balance_dirty_pages() Throttles Writers

A feedback controller hidden inside every buffered write(): pacing producers of dirty memory to the speed of the disk.

November 23, 2026 · 5 min read

Summary

On Linux, a buffered write() almost never touches the disk. It copies bytes into the page cache, marks those pages dirty, and returns. Later, kernel flusher threads write the dirty pages back to storage. This write-back caching lets the kernel merge small writes, let filesystems choose better on-disk layout, and skip I/O entirely for short-lived temporary files.

The catch is that memory fills up far faster than a disk drains. If nothing slowed producers down, a single dd to a USB stick could fill RAM with gigabytes of data that take minutes to flush. Linux handles this with two thresholds, dirty_background_ratio (default 10%) and dirty_ratio (default 20%) [1][2], and with balance_dirty_pages(). Since Linux 3.2, that function has been a control loop. It puts writing tasks to sleep for computed pauses, so each one dirties pages at roughly the rate the device can clean them [3][4].

Key idea: the writer never does the I/O itself. It only sleeps. The flusher thread owns all writeback I/O, which keeps the I/O sequential and the disk busy, while the sleep time paces the writer like a token bucket that refills at the disk's bandwidth.

Deep dive: the moving parts

1. Dirtying and the two thresholds

Pages get dirtied by buffered writes and by stores to shared file mappings. The kernel compares the dirty-plus-writeback count against limits computed from dirtyable memory (free plus reclaimable pages, not total RAM) [1]:

  • bg_thresh comes from dirty_background_ratio or _bytes. Above it, flusher threads start background writeback.
  • thresh comes from dirty_ratio or _bytes. Above it, the process generating writes is throttled.
  • dirty_expire_centisecs (default 3000, so 30 s) is the age at which dirty data becomes eligible for writeout. dirty_writeback_centisecs (default 500, so 5 s) is the periodic flusher wakeup interval [2].

The _bytes and _ratio forms are mutually exclusive. Whichever you write last takes effect, and the other reads as 0 [1][5]. The byte variants were added in 2008 because percentage limits got enormous on large-memory machines [6].

2. Per-device flusher threads

Until 2.6.32, a shared pool of 2 to 8 pdflush threads served every disk. They had to use non-blocking writeback and could get starved when a request queue was congested. Jens Axboe replaced them with flushers bound to each backing device (backing_dev_info, or BDI). The dirty-inode lists moved from the superblock to the BDI, and a flusher can now block on its own queue without hurting other devices [7]. A struct writeback_control describes each pass: WB_SYNC_NONE for background work or WB_SYNC_ALL for data-integrity sync, plus nr_to_write [7]. In today's kernels this work runs as bdi_writeback (wb) work items on kworkers. With cgroup writeback there is one wb per (BDI, memory cgroup) pair.

3. IO-less balance_dirty_pages()

Before 3.2, a task over the limit was made to write pages back itself. With many such tasks, the disk saw several interleaved streams, and the resulting seeks cut bandwidth exactly when it mattered most. Pauses were also bumpy, from hundreds of milliseconds to seconds [3][8]. Fengguang Wu's IO-less throttling series replaced this with a rate controller [9]. The pseudo-code from the patch describes it well [8]:

task_ratelimit = dirty_ratelimit * pos_ratio
pause = pages_dirtied / task_ratelimit; sleep(pause)
Every ~200 ms: ref = dirty_ratelimit * pos_ratio * write_bw / dirty_rate, and dirty_ratelimit steps toward ref.

The controller has two halves:

  • Rate estimation. If N tasks write to a disk with bandwidth write_bw, each one should get about write_bw / N. The kernel does not know N, so it measures the device's average write bandwidth and the observed dirty rate. It then nudges wb->dirty_ratelimit toward the balanced value every BANDWIDTH_INTERVAL (HZ/5, which is 200 ms) [2][8].
  • Position control. pos_ratio scales the rate up or down depending on how far the dirty count sits from a setpoint. Globally, freerun = (thresh + bg_thresh)/2 and setpoint = (freerun + limit)/2. The control line is the cubic f = 1 + ((setpoint - dirty)/(limit - setpoint))3. It is built so that f(freerun)=2, f(setpoint)=1, and f(limit)=0. That gives a fast response to large errors and little oscillation near the setpoint [2]. A second, per-wb control line takes the device's own setpoint into account, and the stricter of the two wins [3].

Below the freerun ceiling, tasks are not throttled at all. To keep the hot path cheap, a task only enters balance_dirty_pages() after dirtying current->nr_dirtied_pause pages. That interval grows roughly with the square root of the remaining headroom, so large NUMA machines do not hammer global counters. A pause is capped at MAX_PAUSE (200 ms) and taken as a killable io_schedule_timeout(), which is why killall dd now takes effect immediately [2][4].

4. Per-device shares, strictlimit, and cgroups

The global limit is divided among BDIs according to each device's recent share of completed writeout. Slow devices therefore cannot hold most of the dirty cache, and fast ones get more room. Admins can override the split in /sys/class/bdi/<dev>/ with min_ratio, max_ratio, max_bytes (plus the _fine variants, in parts per million) and strict_limit. strict_limit enforces a device's share even before the global background limit is reached, which helps with slow or untrusted devices such as FUSE, NFS, or nbd [10]. With cgroup v2, the memory controller defines a second dirty domain whose limits come from the cgroup's memory limit. Both the system-wide and per-cgroup states are checked, and the stricter one is enforced. Writeback I/O is charged per inode to the owning cgroup on ext2, ext4, btrfs, f2fs and xfs [11].

Before 3.2: direct writeback

  • A task over the limit writes pages back itself
  • Many writers produce interleaved, seeky I/O
  • Pauses vary from hundreds of ms to seconds
  • Lock contention and cache bouncing on big boxes

3.2+: IO-less throttling

  • A task over its rate sleeps for a computed pause
  • Only the flusher issues I/O, so streams stay sequential
  • Smooth pauses (≤ 200 ms) sized to device bandwidth
  • Per-device and per-cgroup setpoints

5. Below the page cache: writeback throttling (wbt)

balance_dirty_pages() limits how much dirty data exists. It does not limit how much of that data is queued in the block layer at once. Thousands of queued background writes put a foreground read at the back of a long line, which is a storage version of bufferbloat [12]. Axboe's blk-wbt, inspired by CoDel, limits in-flight buffered writeback per device. It shrinks the allowed queue depth when minimum read latency in a window exceeds wb_lat_usec, which defaults to 2 ms for SSDs and 75 ms for rotational disks [13][14].

Real-world use cases

USB sticks and slow media
Percentage limits on a large-RAM 64-bit machine can let gigabytes pile up for a slow stick, so sync or unmount stalls for minutes. Setting dirty_bytes/dirty_background_bytes or a BDI max_bytes bounds the backlog [5][10].
Databases and latency-sensitive services
Lowering background thresholds makes flushing start earlier and run steadily, which avoids bursts that collide with fsync-heavy commits. wbt protects foreground reads during bulk loads [1][13].
Containers and multi-tenant hosts
cgroup v2 writeback gives each memory cgroup its own dirty domain and charges flush I/O to it. A noisy log writer then runs into its own limit rather than the host's [11].
FUSE and network filesystems
strict_limit and max_ratio keep an untrusted or stuck backend (FUSE daemon, hung NFS server) from holding most of the system's dirty memory [10].
Diagnosing write stalls
The writeback:balance_dirty_pages and writeback:bdi_dirty_ratelimit tracepoints show setpoints, rate limits and per-task pauses live, so you can tell throttling apart from slow I/O [15].
Bulk copy and backup jobs
With IO-less throttling, many concurrent dd/rsync streams share device bandwidth fairly (about write_bw/N each) and stay responsive to signals [3][4].
Tuning rule of thumb: think in time, not percentages. The worst-case backlog is roughly dirty limit ÷ device write bandwidth. A 20% limit on a 256 GB host can mean tens of GB of dirty data, which is minutes of writeback for a slow device. Byte-based limits and per-BDI caps keep that drain time bounded.
