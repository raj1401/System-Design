io_uring: The Ring-Buffer Interface Reshaping Linux I/O

How two shared memory rings and an optional kernel poller let applications do I/O with (almost) zero syscalls.

July 29, 2026 · 5 min read

What is io_uring?

io_uring is a Linux kernel interface, introduced by Jens Axboe, for providing the kernel with a schedule of system calls, and receiving the results as they're generated. It replaces the classic pattern of "call a syscall, block or poll for readiness, call another syscall" with two ring buffers that user space and the kernel both read and write directly, without copying.

The submission and completion queues are shared between userspace and the kernel, which eliminates the need to copy data when initiating and completing I/O. The application places a submission queue entry (SQE) describing an operation — read, write, accept, send, even mkdir — onto the submission queue (SQ), and the kernel eventually pushes back a matching completion queue entry (CQE) onto the completion queue (CQ). In contrast to epoll's readiness-based polling approach, io_uring employs a completion-based model, notifying applications after operations complete rather than when they become possible, using two memory-mapped ring buffers with configurable capacity: the Submission Queue and the Completion Queue.

Why this matters: every traditional syscall costs a user↔kernel mode transition, and interfaces like epoll or POSIX AIO still require one syscall per readiness check or submission. At millions of operations per second, that overhead dominates. io_uring's entire premise is to amortize — or eliminate — that cost by making the kernel and application communicate through memory instead of trapping into the kernel every time.

Mechanics: rings, indirection, and polling

The two rings

Setup happens through io_uring_setup(2), which allocates the rings and returns a file descriptor; the app then mmaps that descriptor into its address space. The general programming model is to set up shared buffers with io_uring_setup(2) and mmap(2), mapping into user space shared buffers for the SQ and CQ; you place I/O requests you want to make on the SQ, while the kernel places the results on the CQ, and for every I/O request you create an SQE and add it to the tail of the SQ.

Interestingly, the SQ is not a direct ring of SQEs. While the completion queue ring directly indexes the shared array of CQEs, the submission ring has an indirection array in between — the submission side ring buffer is an index into this array, which in turn contains the index into the SQEs. That extra layer lets applications reorder or reuse SQE slots flexibly, including embedding requests inside their own data structures.

Completions, by contrast, are simple and guaranteed one-to-one with submissions: there is a completion queue event added by the kernel for each submission queue entry that is submitted — there is exactly one CQE added to the completion queue as a result of the kernel processing an SQE (multishot operations are the deliberate exception). Because different devices finish at different speeds, ordering isn't preserved: it is not necessary that submitted requests complete in the same order they show up as CQEs — CQEs can arrive in any order as they become available, whichever operation finishes first.

Telling the kernel: io_uring_enter

Normally, after writing SQEs, the application still needs one lightweight syscall to notify the kernel: once you place one or more SQEs onto the SQ, you need to let the kernel know by calling io_uring_enter(2), which is also capable of waiting for a specified count of events to complete. That's already far cheaper than issuing a syscall per operation, since one io_uring_enter call can submit a whole batch and simultaneously reap a batch of completions.

SQPOLL: removing the syscall entirely

The more radical mode sets IORING_SETUP_SQPOLL, which spins up a dedicated kernel thread that watches the SQ itself. When this flag is specified, a kernel thread is created to perform submission queue polling, enabling an application to issue I/O without ever context switching into the kernel — by filling in new SQEs and watching the CQ, the application can submit and reap I/Os without doing a single system call. This thread is a real, named kernel thread — the name of this thread is io_uring-sq — and it can even be pinned to a CPU with IORING_SETUP_SQ_AFF.

Because a spinning kernel thread wastes CPU when idle, it backs off automatically: to avoid wasting too much CPU while the io_uring instance is inactive, the kernel side thread will automatically go to sleep when it has been idle for a while, and when that happens it will set IORING_SQ_NEED_WAKEUP in the SQ ring flags member — the application then cannot rely on the kernel automatically finding new entries and must issue one explicit io_uring_enter to wake it back up.

Overflow, feature flags, and registered resources

Because the CQ has fixed capacity, a burst of completions can outrun the consumer. Modern kernels handle this gracefully: if the CQ ring overflows — more entries are generated than fit in the ring before the application can reap them — then if the kernel supports IORING_FEAT_NODROP the ring enters a CQ ring overflow state instead of silently losing events. io_uring also lets applications pre-register file descriptors and buffers with the kernel once, up front: registration creates long-lived kernel references, reducing per-I/O overhead versus passing raw pointers and fds on every request.

A note on completion paths inside the kernel

Not every request finishes instantly. Internally, io_uring dispatches work along different paths depending on whether the operation can complete immediately or must block: io_uring provides three execution paths — inline completion, asynchronous execution via the poll set, and a fallback to worker threads for blocking operations — and an optional SQPoll thread can submit requests without syscalls. That worker-thread fallback isn't free: issuing NOPs handled by io_worker threads added an average overhead of 7.3 microseconds compared to inline execution, resulting from offloading to a separate thread and synchronization between them.

How it compares to older interfaces

epoll / POSIX AIO / libaio

  • Synchronous I/O forces programs to block until operations complete, wasting CPU cycles, and asynchronous alternatives like libaio came with scattered interfaces and inconsistent behavior.
  • These interfaces bring overhead from frequent system calls and memory copies, and offer limited support for non-storage I/O such as sockets.
  • readiness-based: app is told "you may act now," then still issues the syscall

io_uring

  • A unified interface integrates storage, network, and other system calls into one framework, with fully asynchronous execution allowing applications to perform useful work while I/O completes in the background.
  • completion-based: kernel tells the app only once work is actually done
  • SQPOLL / IOPOLL modes can remove syscalls from the hot path almost entirely

It's worth being honest about the gains, though: naively swapping io_uring in for epoll without redesigning the surrounding code barely moves the needle. A naive swap of io_uring for epoll or libaio with no architectural change yields roughly 1.06x-1.10x end-to-end — often noise in A/B tests — while code engineered for rings, with registered buffers, batching, and zero-copy send/receive, can reach up to roughly 2.3x on network shuffle workloads and 2.5x with zero-copy receive. The lesson: io_uring is a different programming model, not a drop-in replacement — you have to batch and register resources to see the real win.

Real-world use cases

Storage engines & databases
High-performance storage systems use io_uring's IORING_SETUP_IOPOLL and registered buffers to drive NVMe devices at near-hardware speed without per-I/O syscall overhead.
Network servers
Multishot accept/recv operations and zero-copy send let event-driven servers replace epoll loops with a single ring, cutting syscalls under heavy connection churn.
Language & runtime integrations
Runtimes such as tokio-uring for Rust and userspace wrappers for languages like Zig expose io_uring as their async I/O backend on Linux.
Cross-platform async I/O
Libraries such as libuv are evolving to treat io_uring as a first-class backend alongside epoll and IOCP, reflecting its role as a general async I/O primitive.

Caveats worth knowing

SQPOLL is a privileged operation on most kernels — note that setting up an io_uring instance with IORING_SETUP_SQPOLL is a privileged operation. Buffer lifetime rules also differ subtly by opcode: pointers used purely at submission time (like a timeout struct) can be freed right after submission, but pointers to a buffer used as part of a IORING_OP_WRITE or IORING_OP_READ operation must remain valid until completion. Getting this wrong is a classic source of use-after-free bugs in io_uring-based code, and it's part of why the interface, while fast, demands careful engineering.
