Tail Latency at Scale: Hedged Requests, Tied Requests, and Fan-out

Why a healthy p99 on every server still gives you a slow service, and how racing replicas tames the tail.

November 2, 2026 · 5 min read

Summary

Average latency is a comforting number that hides the requests users actually remember. In large services a single user request usually fans out to dozens or thousands of backend calls, and the response is only as fast as the slowest one. Dean and Barroso's The Tail at Scale showed that rare per-server hiccups become the common case at the service level, and argued that we should build systems that are tail-tolerant: they keep answering fast even when some components are slow, much as fault-tolerant systems keep working when some components fail.

The workhorse techniques are hedged requests (send a backup copy to another replica if the first is slow, take whichever answers first) and tied requests (enqueue on two replicas and let them cancel each other once one starts work). Both are now available off the shelf in gRPC, Envoy and database drivers such as the Cassandra Java driver.

Why fan-out amplifies the tail

Suppose each leaf server normally answers in 10 ms but its 99th-percentile latency is one second. If a request touches one server, 1 in 100 requests is slow. If it must gather answers from 100 servers in parallel, the request is fast only if every leaf is fast, so the slow fraction becomes 1 - 0.99^100, about 63%. The paper also notes that with just 1 in 10,000 slow responses per server, a 2,000-server fan-out sees almost one in five user requests take over a second (Dean & Barroso, 2013).

Real measurements tell the same story. In a Google service from the paper, a single random leaf's p99 was 10 ms, but the p99 for all leaves to finish was 140 ms, and waiting for just 95% of them took 70 ms. The slowest 5% of leaves were responsible for half of the total p99 latency.

Fan-out: the root waits for the slowest leaf

Deeper dive: where variability comes from

Most slow responses are not caused by the request itself. The paper lists shared resources and noisy neighbours, background daemons, garbage collection, compaction and other maintenance work, queueing at many layers, power and thermal throttling, and hardware variation. Because the cause is usually interference on a particular machine at a particular moment, the same request sent to another replica is very likely to be fast. That observation is what makes the techniques below work.

Within-request techniques act in milliseconds; across-request techniques such as micro-partitioning, selective replication of hot data and putting slow machines on probation act over seconds to minutes. This article focuses on the within-request kind.

Hedged requests

The client sends the request to the replica it thinks is best, and if no answer has arrived after a short delay it sends a second copy to another replica. Whichever reply comes first wins, and the client cancels the rest. Sending the backup immediately would double load, so the paper recommends waiting until the first request has been outstanding longer than the 95th-percentile expected latency for that request class. That caps extra load at roughly 5% while cutting the tail sharply. In a Google benchmark reading 1,000 keys from a BigTable spread over 100 servers, hedging after 10 ms cut 99.9th-percentile latency from 1,800 ms to 74 ms while sending only 2% more requests (CACM).

Tied requests

Hedging still has a window where two servers both do the work, and waiting for p95 means only a small fraction of requests benefit. Much of the variability is queueing before execution starts, and once a request is running its completion time is far more predictable. Building on Mitzenmacher's result that letting a client pick the shorter of two queues exponentially improves load balancing over random choice (Mitzenmacher, 2001), Dean and Barroso propose enqueuing the request on two servers at once, each copy tagged with the other server's identity. When one copy starts executing, it sends a cancellation to its twin, which is dropped or deprioritised if still queued.

Both servers may start in the brief window while cancellations cross in flight, typically when both queues are empty, so the client adds a small delay of about two network message delays (1 ms or less in a modern datacenter) before sending the second copy. Google's distributed file system implementation, reading uncached data from disk with replication factor 3, kept latency nearly identical to an idle cluster even while a large sort job ran concurrently.

Tied requests: whoever starts first cancels the twin

Only hedge what is safe to repeat. A hedged write can be applied twice. gRPC's design doc warns hedging should be enabled only for methods that are safe to execute multiple times (gRFC A6), and the Cassandra driver never speculates on a query not marked idempotent. Pair hedging with idempotency keys if you must hedge writes, and remember that hedging only helps when slowness is uncorrelated across replicas: if every replica is overloaded, extra copies make things worse.

Hedging versus retries

Retry

  • Fires after an error or timeout
  • Original attempt is abandoned
  • Protects against failures
  • Usually with exponential backoff

Hedge

  • Fires after a latency threshold
  • Original keeps running; first reply wins
  • Protects against slowness
  • Needs cancellation and a load budget

How production systems expose it

gRPC configures a per-method hedgingPolicy with maxAttempts (clamped to 5 by default), hedgingDelay and nonFatalStatusCodes. The first RPC goes out immediately, another after each delay, and a non-fatal error fires the next hedge at once; the call deadline covers the whole chain, and server pushback stops further hedges (gRPC docs). Envoy sets hedge_on_per_try_timeout so that hitting the per-try timeout issues a retry without resetting the original, racing both upstreams; it requires a retry policy with a retry limit (Envoy route API). The Cassandra Java driver's speculative execution policy is off by default; the constant policy launches up to max-executions attempts spaced by a fixed delay, and since Cassandra cannot cancel in-flight requests, “cancel” just means discarding late responses.

Real-world use cases

Web search
Queries fan out to thousands of index shards; hedging and tied requests keep the root's tail close to a single leaf's.
Distributed storage
BigTable reads and Google's cluster file system use hedged and tied reads to dodge disks busy with compaction or batch jobs.
Service meshes
Envoy-based meshes hedge idempotent HTTP calls on per-try timeout without changing application code.
NoSQL clients
Cassandra drivers speculatively query another replica when a node stalls on a long GC pause.

Design checklist

Measure per-request-class latency percentiles and set the hedge delay near p95, not a fixed guess. Cap attempts and track the extra-load ratio as a first-class metric. Make cancellation real end to end, and tag hedges as lower priority where the server supports it. Restrict hedging to idempotent operations, and back it with circuit breakers and load shedding so that a cluster-wide slowdown does not turn hedges into a self-inflicted surge.
