The Maple Tree: Range B-Trees for Linux VMAs

One RCU-safe range B-tree replaced three structures that every mmap, page fault and /proc/maps walk used to touch.

October 9, 2026 · 5 min read

Summary

Every process address space is a set of virtual memory areas (vm_area_struct): anonymous heaps, file mappings, stacks, libraries. Until Linux 6.1 those VMAs lived in three places at once — an augmented red-black tree keyed on vm_start, a doubly-linked list for sequential walks, and a per-task vmacache that tried to make the common lookup cheap. Liam Howlett and Matthew Wilcox replaced all three with the maple tree: an RCU-safe, range-keyed B-tree whose 256-byte nodes pack up to 16 leaf slots, track the largest free gap for mmap(), and let readers walk under rcu_read_lock() without taking mmap_lock (LWN, kernel docs).

Why it exists: rbtrees do not store ranges natively, rotations make them hostile to RCU, and the linked list forced a cache miss per VMA. Large threaded workloads spent their time fighting over mmap_lock. The maple tree was built so that structure can eventually stop being the bottleneck.

What got replaced

Before 6.1, mm_struct held mm_rb (the rbtree) and mmap (the head of the VMA list). Each vm_area_struct carried an embedded rb_node plus vm_next/vm_prev — roughly forty bytes of indexing overhead per mapping, and every insert or delete had to update both structures under the write side of what is now called mmap_lock (Kernel Internals). Sequential scans for /proc/PID/maps, mprotect and friends chased pointers across slab objects with no hardware prefetch help. Gap search for a new mapping walked the tree or list looking for a hole large enough. The vmacache papered over hot lookups but was another structure to invalidate.

Oracle's Howlett described the design goals plainly: store non-overlapping ranges, track gaps, stay RCU-safe, and offer a simple API so other subsystems stop reinventing interval trees for non-overlapping data (Oracle blog). The merged series landed in 6.1 and deleted the VMA rbtree, linked list and vmacache in one go (patch cover letter).

From three structures to one range B-tree

How a maple node works

A maple tree is a B-tree variant for non-overlapping ranges of unsigned long keys. On 64-bit, every node is 256 bytes and 256-byte aligned, so the low bits of a node pointer encode type metadata without an extra load (Kernel Internals). Leaf maple_range_64 nodes hold up to 15 pivots and 16 slots; each pivot is the inclusive upper bound of the range in that slot. Allocation trees (used for VMAs) use maple_arange_64 nodes with a branching factor of 10 and an extra gap[] array that stores the largest contiguous NULL hole under each child — so mas_empty_area() can skip whole subtrees when searching for a free region of a given size.

mm_struct.mm_mt is created with MM_MT_FLAGS: MT_FLAGS_ALLOC_RANGE (gap tracking), MT_FLAGS_USE_RCU (deferred free via call_rcu), and MT_FLAGS_LOCK_EXTERN (mutations serialize on mmap_lock, not the tree's internal spinlock). The key for a VMA is [vm_start, vm_end - 1]; the value is the vm_area_struct *.

Leaf node: pivots, slots and tracked gaps

Lookups, iteration and allocation

find_vma() is now a thin wrapper around mt_find(&mm->mm_mt, &index, ULONG_MAX): start at the address and return the first range that covers or follows it. Writers and complex walks use a struct ma_state cursor (MA_STATE / VMA_ITERATOR) that remembers the current node and offset so mas_next() / mas_find() behave like a linked list without restarting from the root — the high branching factor amortizes the cost and keeps neighbors in the same cache line (maple_tree.rst). Inserts go through vma_iter_store_gfp(), which sets [vm_start, vm_end - 1] on the cursor and calls mas_store_gfp().

RCU and the path off mmap_lock

When MT_FLAGS_USE_RCU is set, a store that rewrites a node allocates a fresh node, swings the parent pointer, and schedules the old node with call_rcu(). Readers that already hold a pointer stay safe for one grace period. That is the foundation of the per-VMA lock fast path: lock_vma_under_rcu() takes rcu_read_lock(), runs mas_walk(), and tries a VMA read lock without ever taking mmap_lock (Kernel Internals). Process teardown and bulk dup_mmap() temporarily clear RCU mode so mass frees are not deferred, then re-enable it.

rbtree + list + cache

  • Embedded nodes: load a whole VMA to compare keys
  • Rotations touch many nodes; hard to make RCU-safe
  • Gap search often O(n); list walk is pointer-chasing
  • ~40 B indexing overhead per VMA
  • Readers needed mmap_lock (or fragile cache)

Maple tree

  • External 256 B nodes; up to 16 entries per leaf
  • Copy-on-write nodes + call_rcu for lockless reads
  • Gap metadata → O(log n) empty-area search
  • Amortized ~16 B indexing per VMA
  • RCU walk enables per-VMA lock fast path
War story — StackRot (CVE-2023-3269): early 6.1–6.4 kernels let stack expansion modify the maple tree while holding only the mmap read lock. Growing a stack until it abutted the next VMA deleted a gap and replaced a node; the old node was RCU-freed while another thread walking under the read lock still held a pointer — a use-after-free that escalated privileges. The fix backported proper RCU node replacement so tree mutations under that path stay safe (oss-security). Complexity bought scalability; it also demanded careful locking discipline.

Real-world use cases

Page faults at scale
find_vma and the RCU walk feed every fault path. Shorter trees and lockless lookups cut contention on multi-threaded servers with huge working sets.
mmap address selection
mas_empty_area / mas_empty_area_rev use gap metadata so loading libraries or anonymous mappings does not scan the whole address space.
/proc/PID/maps
Iteration uses for_each_vma over mm_mt; one node load yields many VMA pointers instead of one cache miss per list hop.
Fork and exec
__mt_dup bulk-copies the parent tree; exit_mmap destroys it with __mt_destroy after clearing RCU mode for teardown.
Per-VMA locks
Later work builds fine-grained VMA locking on top of RCU maple walks so unrelated mappings do not serialize on one rwsem.
Generic kernel ranges
The normal mtree_* API is reusable anywhere non-overlapping ranges need RCU-friendly storage — not only VMAs.

Design takeaways

When one lock protects a hot path, ask whether the data structure itself forces the lock. Embedding index nodes inside payload objects looks cheap until every tree walk pulls three cache lines you did not need. Separating the index into dense, cache-aligned B-tree nodes, encoding ranges and gaps in the same layout, and freeing replaced nodes under RCU turns “everyone takes mmap_lock” into “most readers never see the writers.” The maple tree did not remove mmap_lock on day one — that was always the long-term goal — but it made the removal possible, and it removed three parallel structures that had outlived their excuses.
