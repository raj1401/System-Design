Seqlocks: seqcount_t, seqlock_t, and Latch Counters in the Linux Kernel

Lockless readers, writer-serialized updates, and NMI-safe dual-copy latches

September 27, 2026 · 5 min read

Summary

A sequence counter is a reader-writer consistency mechanism with lockless readers and no writer starvation. Readers copy a small data set inside a retry loop; writers bump a sequence number before and after the update so an odd value means “write in progress” and a changed even value means “retry.” The kernel documents this in Sequence counters and sequential locks: use it for data that is rarely written (classic example: system time) when the reader wants a consistent snapshot and is willing to retry if that snapshot changes.

seqcount_t is the raw counter — you serialize writers yourself. seqlock_t wraps a seqcount plus an embedded spinlock so write sections are automatically serialized and non-preemptible. Neither may protect data that contains pointers a reader might follow: the writer can invalidate a pointer after the reader has already loaded it. For NMI (or other contexts that can interrupt a writer), seqcount_latch_t keeps two copies and flips readers between them via the counter’s LSB — formalized in the 5.10 era as covered by LWN’s seqcount latch article.

Deeper Dive

How the retry loop works

Writers call write_seqcount_begin() (sequence becomes odd) then write_seqcount_end() (even again), with write barriers so counter updates order against the payload. Readers do:

do { seq = read_seqcount_begin(&s); /* copy fields */ } while (read_seqcount_retry(&s, seq));

read_seqcount_begin waits while the counter is odd (a write is live), then returns the even value. After copying, read_seqcount_retry re-reads the counter; any change means the copy may be torn and the loop repeats. Consistency means: start even, end equal to start, and the data must be copied out inside the critical section — not used via dangling references afterward.

Writer bumps sequence; reader retries on mismatch

seqcount_t vs seqlock_t

seqcount_t does not protect against multiple writers. You must hold an external lock (spinlock, mutex, …) around write_seqcount_begin/end, and keep the write section non-preemptible. If readers can run from hardirq or softirq, the write path must disable IRQs or BHs accordingly. Variants like seqcount_spinlock_t / seqcount_mutex_t associate the lock at init so lockdep can check that write sections are properly serialized (zero overhead when lockdep is off).

seqlock_t embeds a seqcount plus a spinlock. write_seqlock() / write_sequnlock() take that lock and bump the sequence; use _bh / _irq / _irqsave variants when readers (or other writers) may run from softirq or hardirq. On the read side the docs list three styles: (1) normal lockless read_seqbegin / read_seqretry; (2) exclusive locking readers via read_seqlock_excl (only one locking reader, unlike rwlock_t); (3) read_seqbegin_or_lock — try lockless first, then fall back to a locking reader to avoid starvation under a write spike.

Writer must not be interrupted by its own readers: If a write section is preempted or interrupted by a reader of the same seqcount, that reader can spin for a full tick on the odd counter — and an RT reader can livelock forever. That is why write paths disable preemption (and often IRQs/BHs), or why you switch to a latch when NMI readers cannot be masked.

The no-pointers rule (vs RCU)

Kernel documentation is explicit: this mechanism cannot be used if the protected data contains pointers, because the writer can invalidate a pointer the reader is following. Seqlocks are for small, fixed-size payloads (timestamps, counters, a handful of integers) that readers copy by value. For pointer-heavy or dynamically allocated structures — lists, trees, tables that grow — use RCU: publish a new version, keep the old one alive until a grace period, and let readers dereference safely. Seqlock and RCU are complementary, not substitutes.

seqcount_latch: two copies, LSB selects the live set

seqcount_latch_t

A latch is multiversion concurrency control: the even/odd value of the embedded counter selects which of two data copies is live. The writer updates the inactive copy, then redirects readers with write_seqcount_latch*, then updates the other copy. Readers use read_seqcount_latch, take idx = seq & 0x01, query data[idx], and retry with read_seqcount_latch_retry. Because a stable copy always exists, a reader that interrupts its own writer does not deadlock spinning on an odd counter — critical when the read path can run from NMI. Jonathan Corbet’s LWN piece notes Mathieu Desnoyers introduced the technique in 2014; Ahmed Darwish formalized seqcount_latch_t for 5.10. Situations that truly need a latch remain rare; timekeeping and sched_clock are the textbook cases.

Seqlock / seqcount

  • Lockless reads; writers never wait
  • Small fixed data; copy by value
  • No pointers in the payload
  • Write must not be interrupted by readers

RCU / rwlock

  • RCU: pointer publish + grace period
  • rwlock: shared readers, exclusive writers
  • Safe for dynamic / pointer structures
  • Writers may wait for readers (rwlock)

Real-World Use Cases

Timekeeping
System time and clocksource math are classic seqcount/latch workloads: updated on ticks, read constantly, must stay consistent without locking every ktime_get.
jiffies_64 (32-bit)
get_jiffies_64() uses jiffies_lock (seqlock_t) so a 64-bit counter can be read safely where a single load is not atomic.
sched_clock / NMI
seqcount_latch_t in timekeeping paths lets NMI (or interrupt) readers observe a stable copy even if they interrupt an in-progress update.
Write-spike readers
read_seqbegin_or_lock starts lockless, then falls back to an exclusive locking reader so retry storms under heavy writers do not starve the reader.
When to pick what: Seqlock for small, rarely written, non-pointer data with many readers. Latch when those readers can interrupt the writer (NMI). RCU when the structure is pointer-based or dynamically allocated. Plain rwlock_t when you need shared readers that must not tear and you can afford writers waiting.
