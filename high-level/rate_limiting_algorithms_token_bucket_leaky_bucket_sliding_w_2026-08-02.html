Rate Limiting Algorithms: Token Bucket, Leaky Bucket & Sliding Windows

How distributed systems decide, in microseconds, whether to say "yes" or "429" to every incoming request.

August 2, 2026 · 5 min read

What rate limiting actually solves

Rate limiting is a foundational control in API security, abuse prevention, and distributed systems reliability, determining how systems allocate finite capacity across users, services, and regions. Every backend has a breaking point — a database connection pool, a CPU budget, a third-party quota — and rate limiting is the mechanism that keeps one noisy client, one retry storm, or one scraper from consuming it all.

Without rate limiting, a single client making excessive requests can impact service availability for other users, so throttling ensures equitable resource distribution across all clients. When a limit is exceeded, the server typically responds with the HTTP status defined for exactly this purpose: RFC 6585 defines the 429 Too Many Requests status code , often paired with a Retry-After header telling the client when to come back.

Why this matters: The rate limiter is one of the few components that sits in the hot path of literally every request, at every scale — a bug here either lets an attacker through or throttles legitimate paying customers. Choosing the wrong algorithm is invisible until the day traffic spikes.

The five canonical algorithms

Five algorithms dominate production practice and are not interchangeable — each trades memory, burst tolerance, and accuracy differently, a set codified for a generation of engineers by Alex Xu's System Design Interview as the canonical reference family of Fixed Window Counter, Sliding Window Log, Sliding Window Counter, Token Bucket, and Leaky Bucket.

Fixed window counter

A fixed-window counter counts the number of requests received within a fixed time window, such as one minute, and once the maximum is reached, additional requests are rejected until the next window begins — an algorithm that is easy to implement and effective against DDoS attacks but may limit legitimate users. Its well-known flaw: the naive count-and-reset approach has a real flaw, since nothing stops all N requests from landing in the first 10 milliseconds of a window, followed by silence, followed by another N crammed into the last 10ms of the next window.

Sliding window log

The sliding window log fixes the boundary-burst problem by storing timestamps of requests and calculating the exact number inside the time window — the downside being that every request needs a timestamp stored somewhere, which at scale becomes a lot of memory and cleanup work.

Sliding window counter

Rather than storing every timestamp, a sliding window counter approximates the log using just two adjacent fixed-window counts. It counts the number of allowed requests in the previous fixed window and the current fixed window, then weights the previous window's allowed requests proportional to that window's overlap with a floating window ending at the current time, adding the weighted requests to the unweighted current-window requests. This is exactly the approach behind large-scale edge deployments: most real-world sliding window rate limiters, such as those provided by Upstash or Cloudflare, use this approximation, often called a floating window, keeping all the same pros while removing the resource-intensive cost. It performs remarkably well in practice — an analysis on 400 million requests from 270,000 distinct sources showed 0.003% of requests wrongly allowed or rate limited, with an average difference of 6% between the real rate and the approximate rate.

Token bucket

Each user's bucket is initialized with a capacity of tokens; every time the user makes a request, the tokens are refilled by the refill rate multiplied by the time elapsed since the stored last-refill timestamp, but the total is always capped at the bucket's capacity. Requests consume tokens, so if none remain, requests are rejected — but if a client is idle, tokens accumulate up to the bucket's maximum capacity, allowing controlled bursts without violating the long-term average limit.

Leaky bucket

Leaky bucket flips the model: it enforces a constant output rate, where incoming requests enter a queue that drains at a steady pace, and if the queue is full, new requests are rejected. Where token bucket rewards a well-behaved idle client with the ability to burst, leaky bucket's refusal to ever spike becomes the right guarantee when something fragile sits directly behind the limiter — a legacy service or a database with hard connection limits.

Making it work across many machines

A single-process counter is trivial; the hard part is that modern APIs are served by hundreds of stateless nodes behind a load balancer. Rate limiting protects distributed systems from abuse, prevents resource exhaustion, and rations a finite backend across many callers , which means the counter itself has to become a distributed object.

Most production systems combine a sliding window counter or token bucket with Redis-backed shared state and IETF RateLimit headers. This is precisely how Cloudflare evolved its own limiter: after outgrowing the per-node limit_req_zone module bundled with NGINX, the team worked out how to implement a good counting system using only a few memcache primitives without much contention, though it still required a memcache query on every request to get the current rate. Stripe takes a similar centralized-store approach: it runs a centralized bucket host where tokens are taken on each request and slowly dripped back in — every Stripe user gets a bucket, and every request removes a token from it, implemented using Redis.

Telling clients before they get throttled

Rather than making clients guess, servers can advertise their budget proactively. A standard set of HTTP header fields lets servers communicate rate-limit policies and current quota: RateLimit-Policy describes the quota policy a client's requests will consume, and RateLimit describes the quota currently available under that policy. This IETF draft standardizes what vendors like GitHub and Stripe have long done with bespoke X-RateLimit-* headers. Clients should also add random jitter to retries — if all rate-limited clients retry at exactly the Retry-After time, they all hit the server simultaneously.

Choosing between them

Token Bucket

  • Allows controlled bursts from banked, unused capacity
  • Best default for public, client-facing APIs
  • Runs behind more APIs than any other algorithm, including AWS, Stripe, and GitHub
  • Two numbers of state: token count + last-refill timestamp

Leaky Bucket

  • Forces a strictly constant output rate, no matter the input shape
  • Ideal for shaping traffic into a fragile downstream dependency
  • No memory of idle time — never rewards well-behaved bursts
  • Classic use: traffic shaping / QoS in networking gear

Real-world use cases

Cloudflare Edge
Rate limiting is applied at the edge of the network so origin servers aren't bothered by excessive traffic or layer-7 attacks , using an approximated sliding window across thousands of edge nodes.
Stripe API
Every Stripe user has a Redis-backed token bucket; every request removes a token from that user's bucket , capping both read and write request rates per API key.
GitHub REST API
GitHub is among the APIs whose rate limiter runs on the token bucket algorithm , tiering unauthenticated vs. authenticated request budgets per hour.
Linux Traffic Control
The Linux HTB queuing discipline replaces average-idle bandwidth calculations with token-bucket filters, giving more direct control of burst sizes for shaping outbound network traffic.
AI / LLM APIs
Providers rate-limit on both request count and token throughput per minute, tiered by plan, reflecting that compute cost — not just request count — is the scarce resource.
Load Shedding
When traffic can be split into priority buckets, a load shedder adds backpressure so internal systems can recover , dropping low-priority traffic before critical paths fail.

Design checklist

Before picking an algorithm, be explicit about three independent choices: rate limiting decomposes into three largely independent decisions — algorithm, state location, and response payload. Get the algorithm right for your burst tolerance, decide whether counters live per-instance or in shared storage like Redis, and make sure clients get actionable 429 responses with rate-limit headers and jittered retry guidance rather than a silent drop.
