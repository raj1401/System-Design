XArray: Sparse Arrays Replacing the Radix Tree in Linux

Same 64-way tree underneath, a radically better contract on top: load and store, locking included, marks that prune whole subtrees.

October 15, 2026 · 5 min read

Summary

The XArray is an abstract data type that "behaves like a very large array of pointers", indexed by an unsigned long. Unlike a hash it can step to the next or previous entry cache-efficiently; unlike a resizable array it never copies data to grow; and lookups run under RCU without taking a lock. Its most important user is the page cache: every struct address_space keeps its cached folios in an XArray called i_pages (kernel docs, fs.h).

Matthew Wilcox's insight, presented at linux.conf.au 2018, was that the kernel's radix tree was a fine data structure with a bad API. He kept the tree, changed the metaphor from tree to array, moved locking inside, deleted the preload dance, made GFP flags explicit, and split the interface into a Normal and an Advanced API (LWN, LCA slides). The implementation plus the page-cache conversion was merged for Linux 4.20 (KernelNewbies, merge commit).

The mindset shift: there is no "insert" or "delete". Every index always holds a value; an empty array simply has NULL at every index. Wilcox pushed back on LWN's own write-up for saying a store returns the previous value "if any", calling that "the kind of radix tree thinking that I'm trying to eradicate" (LWN comment).

Why the radix tree API had to go

With the old interface, callers did their own locking, so nobody (not even slab defragmentation code) could know which lock protected a given tree. Inserts that might allocate under a spinlock needed radix_tree_preload() beforehand; Wilcox counted 42 preload call sites and replaced them with seven xa_reserve() calls (LWN comment). Users also handled RCU-protected slot pointers directly, re-walked the tree from the root for every step, and juggled "exceptional entries". The XArray merge message summarises the fix: "locking as part of the API, specifying GFP flags at allocation time, eliminating preloading, less re-walking the tree, more efficient iterations and not exposing RCU-protected pointers to its users" (merge commit).

Crucially, the conversion kept the radix-tree and XArray structures identical, so "a radix tree walk and an XArray walk will touch the same number of cachelines" and the page cache could be converted one function at a time (v11 cover letter). Today radix-tree.h literally does #define radix_tree_root xarray, so the remaining radix-tree and IDR users run on XArray nodes (radix-tree.h).

Under the hood: nodes, entries and the lock

The anchor is tiny: struct xarray holds just xa_lock (a spinlock), xa_flags and an RCU-protected xa_head. Interior struct xa_nodes have XA_CHUNK_SIZE slots, where XA_CHUNK_SHIFT is 6 (64 slots) normally and 4 on CONFIG_BASE_SMALL builds. Each node records its shift (index bits remaining below it), its offset in the parent, counts of non-NULL and value entries, a parent pointer, and a marks[3][] bitmap with one bit per slot per mark (xarray.h). Each level consumes 6 index bits, so a 1 GiB file of 4 KiB pages (218 indices) needs only three levels, and the full 64-bit index space at most eleven.

The bottom two bits of every slot say what it holds: 00 a normal pointer (hence the 4-byte alignment rule), x1 a value entry or tagged pointer (xa_mk_value() stores integers up to LONG_MAX), and 10 an internal entry. Internal entries are mostly pointers to child nodes, plus sibling entries (0–62), a retry entry (256) and a zero entry (257); errors are encoded in the negative internal range and only ever returned, never stored (xarray.h).

Locking: xa_lock plus RCU

With the Normal API you never take a lock yourself. xa_load(), xa_find() and the xa_for_each*() iterators take the RCU read lock; xa_store(), xa_erase(), xa_cmpxchg(), xa_alloc() and the mark setters take xa_lock internally. Variants such as xa_store_bh()/xa_store_irq(), and flags XA_FLAGS_LOCK_BH/XA_FLAGS_LOCK_IRQ, handle arrays modified from softirq or hardirq context. Double-underscore functions like __xa_store() expect the lock to be held already, which lets callers extend the critical section to cover their own counters (kernel docs). When a node is removed, its slots are replaced with retry entries so concurrent RCU walkers restart from the head instead of reading freed memory (xas_free_nodes).

Memory allocation is the subtle part. A store first tries GFP_NOWAIT while holding the spinlock; if that fails, the xa_state records -ENOMEM, the caller drops the lock, and xas_nomem() allocates with the caller's real GFP flags and caches one node in the state for the retry, guaranteeing forward progress (kernel docs).

The Advanced API: xa_state as a cursor

The Normal API is built entirely on the Advanced API, which is GPL-only and does no locking for you. Its core is struct xa_state, declared on the stack with XA_STATE(xas, xa, index): it remembers the array, the index, the current node and offset, a spare allocated node, and an optional update callback. Because the cursor stays at the leaf, you can compose xas_load(), xas_store(), xas_set_mark(), xas_next() and xas_find() without re-walking from the root, and errors are sticky, so you only check xas_error() at the end. If you must drop the lock mid-iteration, xas_pause() makes the state safe to resume. The docs note that xa_for_each() is O(n log n) while xas_for_each() is O(n) (kernel docs).

The page cache's lockless lookup, filemap_get_entry(), shows the pattern. Under rcu_read_lock() it calls xas_load(), restarts on xas_retry(), returns value entries (shadow entries of evicted pages, or shmem swap entries) as-is, takes a speculative reference with folio_try_get(), and then calls xas_reload() to confirm the slot still points at the same folio, retrying if not (mm/filemap.c). No xa_lock is touched on the read-hit path.

Search marks: pruning whole subtrees

Each entry carries three independent mark bits (XA_MARK_0..2). xas_set_mark() sets the bit on the entry and walks up setting it on every ancestor; clearing walks back up clearing ancestors that no longer have any marked child. That aggregation lets xa_for_each_marked() and xa_marked() skip any subtree whose parent bit is clear. The docs are explicit that you cannot efficiently iterate unmarked entries (kernel docs). The page cache maps the three marks to PAGECACHE_TAG_DIRTY, PAGECACHE_TAG_WRITEBACK and PAGECACHE_TAG_TOWRITE, so writeback visits only dirty folios in a file with millions of clean ones (fs.h). Allocating arrays (XA_FLAGS_ALLOC) reserve mark 0 as XA_FREE_MARK to find free IDs for xa_alloc().

Multi-index entries and large folios

An unusual XArray feature is an entry that occupies a naturally aligned power-of-two range of indices: store to any index and all of them change; mark any index and the whole range is marked. You create one with XA_STATE_ORDER() or xas_set_order() followed by xas_store(). Internally, an order-n entry lives at the node whose shift is n - (n % 6) and spans one canonical slot plus 2n % 6 - 1 sibling entries pointing back at it (xarray.h). A 2 MiB folio (order 9) therefore takes eight slots in a shift-6 node instead of 512 leaf slots across eight leaf nodes; the docs note that tying 512 entries together "will save over 4kB" (kernel docs).

This is exactly what the folio-based page cache needs: __filemap_add_folio() stores each folio with XA_STATE_ORDER(xas, &mapping->i_pages, index, folio_order(folio)) (mm/filemap.c). Splitting a large folio uses xas_split_alloc() + xas_split() for a uniform split, or xas_try_split() to split non-uniformly around one index, which for an order-9 entry needs one new node instead of eight (kernel docs).

XArray

  • Index to pointer; fixed 64-way radix nodes
  • Best with densely clustered indices (file offsets, IDs)
  • Ranges only as aligned power-of-two multi-index entries
  • RCU reads always; writers on internal xa_lock
  • Three aggregated search marks per entry
  • Flagship user: page cache (i_pages)

Maple tree

  • Arbitrary non-overlapping ranges in a B-tree
  • Pivots in ~256-byte nodes; handles sparse ranges well
  • Optional gap tracking to find free ranges
  • RCU mode opt-in; lock may be external (mmap_lock)
  • Erase may allocate; preallocation API for atomic paths
  • Flagship user: process VMAs (mm_mt)

The two are siblings, not rivals: both were shaped by Wilcox, share the RCU-plus-spinlock Normal API style and even the xa_mk_value() convention, but the maple tree is a range B-tree optimised for VMAs while the XArray is a radix array optimised for clustered integer indices (maple tree docs). Hashing keys into an XArray is explicitly discouraged; scattered indices waste nodes.

Real-world use cases

Page cache
address_space->i_pages maps file offsets to folios, shadow entries and shmem swap entries; marks drive dirty and writeback tracking.
Workingset shadows
xas_set_update() callbacks let the workingset code track nodes holding only shadow entries so they can be reclaimed.
ID allocation
xa_alloc() / xa_alloc_cyclic() replace the IDR, which kernel docs now mark deprecated; struct ida wraps an XArray.
Large folios
Multi-index entries let one slot range represent a 2 MiB or larger folio, with split helpers for truncation and reclaim.
Device memory
mm/memremap.c keeps ZONE_DEVICE dev_pagemap lookups in a global DEFINE_XARRAY(pgmap_array).
Legacy radix trees
radix_tree_root is now a macro for struct xarray, so every remaining radix-tree user runs on XArray nodes.
Design lesson: the XArray changed almost nothing in memory and everything in the contract. By owning the lock, the allocation retry and the RCU publication rules, the data structure became safe to use by default, and those same guarantees are what made lockless page-cache lookups and multi-index large folios practical to build on top.
