The eBPF Verifier: How Linux Proves Untrusted Code Safe

Abstract interpretation, register types, tnums and state pruning, all inside the kernel at program load time.

November 11, 2026 · 5 min read

Summary

eBPF lets you load small programs into a running Linux kernel and attach them to sockets, tracepoints, XDP hooks, schedulers and more. That only works because every program must first pass the verifier, a static analyzer in kernel/bpf/verifier.c that runs at bpf(BPF_PROG_LOAD) time. It proves, before a single instruction executes, that the program terminates, never reads uninitialized registers or stack, only touches memory it is allowed to touch with in-bounds and aligned accesses, releases every reference it acquires, and calls helpers with correctly typed arguments. If it cannot prove all of that, the load fails with a verifier log instead of a kernel crash.[1]

Key idea: the verifier is not a sandbox at runtime. It is a symbolic executor that walks every feasible path once, at load time, so that the JIT-compiled program can then run at native speed with almost no runtime checks.

How it works

Pass 1: control-flow sanity

The first pass builds the control-flow graph and rejects malformed programs: jumps out of range, unreachable instructions (unreachable insn 1) and, historically, any back-edge at all.[1] Since Linux 5.3, bounded loops are allowed, but only because pass 2 can prove they terminate.[3]

Pass 2: symbolic execution over abstract register state

Starting at instruction 0, the verifier simulates every instruction on an abstract machine state: eleven registers plus a 512-byte stack, each described by a struct bpf_reg_state. Each register has a type: NOT_INIT, SCALAR_VALUE, or a pointer type such as PTR_TO_CTX, PTR_TO_STACK, PTR_TO_MAP_VALUE, PTR_TO_MAP_VALUE_OR_NULL, PTR_TO_PACKET and PTR_TO_PACKET_END.[1] R1 starts as PTR_TO_CTX; R10 is the read-only frame pointer. After a helper call R1-R5 become unreadable and R0 takes the helper's declared return type, while callee-saved R6-R9 keep their state.

Types drive the rules. Adding two pointers yields a scalar that can never be dereferenced. A map lookup returns PTR_TO_MAP_VALUE_OR_NULL, and storing through it fails with R0 invalid mem access 'map_value_or_null' until a if r0 == 0 branch refines it to PTR_TO_MAP_VALUE on the non-null side. Every copy of that pointer shares an id, so one null check upgrades them all. Socket lookups return reference-counted pointers; exit with one still held and you get Unreleased reference id=1.[1]

Verifier pipeline at BPF_PROG_LOAD

Value tracking: ranges plus tnums

For scalars and pointer offsets the verifier keeps signed and unsigned min/max bounds (64- and 32-bit) and a tnum (tristate number): a value/mask pair where mask bits are unknown. A byte loaded from memory is (0x0; 0xff); OR with 0x40 gives (0x40; 0xbf). Conditional branches refine bounds: on the true side of r > 8, umin becomes 9.[1] This is classic abstract interpretation, and its soundness is subtle enough that academics have formally specified the tnum domain, proved its add/sub operators sound and optimal, and upstreamed a faster sound multiplication.[5] The Agni tool automatically checks range-analysis soundness from kernel source; it found 27 previously unknown bugs across kernels 4.14 to 5.19.[6][7]

Direct packet access

Packet pointers carry a safe range. After r5 = r3 + 14; if r5 > r4 goto err (with r4 = data_end), the fall-through state records R3=pkt(off=0,r=14), so loads from bytes 0-13 are allowed. That is why XDP code is full of if (data + sizeof(*eth) > data_end) return checks: they are proofs for the verifier, not just defensive style.[1]

Taming path explosion: pruning and liveness

Naively, every branch doubles the work. The verifier instead keeps a cache of previously verified states per instruction (checkpoints). When it reaches an instruction in a state that is a subset of one already proven safe (same types, ranges at least as tight, packet range at least as long), it prunes the path (regsafe(), states_equal()). Liveness tracking makes this effective: registers and stack slots never read later are dropped from the comparison, so states differing only in dead values collapse together.[1] Heuristics in the kernel avoid adding checkpoints too often, evict states that keep missing, and detect identical states across loop iterations as an infinite loop.[8]

Bounded loops (5.3+)

  • Verifier simulates every iteration
  • Same state twice means reject: infinite loop
  • 100 iterations x 20 insns eats thousands of budget
  • Clamp loop bounds derived from packet fields

bpf_loop / iterators / may_goto

  • Runtime enforces termination
  • Body verified roughly once
  • Same state twice means converge and prune
  • bpf_loop allows up to 1<<23 iterations

Limits keep the verifier itself bounded: until 5.2 programs were capped at 4096 instructions with a 128k complexity limit; since then the processed-instruction budget is 1 million.[2] At BPF Conference 2025, the BPF maintainers noted programs now hit that limit often, mainly from always_inline and #pragma unroll, and recommended global functions, iterators and may_goto/can_loop instead.[4]

After acceptance: Spectre and JIT hardening

Proving architectural safety is not enough on speculative CPUs. For unprivileged loaders, sanitize_ptr_alu() records a limit for each variable pointer offset; a fixup pass then emits masking instructions, and the verifier explores a simulated speculative path to check that truncated offsets stay in bounds.[9][10] Separately, bpf_jit_harden enables constant blinding, rewriting each immediate K as (RND ^ K) ^ RND so attacker-chosen constants never appear verbatim in executable memory (JIT spraying).[11] Research such as BeeBox continues to harden BPF against transient-execution attacks.[12]

Practical tip: when a load fails, read the log from the bottom up. The last lines show the failing instruction and the abstract state, e.g. R0 invalid mem access 'map_value_or_null' or invalid stack off=8 size=8, which usually point to a missing null check, bounds check or stack initialization.

Real-world use cases

XDP load balancing
Meta's Katran runs an L4 load balancer as XDP programs; every packet access is guarded by data_end checks the verifier relies on.[13]
Kubernetes networking
Cilium implements service routing and network policy in eBPF programs that must pass the verifier on each node's kernel.[14]
Production tracing
bpftrace compiles one-liners to BPF; the verifier is why it is safe to attach to live kernel functions on production hosts.[15]
Unprivileged lockdown
Because verifier bugs are exploitable, the kernel.unprivileged_bpf_disabled sysctl lets admins restrict loading to privileged users.[16]
