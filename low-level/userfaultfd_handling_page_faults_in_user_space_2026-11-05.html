userfaultfd: Handling Page Faults in User Space

A file descriptor that turns the kernel's most private event, the page fault, into a message your own thread can read and answer.

November 5, 2026 · 5 min read

Summary

Normally a page fault is the kernel's business: a thread touches an unmapped address, the CPU traps, and the kernel finds or allocates a page before the thread ever notices. userfaultfd, merged in Linux 4.3 [1], lets user space take over that decision for chosen ranges of memory. A process registers a virtual range with a userfaultfd; any fault inside it blocks the faulting thread and delivers a message on the descriptor. A handler thread reads the fault address, decides what the page should contain, and resolves it with an ioctl such as UFFDIO_COPY, which atomically installs the page and wakes the faulter [2][3].

That makes on-demand paging from user land possible: memory can live on another machine, in a snapshot file, or in a half-compacted heap, and be materialized only when touched.

Why not mprotect plus SIGSEGV? The classic trick works, but every protection change splits or merges VMAs and takes mmap_lock for writing. The kernel docs note that userfaultfd never takes mmap_lock for writing at runtime and avoids heavyweight VMA structures, which matters when you track faults at page granularity across terabytes of address space [2].

Deeper Dive: How It Works

1. Create and negotiate

A descriptor comes from the userfaultfd(2) syscall or, on newer kernels, from opening /dev/userfaultfd and issuing USERFAULTFD_IOC_NEW. Before anything else the program must call UFFDIO_API with UFFD_API and the feature bits it wants; the kernel answers with bitmasks of supported features and ioctls [2][4]. Features include extra memory types (hugetlbfs, shmem), minor faults, write-protect, UFFD_FEATURE_MOVE, and non-cooperative events such as fork and mremap notifications.

2. Register a range and a mode

UFFDIO_REGISTER attaches a range with a mode that says which faults to trap [2]:

Fault-on-absence modes

  • MODE_MISSING: no page exists yet; resolve with UFFDIO_COPY or UFFDIO_ZEROPAGE
  • MODE_MINOR: the page is in the page cache but not mapped; optionally edit it, then UFFDIO_CONTINUE

Fault-on-access modes

  • MODE_WP: write-protect tracking via UFFDIO_WRITEPROTECT, a faster mprotect substitute
  • UFFD_FEATURE_WP_ASYNC: no message, the kernel clears protection itself and dirty state is read from /proc/pid/pagemap

3. The fault round trip

When a thread faults in a registered range, the kernel's fault path queues it on the userfaultfd context and puts it to sleep instead of allocating memory. The descriptor becomes readable (POLLIN), and a handler reading it gets a struct uffd_msg with event UFFD_EVENT_PAGEFAULT, the faulting address, and flags telling it whether the access was a write or a write-protect fault [3]. The handler fetches the right bytes from wherever they live and calls UFFDIO_COPY. That copy is atomic in a precise sense: nothing can observe a half-populated page, because readers simply keep faulting until the operation finishes [2]. By default the ioctl also wakes blocked faulters; DONTWAKE lets a handler install many pages and wake once.

A Missing-Page Fault Served From User Space

4. Cooperative vs non-cooperative

Because a userfaultfd is just a file descriptor, it can be passed over a Unix socket to a separate manager process that serves faults for programs that never knew [2]. Such a manager needs to see the target's layout changing, so it can opt into UFFD_EVENT_FORK, REMAP, REMOVE and UNMAP messages. Unlike page faults, these events are delivered asynchronously, and UFFDIO_COPY returns -ENOENT if the layout changed under an outstanding copy, so managers must order copies carefully against events.

5. The security story

A userfaultfd that also traps faults taken while the kernel copies user memory lets an attacker freeze a kernel thread at a chosen instant, widening race windows. That pattern showed up in enough exploits that Linux 5.11 added UFFD_USER_MODE_ONLY: with vm.unprivileged_userfaultfd=0, an unprivileged caller must pass it, or hold CAP_SYS_PTRACE, to get kernel-fault handling [5]. Because CAP_SYS_PTRACE grants far more than needed, a CAP_USERFAULTFD capability was proposed [6], and the merged answer was /dev/userfaultfd, whose ordinary file permissions gate full access [2][5].

Latency budget. Every resolved fault costs a sleep, a wakeup, a context switch to the handler and an ioctl, plus whatever it takes to fetch the data. Real users prefetch aggressively and treat faults as the slow path, which is why QEMU recommends a precopy pass before switching to postcopy [2].

Real-World Use Cases

Postcopy live migration
QEMU/KVM starts the VM on the destination before memory arrives; guest faults become userfaults, the page is requested from the source and installed with UFFDIO_COPY, with no KVM kernel changes needed [2][7].
MicroVM snapshot restore
Firecracker can hand its userfaultfd and memory layout to an external handler over a Unix socket, which serves guest pages lazily from a snapshot file [8].
Lazy container migration
CRIU's lazy-pages daemon restores a process and fills its memory on demand from the source host [9].
Concurrent compacting GC
Android ART's Concurrent Mark-Compact collector uses userfaultfd so mutators touching not-yet-compacted pages get them filled on demand instead of using read barriers [10][11].

Design Takeaways

userfaultfd is a small interface with a big idea: separate noticing a fault from deciding what fills it. The kernel keeps page-table manipulation atomic and safe; user space supplies policy and data. The trade-offs are latency on every served fault, careful synchronization for non-cooperative managers, and a privilege model that has tightened over time.
