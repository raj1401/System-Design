Two-Phase Commit: Atomic Commitment, Blocking, and Paxos Commit

How a transaction that touches many machines commits everywhere or nowhere, and what happens when the coordinator dies mid-vote.

November 8, 2026 · 5 min read

Summary

When a single business operation writes to several independent stores (two database shards, a database plus a message broker, or two Paxos groups), you need atomic commitment: either every participant applies the change or none does. Two-phase commit (2PC) is the classic protocol for this. A coordinator (the transaction manager, TM) first asks every participant (each resource manager, RM) to prepare, meaning durably promise it can commit. Only if all vote yes does the coordinator record a commit decision and tell everyone to commit. Gray and Lamport note that 2PC is sometimes treated as synonymous with transaction commit itself (Gray & Lamport).

2PC is correct, but it is not fault-tolerant: if the coordinator crashes after participants have voted yes, they can be stuck holding locks until it recovers. Most of the modern story, from three-phase commit to Paxos Commit to Spanner, is about removing that single point of blocking.

Not the same as a saga. A saga gives up atomic isolation and undoes work with compensating actions. 2PC keeps real ACID atomicity across participants, at the price of holding locks during the protocol and depending on the coordinator's availability.

How the protocol works

Phase 1: prepare (voting)

After the application finishes its reads and writes, the coordinator sends PREPARE to each participant. A participant that can commit writes everything it needs (the redo data plus a prepared record) to stable storage, keeps its locks, and replies YES. Once it says yes it has given up the right to abort on its own: it must be able to commit even after a crash and restart. A participant that hits a constraint violation, deadlock, or failure replies NO and can abort immediately. PostgreSQL exposes exactly this state: after PREPARE TRANSACTION the transaction is detached from the session and "its state is fully stored on disk," so it can still be committed after a database crash (PostgreSQL docs).

Phase 2: commit or abort (decision)

If every vote is yes, the coordinator durably logs COMMIT. That log write is the commit point: the transaction is now committed, even if no participant knows yet. The coordinator then sends COMMIT to everyone, and participants apply the change, release locks, and acknowledge. If any vote is no, or a vote times out, the coordinator logs and sends ABORT. The decision must be re-sent until acknowledged, because a participant that crashed after preparing will ask on recovery.

Two-phase commit message flow (happy path)

The blocking problem

A participant that voted no, or never received PREPARE, can safely time out and abort. The dangerous window is after a participant votes yes. It is now uncertain: it cannot abort, because the coordinator may already have logged commit and told someone else, and it cannot commit, because another participant might have voted no. Gray and Lamport put it precisely: "if the TM fails right after every RM has sent a Prepared message, then the other RMs have no way of knowing whether the TM committed or aborted the transaction" (Gray & Lamport, section 3.3). Until the coordinator returns, those participants keep their locks, and anything else that wants those rows waits too.

You can see this operationally in PostgreSQL. Prepared transactions that outlive a crashed transaction manager sit in pg_prepared_xacts and in the pg_twophase directory, and the docs warn that although the prepared state is meant to be short, "external availability issues might mean transactions stay in this state for an extended interval" (PostgreSQL two-phase transactions).

Participant state machine and the uncertain window

Fixing the blocking: 3PC and Paxos Commit

Three-phase commit

Dale Skeen's 1981 paper Nonblocking Commit Protocols introduced three-phase commit (3PC), which inserts a PRE-COMMIT round between voting and committing so that no participant can be committed while another is still uncertain (3PC overview). A surviving participant can then finish the protocol on its own. The catch is the failure model: 3PC assumes fail-stop crashes, no network partitions, and failure detectors that can tell slow from dead. Gray and Lamport point out that these protocols assume two processes can never both believe they are the coordinator, an assumption that "cannot be implemented in a purely asynchronous system" (Gray & Lamport). That is why 3PC is rarely used in production.

Paxos Commit: replicate the decision

Gray and Lamport's answer is to treat each participant's vote as its own consensus problem. Paxos Commit uses 2F+1 coordinators (acceptors) and makes progress as long as F+1 of them are working. It has the same stable-storage write delay as 2PC, and in its faster variant the same message delay, at the cost of more messages. Their key observation is that classic 2PC is simply Paxos Commit with F = 0 (Microsoft Research).

Classic 2PC

  • Single coordinator, tolerates zero coordinator faults
  • Fewest messages, one forced log write per node
  • Blocks if the coordinator dies after YES votes
  • Standardised in X/Open XA

2PC over consensus

  • Coordinator and participants are replicated groups
  • A crash becomes a leader election, not a stall
  • More messages and replication latency per commit
  • Used by Spanner, CockroachDB, Kafka

Real-world use cases

Google Spanner
Transactions spanning several Paxos groups run 2PC between group leaders; transaction manager state is stored in the Paxos group, so a crashed coordinator leader is replaced rather than blocking (Spanner paper, MIT 6.824 FAQ).
Apache Kafka
Exactly-once transactions: the transaction coordinator writes PREPARE_COMMIT to its replicated transaction log, then writes commit markers to every partition involved (KIP-98).
CockroachDB
Parallel Commits adds a STAGING transaction record listing in-flight writes, cutting commit latency from two rounds of consensus to one (Cockroach Labs blog, docs).
XA / PostgreSQL
Java EE and other transaction managers coordinate heterogeneous databases and queues through the XA interface; PostgreSQL provides the participant side with PREPARE TRANSACTION and COMMIT PREPARED (XA spec, PostgreSQL).

Design takeaways

Keep the prepared window short. Locks are held from prepare until the decision arrives, so every extra round trip adds contention. Spanner notes that most transactions touch only one Paxos group and can bypass the transaction manager entirely (Spanner paper), which is a good reason to co-locate data that is written together.

Make the coordinator's log durable and replicated. Kafka's design shows the pattern: once the prepare record is durable, a new coordinator can reload it and re-drive the markers, so the client can be answered early (Kafka internals).

Monitor orphaned prepared transactions. With a standalone XA manager, alert on old rows in pg_prepared_xacts, since an orphan holds locks and blocks vacuum cleanup.

Know when not to use it. Across service or organisational boundaries, where you cannot hold another team's locks, prefer the transactional outbox, idempotent consumers, or sagas.
