High-Level System Design

Leader Election with Leases and Fencing Tokens

Picking one leader is easy. Making sure the old one can no longer do damage is the real problem.

October 12, 2026 · 5 min read

Summary

Many systems need exactly one node to do a job at a time: one scheduler assigning work, one controller reconciling state, one primary accepting writes, one cron runner firing a nightly batch. Leader election picks that node, and a lease makes the choice time-bounded: the leader holds a grant that expires unless it keeps renewing it, so if the leader crashes, someone else can take over after the lease runs out. Leases were introduced by Gray and Cheriton as a fault-tolerant way to keep caches consistent, where failures affect performance but not correctness as long as clocks behave (Gray & Cheriton, 1989).

The catch is that a lease tells the old leader when it should stop, not that it has stopped. A process frozen by a garbage-collection pause, a VM migration, or a network partition can wake up still believing it leads. The fix is a fencing token: a number that increases every time leadership is granted, carried on every write, and checked by the resource itself, which rejects any token older than the newest one it has seen (Kleppmann, 2016).

Core rule: Election decides who should act. Fencing decides whose actions are accepted. Without the second, the first is only a hint.

How it works

1. A linearizable store holds the lease

Candidates race to write a single record in a strongly consistent coordination store such as ZooKeeper, etcd, Consul, or a Kubernetes Lease object (which itself sits in etcd behind the API server). Because the store runs consensus, only one conditional write can win. In etcd, a candidate attaches its key to a lease with a TTL and campaigns with a compare-and-swap transaction that succeeds only if the key does not yet exist; the returned LeaderKey carries the key's creation revision, which can be used to guard later transactions on leadership still being held (etcd concurrency API, election.go).

2. The leader renews, followers wait

The leader heartbeats to extend its lease. Followers watch the record and only try to take over once it has gone unrenewed for the full lease duration. Kubernetes' client library exposes exactly these knobs: LeaseDuration (how long candidates wait before force-acquiring), RenewDeadline (how long the leader keeps retrying renewal before giving up), and RetryPeriod (client-go leaderelection). The Lease object stores holderIdentity, renewTime, leaseDurationSeconds, and a leaseTransitions counter (Lease v1 API).

Lease timing: leader renews well before followers may take over

3. Why leases alone are not enough

Every lease depends on time. The client-go docs say plainly that the implementation "does not guarantee that only one client is acting as a leader (a.k.a. fencing)"; it tolerates clock skew but not arbitrary differences in clock rate, which you budget for via the ratio of LeaseDuration to RenewDeadline (client-go). The etcd team makes the same point in its notes on the usage of lock and lease and ships a runnable demo of a client whose lease expires during a pause (etcd contrib/lock). Jepsen's analysis of etcd 3.4.3 found key-value operations strict serializable but concluded that "etcd locks are fundamentally unsafe" for mutual exclusion on their own (Jepsen, 2020).

The zombie leader and the fence that stops it

4. Fencing tokens close the gap

The token must come from the same atomic operation that grants leadership and must strictly increase across grants. Coordination stores give you one for free: Kleppmann suggests ZooKeeper's zxid or the znode version, and etcd exposes the leader key's creation revision (Kleppmann, etcd). Google's Chubby built the same idea in as a sequencer, an opaque string holding the lock name, mode, and generation number that downstream servers check before acting. For servers that could not check sequencers, Chubby added a fallback called lock-delay: after a holder fails, the lock cannot be re-acquired for a bounded period (at most one minute), which the paper itself calls imperfect (Burrows, OSDI 2006).

The important design shift is that the resource enforces the fence, not the client. In a SQL store that is a conditional write:

UPDATE jobs SET state = :s, fence = :token WHERE id = :id AND fence < :token

Zero rows updated means a newer leader already wrote, so the stale leader should abort and step down rather than retry. This is also why Kleppmann argues Redlock is unsuitable for correctness: it produces no monotonically increasing token to fence with (Kleppmann).

5. Avoiding the thundering herd

If every follower watches the same leader key, every follower stampedes the store the instant it disappears. ZooKeeper's recipe instead has each candidate create an EPHEMERAL_SEQUENTIAL znode; the lowest sequence number leads, and each other candidate watches only the node immediately before it, so "the removal of a node will only cause one client to wake up" (ZooKeeper Recipes). Ephemeral nodes vanish when the session's lease-like timeout expires, which ties election to liveness. Libraries such as Apache Curator's LeaderLatch package this recipe so you don't hand-roll it.

ZooKeeper election chain: each candidate watches only its predecessor

Trade-offs

Short leases

  • Fast failover after a crash
  • More renewal traffic on the coordination store
  • More false failovers from brief GC pauses or network blips
  • Gray & Cheriton found short terms (around 10 s) near-optimal for their file workload

Long leases

  • Fewer spurious leader changes
  • Longer unavailability when the leader really dies
  • Wider window in which a zombie can act if you skip fencing
  • More tolerance for clock-rate drift between nodes
Efficiency vs correctness: If a duplicate leader only wastes work (two nodes send the same report), a lease alone is often fine. If a duplicate leader corrupts data or double-charges a customer, you need fencing at the resource, full stop. Kleppmann draws exactly this line between locks for efficiency and locks for correctness.

Real-world use cases

Kubernetes control plane
kube-controller-manager and kube-scheduler run several replicas but use Lease objects in coordination.k8s.io so only one is active; kubelets also heartbeat through per-node Leases in kube-node-lease (Kubernetes Leases).
Google Chubby
GFS and Bigtable-era systems used Chubby locks to elect masters, with sequencers so file servers could reject commands from a deposed master (Burrows).
ZooKeeper-based clusters
Services built on Curator recipes elect a single active coordinator using ephemeral sequential znodes and session timeouts (ZooKeeper Recipes).
etcd-backed singletons
Schedulers and operators campaign with the etcd Election API and guard writes with a transaction comparing the leader key's creation revision (etcd API).

Design checklist

Elect through a consensus-backed store, never a single cache node. Tie leadership to a lease with a TTL comfortably larger than your worst observed pause. Have the leader stop work when it fails to renew within its renew deadline, before the lease can expire for others. Derive a monotonic token from the grant and pass it as a required argument to every protected write. Make the storage layer reject lower tokens with a conditional write. Watch predecessors, not the leader, to avoid stampedes. Finally, test it: pause the leader process (for example with SIGSTOP) past its lease and confirm its writes are refused when it resumes.
