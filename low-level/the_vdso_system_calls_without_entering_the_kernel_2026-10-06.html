The vDSO: System Calls Without Entering the Kernel

A tiny shared library the kernel writes for you, so asking “what time is it?” costs a function call instead of a ring transition.

October 6, 2026 · 5 min read

Summary

Some system calls are called so often, and do so little, that the cost of entering the kernel dominates the work. clock_gettime() is the classic case: databases, tracers and loggers call it millions of times a second just to read a number the kernel already knows. The vDSO (virtual dynamic shared object) is Linux's answer. At execve() the kernel maps a small ELF shared library into every process, plus a read-only data page called [vvar] that the kernel keeps up to date. The C library finds the vDSO and calls its functions directly, so the common path never executes a syscall instruction at all (vdso(7)).

Why it is safe: the vDSO never gets privilege. It only reads memory the kernel deliberately shares (read-only) and executes unprivileged instructions like rdtsc. Anything it can't answer from that shared state, it hands to the real syscall.

How it works

Finding the library

The kernel passes the vDSO's base address to each program in the ELF auxiliary vector under AT_SYSINFO_EHDR, readable with getauxval(3). Its location is randomized by ASLR, and it shows up in /proc/self/maps as [vdso] next to [vvar] (Kernel Internals: vDSO). glibc parses its dynamic symbol table at startup; on x86-64 it exports __vdso_clock_gettime, __vdso_gettimeofday, __vdso_time and __vdso_getcpu with version LINUX_2.6 (vdso(7)). Programs without glibc can do the same lookup; the kernel ships a reference parser in tools/testing/selftests/vDSO/parse_vdso.c.

Two paths to the current time

The data page and the seqcount

The interesting part isn't the code, it's the coordination. The kernel's timekeeping core updates the vvar page whenever it advances its notion of time; in current kernels the layout is struct vdso_time_data, holding an array of per-clocksource struct vdso_clock records (include/vdso/datapage.h). Userspace can't take a lock the kernel would respect, so the vDSO uses a sequence counter: the writer makes seq odd, updates the fields, then makes it even again. The reader in lib/vdso/gettimeofday.c spins while seq is odd, issues smp_rmb(), reads the hardware counter and the base values, and retries if seq changed underneath it. It's the same idea as the kernel's seqlocks, applied across the user/kernel boundary.

Inside the loop the conversion is fixed-point arithmetic precomputed by the kernel: ns = ((cycles - cycle_last) * mult + base) >> shift. On x86 the helper also filters out “negative motion,” because TSCs on different sockets can be slightly off, and an unsigned subtraction would otherwise produce an enormous jump forward (arch/x86/include/asm/vdso/gettimeofday.h).

Seqcount retry across the user/kernel boundary

When the vDSO says no

The fast path only works when the current clocksource can be read from ring 3. If it can't, the kernel marks the clock VDSO_CLOCKMODE_NONE and the vDSO issues the real syscall itself through an arch-specific fallback (VDSO_SYSCALL2 on x86-64). The same happens for clock IDs the vDSO doesn't handle, such as per-process CPU-time clocks; as Bert Hubert found, glibc “always” calls the vDSO, but the vDSO may quietly make a syscall on your behalf.

Time namespaces reuse the same trick. A task inside a time namespace gets a special vvar page whose seq is permanently odd and whose clock_mode is VDSO_CLOCKMODE_TIMENS; the reader notices while it would otherwise spin and takes a path that adds the namespace's offsets. Tasks outside a namespace pay nothing extra (lib/vdso/gettimeofday.c).

Legacy vsyscall page

  • Fixed address 0xffffffffff600000, same in every process
  • A gift to exploits that need known code addresses (LWN)
  • Now trap-and-emulate; default vsyscall=xonly makes it unreadable (LWN)
  • Recent LASS patches emulate it from the #GP handler (tip)

vDSO

  • Real ELF library, ASLR-randomized
  • Symbol-versioned, discovered via AT_SYSINFO_EHDR
  • Kernel can add functions without breaking old binaries
  • Falls back to the syscall when it can't answer

The newest resident: getrandom()

Linux 6.11 added vgetrandom(), by Jason Donenfeld, so cryptographically secure random bytes no longer need a syscall per call (6.11 pull request). Unlike time, randomness needs per-thread state that must never be duplicated. The caller first asks the vDSO how big that state is and which mmap() flags to use, then allocates it with the new MAP_DROPPABLE flag, which lets the kernel reclaim and zero it under memory pressure; the area is also wiped on fork so parent and child never emit the same stream (LWN, LWN). A generation counter in the vvar data tells the vDSO when the kernel has reseeded, and the implementation in lib/vdso/getrandom.c follows random.c's fast key erasure design. glibc 2.41 picked it up for x86-64 on 6.11 and several other architectures on 6.12, falling back to the syscall on reentrancy or allocation failure (glibc commit, 2.41 release notes).

Debugging tip: successful vDSO calls never appear in strace. If you see a flood of clock_gettime lines, that's your sign the fast path is being skipped.

Real-world use cases

Timestamps at scale
Databases, tracers and loggers read the clock per operation. The vDSO turns that from a kernel entry into a few loads and an rdtsc.
The EC2 clocksource trap
Xen's xen clocksource couldn't be read from userspace, so timing calls fell back to syscalls; Packagecloud measured them about 77% slower (Packagecloud), and Heap credited switching to tsc as part of a 30% p95 query improvement (Heap). A later patch prefers tsc on Xen when it's provably safe (xen-devel).
Per-CPU sharding
__vdso_getcpu lets allocators and counters pick a per-CPU shard cheaply, without a syscall.
Fast secure randomness
UUID generation, TLS nonces and hash-table seeding get kernel-quality random bytes through vgetrandom() instead of userspace CSPRNGs that can go wrong across fork.
Containers with shifted clocks
Time namespaces give a container its own CLOCK_MONOTONIC and CLOCK_BOOTTIME offsets while staying on the vDSO fast path.
Hardening legacy binaries
Ancient static binaries that still jump to the vsyscall page keep working through emulation, while modern code gets a randomized, unreadable-by-default layout.

Design takeaways

The vDSO is a pattern, not just a Linux feature: when a privileged component owns data that is read far more often than it changes, publish a read-only snapshot and let readers validate it with a version counter. Keep the escape hatch (the syscall) so correctness never depends on the fast path. And make the contract an ELF symbol table rather than a fixed address, so the kernel can grow the interface, as it did with getrandom(), without breaking anything already running.
