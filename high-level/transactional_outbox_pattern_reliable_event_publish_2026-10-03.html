Transactional Outbox Pattern: Reliable Event Publishing

How to publish domain events without dual-write failures between your database and message broker

October 3, 2026 · 5 min read

The Concept, Briefly

Microservices often need to do two things in one business operation: update local state and notify other services. Place an order, then emit OrderCreated. Capture a payment, then tell shipping to start. The catch is that your database and your message broker are separate systems. There is no cheap, reliable two-phase commit (2PC) that spans both—and even when XA/2PC exists, coupling the service to both stores is usually undesirable.

That gap is the dual-write problem. If you commit the DB first and crash before publish, downstream services never learn about the change. If you publish first and the transaction rolls back, other services act on an event that never happened. Chris Richardson’s Transactional Outbox pattern collapses both intents into one local transaction: write the business row and an outbox event row together. A separate message relay later reads committed outbox rows and publishes them to the broker. The event exists if and only if the business change committed.

Key guarantee: The outbox does not make the broker part of your DB transaction. It makes the intent to publish durable in the same commit as the business data. Delivery to consumers is still at-least-once—idempotent consumers remain mandatory.

Underlying Ideas & Mechanisms

Why Dual-Write Breaks

A service that updates aggregates and sends messages (saga participants, domain-event publishers, CQRS write models) must keep those two effects consistent. Without 2PC, any sequence of “DB then broker” or “broker then DB” leaves a crash window. Network timeouts make it worse: a publish may have succeeded even when the client saw a failure, so naive retries can invent duplicates while crashes invent losses. The outbox removes the loss path for published intent by anchoring it in the database first.

Dual-Write Failure Modes vs Outbox

Write Path: One Transaction, Two Rows

The write path is the entire trick. Inside a single database transaction the service: (1) mutates business tables, (2) inserts a row into an outbox table with a stable event id, aggregate type/id, event type, and payload, then (3) commits once. No broker call happens inside that transaction—holding DB locks while waiting on the network only adds latency and still does not make the broker transactional. If either write fails, both roll back. If the commit succeeds, a durable record says which event still needs publishing.

On relational databases the outbox is typically a dedicated table. On document stores it can be an embedded property on the aggregate document, written in the same atomic update. Either way, the message relay is a separate process: poller, sidecar, or CDC connector.

Relay: Polling vs CDC

A polling relay periodically selects unpublished rows, publishes them, then marks them published. Concurrent relays use row locks such as PostgreSQL’s SELECT … FOR UPDATE SKIP LOCKED so each worker claims a disjoint batch without a distributed lock manager. Polling is operationally simple—no Kafka Connect cluster required—and is often the right default when sub-second lag is acceptable.

Change Data Capture (CDC) relays—notably Debezium—tail the database transaction log (WAL) and stream outbox inserts to Kafka with low overhead and near-real-time latency. Debezium’s Outbox Event Router SMT extracts payload, keys by aggregate id, and routes by aggregate type. CDC shines when you already run Kafka Connect and need lower lag or higher throughput; it adds Connect ops, replication-slot monitoring, and WAL retention concerns.

Outbox Write Path and Relay Paths

At-Least-Once and Idempotent Consumers

The relay can publish successfully and crash before marking the row published (or before committing its CDC offset). On restart it publishes again. Richardson notes this explicitly: consumers must be idempotent, typically by tracking processed message ids. Pair the business effect and the dedupe insert in one local consumer transaction so “processed but crashed before recording” cannot reopen. Preserve per-aggregate ordering by partitioning/keying broker messages on aggregate id and writing events in commit order for that aggregate.

Design Comparison

Polling Outbox

  • No Kafka Connect / CDC infra
  • Lag roughly half the poll interval
  • SKIP LOCKED for multi-relay scale-out
  • Needs a reaper for published rows
  • Best default for most teams

CDC Outbox (Debezium)

  • Near-real-time via WAL / binlog
  • Low DB polling load
  • Needs Connect + slot monitoring
  • EventRouter SMT for topic routing
  • Right when Connect already runs

Outbox Wins

  • Atomic business + publish intent
  • No 2PC with the broker
  • Works with sagas and CQRS writes
  • Intentional, versioned event contracts
  • Ordering by aggregate is controllable

Watch-outs

  • Developers can forget the outbox write
  • Still at-least-once to the broker
  • Outbox table growth needs cleanup
  • CDC ops cost if you introduce Connect solely for this
  • Not a substitute for consumer idempotency

Real-World Use Cases

Saga Participants
Update local entities and emit the next choreography/orchestration message only if the local transaction commits.
CQRS Write Models
Persist command results and feed projections without missing or inventing updates after a crash.
Order → Shipping
Debezium’s classic example: order-service outbox events stream to Kafka; shipment-service consumes with id-based dedupe.
Payments & Notifications
Record a charge and enqueue email/webhook intents in one commit so customers are never charged without a follow-up path.

Trade-offs to Keep in Mind

The transactional outbox is the boring, production-proven fix for dual-write. It trades a small amount of publish latency and an extra table (plus a relay) for a guarantee that is otherwise hard: events leave the service only when the business change actually committed. Prefer polling until lag or load forces CDC. Always design stable event ids, per-aggregate keys, and idempotent consumers from day one. And treat “forget to write the outbox row” as a process risk—frameworks, domain events raised inside the aggregate, or linting around write handlers help more than hoping reviewers catch it every time.

If you already covered message-queue delivery guarantees, sagas, and CQRS in this series, the outbox is the glue that makes those patterns honest under failure: local ACID for intent, asynchronous fan-out for everyone else.
