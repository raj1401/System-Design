Saga Pattern: Distributed Transactions with Compensating Actions

Why database-per-service kills classic 2PC, and how local commits plus compensations keep workflows consistent

September 27, 2026 · 5 min read

The Concept, Briefly

When each microservice owns its own database, a business operation such as “place order” may touch Orders, Inventory, Payments, and Shipping as separate local transactions. You cannot wrap them in one ACID transaction: two-phase commit (2PC) across heterogeneous stores is slow, brittle under partitions, and often unavailable. The saga pattern replaces that global lock with a sequence of local transactions. Each step commits independently and publishes a message or event that triggers the next. If a later step fails, the saga runs compensating transactions that semantically undo earlier commits rather than rolling them back inside one database engine.

Hector Garcia-Molina and Kenneth Salem introduced sagas in their 1987 SIGMOD paper for long-lived database transactions. The microservices community revived the idea for cross-service workflows: Chris Richardson’s microservices.io pattern catalog, Microsoft’s Azure Architecture Center, and AWS Prescriptive Guidance all describe the same core guarantee—either the forward sequence completes, or a compensating sequence amends the partial execution.

Compensation is not rollback: A refund is a new forward write, not an erase of the charge. Other transactions may have observed intermediate state. Design for eventual consistency and make every forward and compensating step idempotent.

Underlying Ideas & Mechanisms

Local Transactions, Messages, and Compensations

A saga is T1, T2, …, Tn where each Ti is a real local ACID transaction in one service. After Ti commits, locks are released and other work can see the effects. If Tk fails, the system runs C(k-1), …, C1—compensating transactions defined for each earlier step. Garcia-Molina and Salem were explicit: compensation undoes effects semantically. Canceling a seat reservation decrements the reserved count; it does not restore an earlier snapshot that other bookings may have changed.

Reliability hinges on dual-write safety. Updating business state and publishing the “next step” event must not diverge. Practitioners pair sagas with the transactional outbox (or CDC / transaction-log tailing) so the local commit and the outbound message share one database transaction, then rely on at-least-once delivery plus idempotent handlers on the far side.

Happy Path vs Compensation Path

Choreography: Events Without a Central Boss

In choreography, each service listens for domain events, runs its local transaction, and publishes the next event. An OrderCreated event triggers Inventory to reserve stock and emit InventoryReserved; Payment listens for that and charges the card. On failure, services publish failure events (for example PaymentFailed) that peers handle by compensating. There is no single orchestrator process. AWS and Azure both note this shines for short, linear workflows with few participants: less central infrastructure, looser coupling. The cost is scattered control flow—the “saga” lives only in the event graph, which gets hard to reason about as branches and compensations multiply.

Orchestration: A Coordinator Owns the State Machine

In orchestration, a saga orchestrator (a dedicated service or a durable workflow engine) tells each participant which command to run, records replies, and decides the next step or compensation. Participants stay simpler: they expose command handlers and emit replies; they do not encode the whole business workflow. Microsoft and Temporal-style guidance favor orchestration when there are many steps, parallel branches, timeouts, or human approvals—visibility and debugging live in one place. The trade-off is that the orchestrator becomes critical path infrastructure and a potential bottleneck; it must be durable, restartable, and carefully versioned.

Choreography vs Orchestration

Design Rules That Keep Sagas Safe

Every forward step and every compensation must be idempotent: orchestrators and brokers retry. Prefer semantic compensations you can actually perform (refund, release hold, cancel reservation) over pretending time travel. Prefer reservations and tentative holds early in the saga so later failures compensate cheaply. Isolate irreversible side effects (physical shipment, irreversible external API) as late as possible. Persist saga state durably so a crash mid-compensation resumes instead of restarting. And accept that observers may briefly see intermediate states—design UIs and downstream consumers for that reality.

Design Comparison

Choreography

  • Services react to domain events
  • No central coordinator to run
  • Looser coupling; easy to add a listener
  • Workflow logic is hard to see end-to-end
  • Fits short, mostly linear sagas

Orchestration

  • Orchestrator drives commands and replies
  • Single place for branching and timeouts
  • Easier observability and versioning
  • Orchestrator is critical infrastructure
  • Fits complex or long-running workflows

Saga Strengths

  • No distributed locks / 2PC across DBs
  • Each service keeps local ACID
  • Scales with independent data stores
  • Works across heterogeneous tech stacks
  • Natural fit for event-driven platforms

Saga Costs

  • Only eventual consistency across services
  • Compensation logic is hard to get right
  • Partial visibility of intermediate state
  • Needs outbox + idempotency everywhere
  • Some actions have no clean reverse

Real-World Use Cases

E-commerce Checkout
Create order, reserve stock, charge card, schedule shipment; release stock and refund if payment or fulfillment fails.
Travel Booking
Classic Garcia-Molina example: reserve flight, hotel, car; cancel prior holds if a later booking fails.
Bank Transfers
Debit source ledger, credit destination; compensating credit/debit (or reverse transfer) if the far side rejects.
Provision Cloud Resources
Orchestrated create of network, compute, DNS, and secrets; tear down allocated pieces on a mid-pipeline failure.

Trade-offs to Keep in Mind

Reach for a saga when you already chose database-per-service and the business can tolerate brief inconsistency with clear compensations. Prefer a single local transaction (or a modular monolith) when the workflow is small and co-located data would be simpler. Prefer orchestration frameworks or durable workflow engines when the state machine is non-trivial; prefer choreography when three services and a linear happy path are enough. Never treat compensation as optional cleanup—design and test the failure path with the same rigor as the happy path, including retries, timeouts, and poison-message handling.

Finally, sagas do not replace idempotent consumers or transactional outboxes; they depend on them. Without atomic “write state + emit next message,” you get stuck or duplicated steps that look like saga bugs but are dual-write bugs.
