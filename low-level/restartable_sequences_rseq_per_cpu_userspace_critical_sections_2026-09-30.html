Restartable Sequences (rseq): Per-CPU Userspace Critical Sections in Linux

Abort-on-preemption atomics for userspace per-CPU data — without locks or lock-prefixed instructions

September 30, 2026 · 5 min read

Summary

The kernel can disable preemption while it touches per-CPU data. Userspace cannot. Any thread can be preempted or migrated between reading its CPU number and updating that CPU’s freelist — so the usual fix is a heavyweight atomic (lock-prefixed cmpxchg on x86, LL/SC elsewhere). Restartable sequences flip the problem: instead of preventing interruption, detect it and restart.

A thread registers a shared struct rseq with the rseq() syscall (Linux 4.18+). Before a short assembly critical section, it points rseq_cs at a descriptor naming start_ip, length, and abort_ip. If the kernel preempts, migrates, or delivers a signal while the instruction pointer is inside that range — before the final commit store — it redirects execution to the abort handler. Complete the commit and the update is atomic w.r.t. other threads on that CPU and nested signal handlers. Proposed by Paul Turner and Andrew Hunter, driven upstream by Mathieu Desnoyers, and registered automatically by glibc since 2.35.

Deeper Dive

Two rules that make it work

An rseq critical section follows a preparation / commit pattern. First: make no changes visible to other threads until the last instruction (typically a single store that publishes a pointer or pops a freelist head). Second: if anything interrupts before that commit, discard the partial work and restart from the top. The kernel does not roll back memory — userspace must tolerate aborts by keeping intermediate state private (registers, stack temps) until the commit store.

Critical sections are tiny, written in assembly, and must not issue syscalls. Nesting is unsupported: one active rseq_cs per thread. On abort the kernel clears rseq_cs; you must re-arm it before retrying. The abort handler begins with an architecture-specific RSEQ_SIG sentinel so a stray jump cannot land in the middle of recovery code.

The ABI: struct rseq and struct rseq_cs

Registration is one syscall: rseq(struct rseq *rseq, uint32_t rseq_len, int flags, uint32_t sig). Only one registration per thread — checking more in the scheduler hot path would be too expensive. The per-thread object (glibc exposes it via the thread pointer and __rseq_offset / __rseq_size) holds:

cpu_id_start / cpu_id — kernel-updated CPU number (fast sched_getcpu without a syscall); rseq_cs — pointer to the active critical-section descriptor (or NULL); node_id — NUMA node; mm_cid — concurrency ID within the mm, dense when a process runs on few CPUs. The descriptor itself carries start_ip, post_commit_offset, and abort_ip.

One ABI, many libraries: Because only one struct rseq exists per thread, glibc (2.35+) owns registration and libraries share it. Each library arms its own struct rseq_cs for its short asm block. Overwriting read-only ID fields breaks co-existence — Optimized RSEQ V2 enforces that and kills violators with SIGSEGV.

glibc, librseq, and Optimized V2

Since glibc 2.35, every new thread gets an rseq registration in the TCB. Applications include sys/rseq.h, check __rseq_size (zero if unavailable), and point rseq_cs at their descriptor. Mathieu Desnoyers’ librseq provides portable inline asm helpers for common per-CPU patterns and a registration API for older libcs that coexists with glibc 2.35+. The tunable glibc.pthread.rseq can disable automatic registration when a process must own the ABI itself.

Recent kernels advertise Optimized RSEQ V2 via getauxval(AT_RSEQ_FEATURE_SIZE): ID fields update only on migration, critical-section checks run only when the thread was actually interrupted, and optional scheduler time-slice extensions let a thread ask for a few extra microseconds to finish a critical section (prctl(PR_RSEQ_SLICE_EXTENSION, …), then rseq_slice_yield). Legacy 32-byte registrations keep the older unconditional-update behavior for ABI compatibility — documented in the kernel rseq UAPI docs.

Who owns __rseq_abi in a process

rseq per-CPU update

  • Plain loads/stores in the fast path
  • Abort + retry on preempt/migrate
  • Best for short, CPU-local ops
  • Asm critical sections; no syscalls

Atomics / locks

  • Lock-prefixed or LL/SC every update
  • Correct across migration by design
  • Higher cost on contended hot paths
  • Easier to write in C; nestable locks

Real-World Use Cases

Allocator freelists
Per-CPU free-lists in jemalloc, TCMalloc, and glibc malloc: pop/push without atomics when the thread stays on the CPU — the original production motivation for merging rseq.
Fast getcpu
Reading cpu_id from the registered ABI replaces sched_getcpu syscalls / vDSO round-trips for indexing per-CPU arrays.
Ring buffers & tracers
LTTng-UST and similar tracers write per-CPU ring buffers; rseq keeps the producer path CPU-local without expensive atomics on every event.
Userspace RCU / counters
Per-CPU grace-period tracking, counters, and linked-list ops that only need atomicity vs other threads on the same CPU — not a global total order.
When not to use rseq: Long critical sections (aborts become frequent), anything that needs a syscall, or updates that must be atomic across CPUs. Cross-CPU publication still wants ordinary atomics, mutexes, or RCU. rseq is the userspace analogue of kernel percpu ops — not a replacement for shared-memory synchronization between cores.
