Service Discovery: Client-Side vs Server-Side Registries

How services find healthy peers when IPs keep changing under them

September 21, 2026 · 5 min read

The Concept, Briefly

Service discovery is the mechanism that maps a logical service name (for example payment-service) to the current set of network endpoints that implement it. In a dynamic fleet, instances come and go, change IPs on restart, and fail health checks; hard-coded host lists cannot keep up. Discovery uses a service catalog (registry) so callers resolve identity to address at runtime instead of bake-time.

HashiCorp frames the idea as discovering services by identity rather than by static IP and port: consumers look up access information from a catalog that tracks registration and health as the fleet evolves. Two dominant patterns emerge: client-side discovery, where the caller queries the registry and picks an instance itself, and server-side discovery, where an intermediary (load balancer, proxy, or mesh sidecar) does the lookup and routing on the caller's behalf.

Why this matters: Without discovery, every deploy becomes a configuration chase across callers. With it, autoscaling, rolling updates, and multi-zone failover become catalog updates rather than redeploys of every dependent service.

Underlying Ideas & Mechanisms

The Service Catalog Lifecycle

A typical instance lifecycle is register → heartbeat / health-check → deregister (or expire). On registration the instance publishes name, IP, port, and optional metadata (zone, version, weight). Periodic renewals prove liveness; missing renewals or failed active checks remove the instance from healthy results so callers stop targeting it.

Netflix Eureka is a classic client-side registry for mid-tier load balancing and failover in AWS. Services register with Eureka and renew leases about every 30 seconds; if renewals stop, the instance is normally removed after roughly 90 seconds. Clients periodically fetch (and cache) the registry, then load-balance locally to chosen instances.

Client-Side Discovery

In client-side discovery the consumer is responsible for the full path: query the registry, apply a load-balancing policy (round-robin, weighted, zone-aware), and dial the chosen instance directly. No proxy sits in the data path for that hop. Flexibility is high — each team can tune retries and affinity — but every language and framework needs a capable registry client, and stale caches can briefly send traffic to dead instances.

Server-Side Discovery

In server-side discovery the consumer dials a stable virtual address. An intermediary consults the catalog, selects a healthy backend, and forwards the request. Kubernetes Service objects are the everyday example: CoreDNS publishes a DNS name; traffic to the Service's ClusterIP is distributed by kube-proxy (or an equivalent dataplane) to ready pods tracked via EndpointSlices. Callers stay simple and polyglot-friendly; the cost is an extra hop and dependency on the proxy tier.

Client-Side vs Server-Side Discovery

DNS as the Universal Interface

DNS is the original discovery API: every language can resolve a name, and no proprietary client is required. Consul exposes healthy instances over DNS (commonly under .consul) and an HTTP catalog API. Kubernetes CoreDNS creates A and SRV records for each Service so pods can resolve names like my-service.my-ns.svc.cluster.local.

The tradeoff is caching. Resolvers honor TTLs; even with low TTLs you cannot guarantee instantaneous failover when an instance dies. For short-lived pods and aggressive scale events, pure DNS discovery often pairs with short TTLs, client reconnect logic, or a headless Service that returns pod IPs so the application (or a mesh) owns load balancing.

Health Checks and Consistency

Discovery is only as good as its health signal. Eureka leans on lease renewals and prefers availability — during suspected partitions it can enter self-preservation and stop expiring instances so a network blip does not empty the catalog. Consul agents run active and passive checks and push status into a Raft-backed server catalog, with gossip (Serf) handling membership among agents. Kubernetes readiness gates which endpoints are eligible for Service traffic.

Design Comparison

Client-Side Discovery

  • Caller queries registry and load-balances in-process
  • No extra proxy hop on the data path
  • Fine-grained control over LB, retries, and affinity
  • Needs a solid client library per language
  • Cache staleness can briefly hit dead instances

Server-Side Discovery

  • Caller uses one stable name or VIP
  • Proxy or LB owns lookup and health routing
  • Ideal for polyglot fleets and managed platforms
  • Adds a network hop and a critical dataplane dependency
  • Default fit for Kubernetes Services and service meshes

Real-World Use Cases

Netflix Eureka
REST registry underpinning mid-tier load balancing and failover in AWS; clients cache the catalog and renew instance leases on a fixed cadence.
HashiCorp Consul
Platform-agnostic catalog with DNS and HTTP lookup, agent health checks, Raft-backed servers, and multi-datacenter federation options.
Kubernetes Services
CoreDNS plus ClusterIP (or headless) discovery; EndpointSlices track ready pods so in-cluster callers resolve by Service name.
Service Mesh (Envoy)
Sidecars implement server-side discovery with centralized traffic policy, mTLS, and retries — discovery leaves application code entirely.

Trade-offs to Keep in Mind

Pick client-side discovery when you need custom load-balancing logic and can standardize on one discovery stack (historically Eureka + Ribbon / Spring Cloud LoadBalancer). Prefer server-side discovery on Kubernetes or when many languages must share one operational model. Treat DNS TTLs as a latency dial, not a guarantee of instant failover. Couple discovery tightly with health checks: a perfect registry that lists unhealthy instances is worse than a slightly stale registry that only lists healthy ones.

Service discovery also sits next to — but is not the same as — membership gossip. Gossip (as in Consul's Serf or Cassandra) spreads node liveness; the catalog answers "which healthy endpoints implement this service name." Production systems often combine both: gossip for agent/node health, a strongly or eventually consistent catalog for service lookups.
