The Slab Allocator: Object Caching for Kernel Memory

Why kernels don't malloc() task structs from scratch — they keep a warm pool of pre-built objects ready to hand out.

July 31, 2026 · 5 min read

The concept, in short

Every second, a running kernel creates and destroys thousands of small, fixed-shape objects: process descriptors, inodes, network buffer headers, filesystem dentries. A general-purpose heap allocator (think malloc) is bad at this job — it fragments memory into odd-sized holes and pays the full cost of constructing and tearing down complex structures on every call. The slab allocator fixes this by carving memory into slabs — chunks of one or more contiguous pages — and pre-dividing each slab into equal-sized object slots. Freed objects go back into a cache instead of being destroyed, so the next allocation of the same type can be handed out immediately, often already partially initialized.

This design was introduced as a comprehensive overview of the SunOS 5.4 kernel memory allocator, based on a set of object-caching primitives that reduce the cost of allocating complex objects by retaining their state between uses. That 1994 idea from Sun Microsystems became the ancestor of the allocators still running inside Linux, BSD, and Windows kernels today.

Why this matters: Kernel code allocates and frees memory on nearly every system call, page fault, and packet arrival. If that path isn't close to free in both time and fragmentation, the whole system slows down. Slab allocation turns a general heap problem into a cheap "pop from a free list" problem for the object types the kernel cares about most.

How it actually works

Caches, slabs, and objects

The allocator organizes memory in three tiers. A kmem_cache represents one object type — say, struct task_struct or struct inode. Each cache owns one or more slabs, and the slab allocator system organizes memory into caches of reusable slabs, each consisting of one or more contiguous pages of memory from the kernel's page cache, subdivided into fixed-sized blocks for the allocation of kernel objects, which minimizes fragmentation common in conventional allocation methods. Because every block in a slab is exactly the object's size, there is no external fragmentation within that cache — no leftover slivers of unusable space between objects.

Bonwick's original scheme went further than plain free-lists: caches can carry constructor and destructor callbacks, so an object's invariant state (locks, list heads, magic numbers) is set up once and preserved across many alloc/free cycles instead of being rebuilt every time. The primary problem with earlier allocators was the construction and destruction of objects on every allocation; this allocator instead maintains a pool of preallocated and constructed instances that do not get destroyed on each logical free, returning them to the cache instead.

Slab coloring

One subtle addition from the original paper is object coloring: successive objects handed out from a cache are offset by a small, varying amount so that their start addresses don't all land on the same cache-line or memory-bank boundary. The allocator's object caches respond dynamically to global memory pressure, and employ an object-coloring scheme that improves the system's overall cache utilization and bus balance. Without coloring, many objects of the same type would alias onto the same L1 cache lines, causing needless evictions.

SLAB, SLUB, and SLOB: three Linux flavors

Linux has shipped multiple slab implementations over the years. The Linux kernel has 3 flavors of slab allocators — SLAB, SLUB, and SLOB — with SLUB being the default and most widely used. The original Linux SLAB allocator, ported from Bonwick's design, kept per-CPU, per-shared, and per-NUMA-node queues of objects to minimize cross-CPU movement, but this three-level structure came at a cost: on a 256-CPU NUMA machine with many kmem_cache instances, SLAB metadata could consume hundreds of megabytes, the queue-draining logic between the three levels had subtle bugs, and multiple CPUs could contend on the per-node shared queue lock.

Christoph Lameter designed SLUB, merged into Linux 2.6.23 in 2007, by removing the queues entirely. Instead of managing lists of free objects, SLUB embeds a freelist pointer directly inside each free object and gives every CPU a private "current slab" to allocate from without taking a lock. Objects in a slab are stored contiguously in memory but are logically interconnected through a linked list, so the allocator can always find the next free object without touching data already in use. Only when a CPU's local slab is exhausted does it fall back to a per-NUMA-node list of partially-used slabs, and only after that to the page allocator for a brand-new slab.

The third variant, SLOB (Simple List Of Blocks), traded throughput for a tiny memory footprint. The SLOB allocator was designed to require little memory for implementation and housekeeping, for use in small systems such as embedded systems, though it suffers greatly from external fragmentation. It was removed from the kernel in version 6.4 after SLUB absorbed its low-memory optimizations.

Cache → Slab → Object hierarchy

SLUB fast path: allocation without a lock

This layered fallback — per-CPU slab freelist, then per-node partial list, then the page allocator — is exactly what lets SLUB satisfy the overwhelming majority of allocations with no locking at all: only when a CPU's local slab is fully drained does it need to touch shared, lock-protected state.

Comparing the approaches

SLAB (queue-based, legacy)

  • Per-CPU, per-shared, and per-node queues per cache
  • Minimizes cross-CPU object movement by routing freed objects to the per-CPU list first
  • Metadata overhead balloons on large NUMA machines
  • Default in Linux until kernel 2.6.23 in 2008

SLUB (unqueued, current default)

  • Removes the queues entirely , tracks free objects inline
  • Simple per-CPU "current slab" fast path
  • Designed by Christoph Lameter as a drop-in replacement conforming to the same API; the default allocator today
  • Rich slabinfo / debugging tooling built in

Debugging and observability

Production kernels can turn on extensive slab sanity checking without a rebuild. The slab allocator includes full debugging support when built with CONFIG_SLUB_DEBUG=y, off by default, and can be enabled only for selected slabs via a slab_debug option on the kernel command line to avoid impacting overall performance. Options include red-zoning to catch overwrites, poisoning to detect use-after-free, and allocation/free tracking for forensic analysis — the same debugging primitives Bonwick highlighted three decades ago.

Real-world use cases

Process management
Every struct task_struct, mm_struct, and kernel stack is allocated from a dedicated slab cache so fork/exit stays fast under heavy process churn.
Filesystems
Inode and dentry caches rely on slab allocation to keep path lookups and metadata operations cheap even with millions of cached filesystem objects.
Networking
sk_buff headers, socket structures, and connection-tracking entries are allocated and freed per-packet, making slab's near-zero-cost reuse essential to throughput.
Security research
SLUB's design — inline freelist pointers, per-CPU caches, and cache merging — creates a rich attack surface; a 15-year-old heap out-of-bounds write in Linux Netfilter won $10,000 in Google's kCTF program.
A note on general-purpose kmalloc: Not every allocation has its own dedicated object type. Linux maintains a family of generic slab caches sized in power-of-two-ish steps (kmalloc-8 up through larger sizes) so that arbitrary small kmalloc() requests still benefit from the same fast, lock-light slab machinery instead of falling back to a general heap.

Legacy and lineage

The slab allocator's impact on operating system design has been significant, particularly in Unix-like systems such as Solaris where it was first implemented, and it remains a widely adopted mechanism in kernel memory management across various operating systems. The core insight — that fixed-shape, high-churn objects deserve their own specialized, fragmentation-free arena instead of a general-purpose heap — has outlived the specific SunOS implementation it was built for, and shows up today in FreeBSD's UMA allocator, Windows' pool allocator, and userspace object-caching libraries alike.
