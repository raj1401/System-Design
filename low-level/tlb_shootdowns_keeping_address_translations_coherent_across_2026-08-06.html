TLB Shootdowns: Keeping Address Translations Coherent Across Cores

When one core edits a page table, every other core's cached translation becomes a lie — here's how the kernel cleans that up.

August 6, 2026 · 5 min read

The concept in a nutshell

Every memory access a CPU makes is really two lookups: a translation from a virtual address to a physical one, followed by the actual read or write. Walking the page tables in memory to do that translation on every single access would be devastatingly slow, so CPUs cache recent translations in a small, per-core hardware structure called the Translation Lookaside Buffer (TLB). The TLB is an on-chip memory structure that caches the page table; it holds only page table entries, and its only purpose is to speed address translation and permissions checking.

That caching is exactly what makes it dangerous on a multicore machine. If Core 0 unmaps a page, shrinks a heap, or changes permissions with mprotect(), Core 1's TLB may still be happily translating the old, now-invalid mapping — reading freed memory, writing across a permission boundary, or executing stale code. The operating system removes invalid TLB entries via interprocessor interrupts (IPIs). Invalidations sent to all cores running an application are called TLB shootdowns and take a significant amount of time to process. It is, in effect, a tiny cache-coherence protocol implemented almost entirely in software.

Why this matters: Unlike a data cache, a stale TLB entry is not merely a performance bug — it is a correctness and security hazard. A thread on another core could keep reading or executing through a mapping the kernel believes no longer exists, which is exactly the class of bug that Meltdown-style mitigations had to reason about carefully.

How address translation and the TLB actually work

On a TLB hit, the story is simple: the Translation Lookaside Buffer is a cache of recently executed page translations within the MMU, and on a memory access the MMU first checks whether the translation is cached in the TLB — if it is, you have a TLB hit and the TLB provides the physical address immediately. On a miss, hardware (or, on some architectures, software) walks the page tables: if the requested translation is not in the TLB it is a miss, and the processor proceeds by looking up the page table via the page walk, which is time-consuming compared to processor speed because it involves reading multiple memory locations. The result is then installed back into the TLB so the next access to that page is fast again — a TLB miss triggers an external translation table walk, and the newly loaded translation is cached in the TLB for possible reuse.

TLBs are small on purpose — they need to be searched on almost every instruction, so they're built from fast, associative or content-addressable memory: a TLB may be implemented via a standard random-access memory or content-addressable memory (CAM), where a standard RAM is accessed via an index while a CAM is accessed via content. Capacity is the perennial constraint: modern x86 cores carry on the order of a couple thousand entries per core, split by page size each physical core has a dedicated TLB that can hold up to 2,048 entries (x86) — and processors such as Intel Sandy Bridge, Haswell, and Skylake maintain separate L1 TLBs for 4KB, 2MB, and 1GB page sizes , because a single small TLB can't efficiently hold translations for wildly different page granularities.

Tagging translations so they don't have to be nuked

Historically, switching between processes meant flushing the entire TLB, since a TLB entry with no context tag is ambiguous — process A's virtual address 0x1000 doesn't mean the same thing as process B's. x86 addressed this with PCID (Process-Context Identifier): when a logical processor creates entries in the TLBs it associates those entries with the current PCID, and when translating an address it uses only entries associated with the current PCID. This lets the kernel switch address spaces without wiping out every cached translation. Software can then selectively invalidate: if the INVPCID type is 3, the logical processor invalidates all mappings — except global translations — associated with any PCID , while other invalidation types target a single PCID or a single address. This same tagging idea (called ASID on ARM/MIPS) is central to Linux's Kernel Page Table Isolation, the Meltdown mitigation, where each syscall, interrupt or exception would otherwise flush the TLB if PCIDs weren't used to keep kernel and user mappings from stomping on each other.

The shootdown itself: a software coherence protocol

Because ordinary CPU cores cannot reach into each other's TLBs directly, invalidation has to be requested and executed cooperatively. After PTE changes, OS kernels cannot invalidate TLBs on other cores directly, so they perform a TLB shootdown: the initiating core sends an inter-processor interrupt to remote cores. On Linux this happens through a well-worn path: a function like unmap_vmas() or mprotect_fixup() modifies the page table entries, then fills out a flush_tlb_info struct with info on the parts of the address space that must be flushed, sets it as the argument to the flush_tlb_func() callback, and calls smp_call_function_many() with a CPU mask . Each targeted core receives the IPI, and pauses its current task, invokes a kernel-defined interrupt handler such as tlb_ipi_handler, which executes CPU-specific instructions like invlpg or tlbi to invalidate the stale entries . Only once every core has acknowledged completion does the initiator continue — and crucially the wait matters: in certain shootdown scenarios an instruction barrier is needed at target cores so they don't execute stale kernel code before their local TLB is flushed, which is why the IPI mechanism is preferred over asynchronous broadcast in those cases.

This synchronous wait is where the cost lives. The TLB shootdown mechanism has three overheads: sending IPIs to remote cores, which is worse on large NUMA machines; handling interrupts on remote cores, which can be delayed if interrupts are temporarily disabled; and the wait time for ACKs on the initiating core. Delivery alone isn't free — IPI delivery can take several hundreds of cycles — and it competes with other latency-sensitive work: IPIs are widely used to coordinate state across cores, for example to initiate TLB shootdowns, and from the perspective of an application pinned to a dedicated core they are asynchronous and unpredictable, often causing unwanted preemptions.

Cutting the cost: batching, laziness, and hardware broadcast

Because shootdowns are so expensive, both hardware and software vendors have spent a lot of effort avoiding them or making them asynchronous. Some ARM cores support a hardware broadcast invalidation instruction instead of interrupts, though it comes with trade-offs: SMP systems that include chips not supporting the broadcast TLBI mechanism must always use IPIs for performing TLB shootdowns , and even where broadcast is available the OS may pick dynamically — the OS can compare the cost of using an IPI versus a hardware broadcast to all cores and select whichever is cheaper, based on factors like the number of cores actually caching the affected pages and system topology. Research systems go further: Barrelfish, a research multi-kernel OS, uses message passing instead of IPIs to shoot down remote TLB entries, eliminating interrupt handling on remote cores, though it still waits for ACKs and is therefore still synchronous. Other proposals remove the wait from the critical path entirely: ecoTLB removes the instantaneous TLB shootdown from the critical path by executing it asynchronously , deferring safety to versioned bookkeeping rather than an immediate rendezvous.

Making the cache bigger instead of flushing it

A complementary strategy is simply reducing how often translations need to be cached or invalidated at all, by using bigger pages. Using more than one page size was identified in the 1990s as one means of reducing time spent servicing TLB misses by increasing TLB reach. A single huge-page TLB entry replaces hundreds of small ones: as large pages can increase the coverage of the TLB — for example, each 2MB page TLB entry can cover 512 base pages — the TLB hit ratio can be improved significantly. The effect on real workloads is measurable: the utilization of huge pages can reduce the number of TLB misses by an order of magnitude and decrease page walk latency by up to 40%. Fewer, larger mappings also mean fewer address ranges to shoot down in the first place.

Why this matters: KPTI, the Meltdown mitigation, is a textbook example of the shootdown/flush tax in practice — separating kernel and user page tables meant every syscall risked a full TLB flush until PCID-aware invalidation was carefully wired in to avoid it.

Approaches compared

IPI-based shootdown (classic Linux/x86)

  • Precise: targets exactly the cores that mapped the page
  • Synchronous — initiator blocks on ACKs
  • Cost grows with core count and NUMA distance
  • Interrupt handling can itself be delayed

Hardware broadcast TLBI (ARM64)

  • No interrupt handler needed on remote cores
  • Not universally supported across SoCs
  • Sometimes still needs an instruction barrier for correctness
  • Kernel may pick IPI vs. broadcast per-call based on cost

PCID/ASID-tagged TLBs

  • Avoids full flushes on context switches
  • Enables selective, per-address-space invalidation
  • Core to making KPTI affordable
  • Limited number of IDs must be recycled carefully

Asynchronous / lazy schemes (research)

  • Removes the wait from the hot path
  • Relies on versioning to detect staleness later
  • Improves tail latency for memory-heavy services
  • Not yet mainstream in stock kernels

Real-world use cases

munmap / mprotect
Unmapping or changing permissions on a shared region forces every core that touched it to drop the stale entry before the syscall returns.
Copy-on-write fork
When either thread writes to a shared page after a fork, the kernel copies the page and updates PTEs, which needs propagating to any core caching the old mapping.
JIT code patching
Self-modifying or JIT-compiled code that remaps executable pages must shoot down remote TLBs so no core executes stale instructions.
Kernel Page Table Isolation
KPTI splits kernel and user page tables to mitigate Meltdown; PCID-aware invalidation exists specifically to avoid flushing the TLB on every syscall boundary.
Huge pages in databases
Large in-memory databases and hypervisors use 2MB/1GB pages so a handful of TLB entries can cover gigabytes, cutting both miss rate and shootdown frequency.
Disaggregated / swapped memory
Systems that page memory out over the network, such as those studied for memory disaggregation, are especially sensitive to shootdown latency on the critical path.

Wrapping up

The TLB is one of the smallest structures in a modern CPU, but keeping it coherent across dozens of cores touches interrupts, cache-coherence-adjacent invalidation instructions, virtual memory management, and even hardware security mitigations like KPTI. TLB shootdowns are, in essence, a software-defined coherence protocol layered on top of hardware that has no native concept of shared TLB state — and understanding their cost is essential to understanding why huge pages, PCIDs, and lazy invalidation schemes exist at all.
