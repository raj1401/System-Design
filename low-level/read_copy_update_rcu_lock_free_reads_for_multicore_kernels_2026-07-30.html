Read-Copy-Update (RCU): Lock-Free Reads for a Multicore World

How the Linux kernel lets thousands of readers walk a data structure with zero locks, zero atomics, and zero waiting — by making writers do all the work instead.

July 30, 2026 · 5 min read

The Concept in Brief

Read-Copy Update (RCU) is a synchronization mechanism optimized for read-mostly data, where the key insight is that readers need not acquire any lock, perform atomic instructions, or execute memory barriers on most architectures. It was added to the Linux kernel in October of 2002 and was invented by McKenney and Slingwine as a synchronization mechanism that has been part of the Linux kernel since then.

Traditional locking forces readers and writers to fight over the same mutual-exclusion primitive. In contrast with conventional locking primitives that ensure mutual exclusion among concurrent threads regardless of whether they be readers or updaters, or with reader-writer locks that allow concurrent reads but not in the presence of updates, RCU supports concurrency between a single updater and multiple readers. RCU achieves this by never mutating data in place while a reader might be looking at it. Instead, an updater builds a new version of the data, atomically swaps in a pointer to it, and only reclaims the old version after it can prove no reader could still be using it.

Why this matters: Lock contention is one of the biggest scalability killers on many-core machines. RCU sidesteps the problem entirely for the read path — the most common operation on structures like routing tables or the dentry cache — so read-side cost stays flat no matter how many cores are hammering the data structure simultaneously.

Under the Hood: Removal, Grace Periods, and Reclamation

The basic idea behind RCU is to split updates into "removal" and "reclamation" phases. The removal phase removes references to data items within a data structure, possibly by replacing them with references to new versions, and can run concurrently with readers because modern CPUs guarantee that readers will see either the old or the new version rather than a partially updated reference. The reclamation phase does the work of reclaiming the data items removed during the removal phase, and because reclaiming can disrupt any readers concurrently referencing those items, it must not start until readers no longer hold references to them.

Concretely, the update sequence is: copy the data to be changed, modify the copy, publish the new version atomically, wait for a grace period until all pre-existing readers have finished, and finally free the old version.

Quiescent States and the Grace Period

The hard problem is step four: how does an updater know every reader that might have seen the old pointer is done with it? The updater cannot rely on readers giving any indication when they are done, but just as with spinlocks, RCU readers are not permitted to block, switch to user-mode execution, or enter the idle loop — so as soon as a CPU is seen passing through any of these three states, that CPU is known to have exited any previous RCU read-side critical sections. Each such observation is called a quiescent state; once every CPU has passed through at least one, a full grace period has elapsed and it is safe to reclaim memory. So if we remove an item from a linked list and then wait until all CPUs have switched context, executed in user mode, or executed in the idle loop, we can safely free up that item.

This is exposed to kernel code through primitives like rcu_read_lock() / rcu_read_unlock() to bound a read-side critical section, and synchronize_rcu() or call_rcu() for updaters. RCU's grace-period guarantee allows updaters to wait for the completion of all pre-existing RCU read-side critical sections, and an RCU read-side critical section begins with the marker rcu_read_lock() and ends with rcu_read_unlock(); these markers may be nested, and RCU treats a nested set as one big critical section.

Tree RCU and Memory Ordering

On large systems tracking a quiescent state from every CPU one-by-one doesn't scale, so modern Linux uses Tree RCU, which organizes CPUs into a combining tree of rcu_node structures so that grace-period bookkeeping is distributed rather than funneled through a single global lock. Beyond scalability, RCU grace periods double as a powerful ordering primitive: RCU grace periods provide extremely strong memory-ordering guarantees for non-idle non-offline code — any code that happens after the end of a given grace period is guaranteed to see the effects of all accesses prior to the beginning of that grace period that are within RCU read-side critical sections, and symmetrically for code before the grace period. This leads to the memorable description that since RCU-sched read-side critical sections include any region of code for which preemption is disabled, and each machine instruction can be thought of as a tiny region of preemption-disabled code, one can think of synchronize_rcu() as smp_mb() on steroids.

Reader Patterns and Reference Counting

A common real-world pattern combines RCU lookup with ordinary reference counting: given a Process ID number, find_vpid() searches for the struct pid in a radix tree while rcu_read_lock is held throughout, ensuring that any objects found will exist long enough for find_get_pid to increment the object's reference counter, after which rcu_read_lock may be dropped because the object is now protected by the reference counter. When the process exits, its struct pid object is freed by calling free_pid, which first removes the object from the radix tree making it inaccessible to new callers, then uses call_rcu to wait for an RCU grace period before dropping a reference to the object. This RCU-plus-refcount idiom appears throughout the kernel wherever lookups must be fast and lock-free but object lifetime still needs precise tracking.

For readers that must sleep inside their critical section — something plain RCU forbids — the kernel provides SRCU (Sleepable RCU). SRCU grace periods are slower than regular RCU grace periods because the kernel must wait for all SRCU read-side critical sections to complete rather than simply waiting for all CPUs to pass through a quiescent state, so it should be used only when blocking inside the read-side critical section is genuinely required. There are also expedited variants: Linux kernels will sometimes execute synchronize_rcu_expedited() to obtain a faster grace period at the cost of more IPI traffic, and polling APIs such as get_state_synchronize_rcu() and poll_state_synchronize_rcu() let a caller check whether a grace period has already elapsed without blocking at all, useful for use even from NMI handlers.

RCU vs. Alternatives

RCU

  • Readers: no locks, no atomics, near-zero overhead
  • Writers: copy, publish, defer free until grace period
  • Unbounded number of concurrent readers scale linearly
  • Reclamation latency, not throughput, is the cost
  • Readers may see the old or new version, never a torn one

Reader-Writer Lock

  • Readers still take a shared lock — cache-line bouncing under contention
  • Writers can starve, or starve readers, depending on policy
  • In-place mutation; no extra memory for old/new copies
  • Simpler mental model, worse multicore scalability

Seqlock

  • Readers retry if a writer ran concurrently (sequence counter)
  • No blocking, but readers can spin/retry under heavy writes
  • Not safe for pointer-based structures readers might free
  • Good fit for small, fixed-size data (e.g. jiffies, time)

Hazard Pointers

  • Per-thread reader announces the pointer it's using
  • Reclaimer scans announcements instead of waiting for a grace period
  • Popular in userspace lock-free structures (no kernel-wide GP)
  • More per-read bookkeeping than RCU's near-zero-cost reads

Real-World Use Cases

Networking
Routing table and forwarding-information-base lookups, which need to stay fast even while routes are updated — one of the classic examples cited in kernel documentation.
Filesystem
The virtual filesystem (VFS) uses RCU heavily to achieve scalability , most notably in RCU-walk path lookups that traverse the dentry cache without taking locks.
Process Management
PID lookups in find_vpid() use RCU-protected radix tree traversal combined with reference counting to keep struct pid objects alive just long enough.
NMI Handlers
Because RCU read-side critical sections need no locks or blocking, they can safely run inside non-maskable interrupt handlers where almost nothing else is safe.
Module & Table Lists
Kernel module lists and other read-mostly linked structures are traversed via list_for_each_entry_rcu without ever blocking a concurrent unload.
Userspace RCU
LGPL implementations of user-level RCU are available via liburcu , bringing the same technique to databases and userspace lock-free data structures.
Try it mentally: Imagine 64 CPUs all walking the same linked list to answer packet-routing queries, while one CPU occasionally updates a route. With a lock, every reader serializes on that lock's cache line. With RCU, the readers never touch a shared cache line at all — the update's cost (waiting for a grace period) is paid once per batch of updates, not once per read.

Trade-offs to Keep in Mind

RCU is not free — it shifts cost from readers to writers and to memory footprint. Because old versions must be kept alive until a grace period completes, RCU batches many synchronize_rcu and call_rcu requests into a single grace-period computation, trading a higher latency for a lower average per-call cost, and Linux can satisfy more than 1,000 such calls in a single batch. This means RCU shines for read-mostly workloads but is a poor fit when updates are frequent or when the update itself cannot be expressed as an atomic pointer replacement.
