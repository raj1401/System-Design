Database Sharding: Partitioning Data to Scale Beyond One Machine

How systems split one logical dataset across many physical servers — and why picking the shard key is the most important decision you'll make.

August 4, 2026 · 5 min read

Every database eventually hits a wall: a single machine only has so much CPU, memory, disk, and network throughput to give. You can buy a bigger box for a while — vertical scaling — but eventually the curve of "more data, more traffic" outpaces what any single server can offer. Sharding (also called horizontal partitioning) is the technique of splitting one logical dataset into smaller, independent pieces called shards, each living on its own database instance, so that storage and throughput scale by adding machines rather than upgrading one.

Unlike table partitioning inside a single database instance, true sharding distributes data across multiple independent servers, each capable of answering queries on its own slice of the data. Get it right and you scale linearly for years. Get it wrong — pick a bad shard key, forget how you'll rebalance — and you can spend the next year migrating data while queries slow to a crawl.

Why this matters: Sharding is usually the last scaling lever teams pull, not the first — because it is largely irreversible without significant engineering effort. Once terabytes of data are spread across 50 machines by a shard key, changing that key means re-partitioning everything live, without downtime, while traffic keeps flowing.

The Core Idea

At its simplest, sharding needs three things: a way to decide which shard a given row or document belongs to (the shard key and a partitioning strategy), a way to route requests to the right shard (a router or client-side library), and a way to move data between shards as the cluster grows (rebalancing). Database sharding is a method of splitting and storing a single logical dataset in multiple databases, and by distributing the data among multiple machines, a single database cluster can store more data and handle more requests than a single machine could.

Choosing a Shard Key

The shard key is the column (or columns) used to decide where a row lives — a user ID, a tenant ID, a geographic region. MongoDB's own guidance is a good general rule for any sharded system: a good shard key enables the database to distribute documents evenly throughout shards, needs high cardinality for better horizontal scaling and low frequency to prevent uneven distribution, and should not increase or decrease monotonically. A monotonically increasing key (like an auto-increment ID or a timestamp) sounds convenient, but it concentrates all new writes onto whichever shard currently owns the "latest" range — the exact opposite of the load-spreading sharding is supposed to deliver.

Three Ways to Route Data

Almost every sharded system chooses among three routing strategies, sometimes blended together.

Range-based sharding assigns contiguous ranges of the shard key to each shard. Contiguous ranges of the shard key are assigned to each shard — users 1–1,000,000 go to shard A, 1,000,001–2,000,000 to shard B, and so on. This keeps related rows physically close together, which is great for range scans, but it is exactly what creates hot shards when traffic or IDs aren't uniformly distributed over the range.

Hash-based sharding runs the shard key through a hash function and uses the result (often modulo the shard count) to pick a shard. Hash based sharding distributes both data and traffic evenly, dramatically reducing the risk of hotspots caused by sequential IDs or rapidly growing user bases, and works well for write heavy systems where uniform load matters more than query locality. The cost shows up in two places: range queries become expensive, because fetching a contiguous range of IDs may mean the data lives across hundreds or thousands of shards, forcing scatter-gather queries and aggregation at the application layer ; and when the number of shards changes, adding a shard changes the modulo value, so most keys must be rehashed and moved — at large scale this can mean relocating petabytes of data. (A separate technique, consistent hashing, was designed specifically to soften that second problem by minimizing how many keys move per resize — worth its own deep dive, but distinct from the sharding decision itself.)

Directory-based sharding keeps an explicit lookup table mapping key values to shards instead of computing the mapping algorithmically. With directory-based (also known as lookup-based) sharding, shards are mapped using a lookup table — for example, a table that maps a region to the specific shard holding all rows for that region. This buys enormous flexibility: you can move users between shards without changing application logic, isolate high-traffic users onto dedicated shards, and rebalance load gradually and surgically. The price is an extra hop and a new single point of failure: the directory itself can become a bottleneck, cache misses introduce extra network hops and latency, and the operational complexity is significantly higher compared to range or hash based approaches.

Chunks, Balancers, and the Cost of Growing

Real systems rarely map keys directly to shards one-for-one; instead they carve the key space into many small, contiguous pieces and assign those pieces to shards, so pieces can move independently of the logical key mapping. MongoDB calls these pieces chunks: a chunk is a contiguous range of shard key values that resides on a single shard, and the cluster divides the collection's shard key space into these ranges and assigns each range to a shard. A background balancer keeps things even: the balancer moves chunks between shards to keep data evenly distributed, and by default a chunk grows to a maximum size of 128 MB — once it exceeds this threshold, it is split into two smaller chunks, and this split-and-balance cycle is the core mechanism that allows horizontal scaling.

This indirection has a failure mode worth knowing: a chunk that cannot be split because too many rows share the same shard-key value becomes a jumbo chunk. Chunks that grow beyond the specified chunk size but cannot be split are called jumbo chunks, most commonly when a chunk represents a single shard key value, and jumbo chunks can become a performance bottleneck, especially if that value occurs with high frequency. This is the classic "celebrity problem" — a single influencer's user ID gets so much write and read traffic that its shard becomes a hotspot no amount of balancing can fix, because the balancer can't split a single indivisible key across two machines.

Cross-Shard Queries: the Scatter-Gather Tax

Sharding trades single-node simplicity for distributed-systems overhead the moment a query doesn't include the shard key. Without it, the router has no way to know which shard holds the answer, so it must ask everyone. Range queries across the shard key become scatter-gather operations because adjacent values land on different shards. Joins across shards, global secondary indexes, and multi-row transactions that span shards all inherit this same tax — which is why application teams generally try to co-locate related data (e.g., a user and all of their orders) on the same shard whenever possible.

Comparing the Strategies

Range-Based

  • Efficient range scans, ordered scans
  • Simple to reason about and pre-split
  • Prone to hot ranges from skewed key growth
  • Used by MongoDB ranged shard keys, HBase, Bigtable

Hash-Based

  • Even write/read distribution, avoids hotspots
  • Range queries become scatter-gather
  • Resharding can require moving huge fractions of data
  • Used by MongoDB hashed shard keys, DynamoDB partitions

Directory-Based

  • Maximum placement flexibility, surgical rebalancing
  • Can isolate noisy tenants onto dedicated shards
  • Directory itself needs high availability and caching
  • Used by Instagram-style logical shard maps, multi-tenant SaaS

Resharding: the Part Nobody Enjoys

Whatever strategy you start with, eventually a shard fills up or gets too hot and you need to add capacity. MongoDB's newer resharding tooling exists precisely because this used to be so painful: starting in MongoDB 5.0, a collection can be resharded by changing a document's shard key, and the refineCollectionShardKey command enables more fine-grained data distribution and can resolve jumbo chunks caused by insufficient shard key cardinality. Instagram avoided the problem almost entirely by over-provisioning at the logical layer up front — creating far more shards than they had machines and mapping many logical shards onto few physical ones, so growth only requires moving whole logical shards rather than re-partitioning data. Because a shard can grow bigger than a machine, they made many thousand logical shards that map to fewer physical nodes, kept a logical-to-physical map, and when a machine filled up a logical shard could be moved to a new machine — nothing needs to be resharded, saved by a level of indirection.

Real-World Examples

MongoDB sharded clusters use three components: config servers holding metadata, mongos query routers, and shard replica sets holding the actual chunks. The sharding operation creates one large initial chunk to cover all of the shard key values, and after the initial chunk creation, the balancer moves ranges off of the initial chunk when it needs to start balancing data.

Vitess, born at YouTube, wraps unmodified MySQL instances with a sharding-aware proxy layer. It is a database clustering system for horizontal scaling of MySQL through generalized sharding, encapsulating shard-routing logic so application code and queries remain agnostic to the distribution of data — and shards can even be split and merged with an atomic cutover step that takes only a few seconds. Vitess has been a core component of YouTube's database infrastructure since 2011, and has grown to encompass tens of thousands of MySQL nodes.

Instagram sharded PostgreSQL by embedding the shard ID directly inside every primary key. Each 'logical' shard is a Postgres schema, and each sharded table exists inside each schema, with ID creation delegated to each table inside each shard using PL/PGSQL and Postgres' auto-increment functionality. Sharding by user ID with 2000 logical shards means a user ID of 31341 maps to shard ID 31341 % 2000 = 1341 — self-routing, no directory lookup required.

Use Cases

Social / Content Platforms
Instagram shards billions of photos and likes by user ID across thousands of logical Postgres schemas mapped onto far fewer physical machines.
Video Infrastructure
YouTube's MySQL fleet runs on Vitess, spreading metadata and viewing data across tens of thousands of shard-aware MySQL nodes.
Multi-Tenant SaaS
Directory-based sharding lets a SaaS provider pin a noisy or oversized enterprise tenant onto its own dedicated shard without touching app code.
Document Databases at Scale
MongoDB Atlas clusters auto-split collections into chunks and rebalance them across shards as write volume and dataset size grow.
Time-Series / IoT
Range sharding by timestamp keeps recent, hot data together for fast writes, while older ranges age onto cheaper, colder shards.
Ad Platforms
Campaign and bidding systems shard by advertiser or account ID so a single advertiser's load never degrades another's queries.
The takeaway: Sharding is not a single algorithm but a family of trade-offs between even load distribution, query locality, and rebalancing cost. Most production systems don't purely pick one strategy — they combine range sharding within a hash bucket, or a directory layer on top of hashed shards, to get the best of each.
