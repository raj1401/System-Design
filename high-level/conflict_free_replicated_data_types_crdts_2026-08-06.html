Conflict-Free Replicated Data Types (CRDTs)

Letting every replica accept writes offline, and still converge to the same answer without asking permission first.

August 6, 2026 · 5 min read

The Idea In One Breath

Most distributed data problems boil down to one question: what happens when two replicas are updated at the same time, disconnected from each other? The traditional answer is coordination — locks, consensus, a leader that serializes writes. A conflict-free replicated data type answers differently: design the data structure itself so that any replica can be modified without coordinating with another replica, and when any two replicas have received the same set of updates, they reach the same state deterministically . No voting, no blocking, no leader — just math that guarantees the merge always works out.

Wikipedia's summary captures the same guarantee from the outside: an algorithm built into the data type automatically resolves any inconsistencies that occur, and although replicas may briefly disagree, they are guaranteed to eventually converge . The concept was formally defined in 2011 by Marc Shapiro, Nuno Preguiça, Carlos Baquero and Marek Zawirski, motivated originally by collaborative text editing and mobile computing — exactly the kind of environment where you can't assume a reliable connection to a central server.

Why this matters: CRDTs are one of the few practical answers to the availability side of the CAP theorem that doesn't just punt the conflict problem to "figure it out later." If a mobile client or an edge datacenter goes offline for an hour, it can keep accepting writes, and when it reconnects the merge is guaranteed correct — not "usually correct," not "correct if you wrote good tests," but mathematically guaranteed by the structure of the data type.

Two Families, One Guarantee

Shapiro et al. define two equivalent ways to build a CRDT, and nearly every real implementation is one of these:

State-based (CvRDT — convergent). A replica updates its local state when it receives a client update, and occasionally ships its entire state to another replica, which merges the incoming state with its own local state . For this to converge no matter what order states arrive in, the merge function has to behave like a mathematical join: it must be associative and commutative , and idempotent, which together mean the set of possible states forms a join-semilattice with a well-defined "least upper bound" for any two states.

Operation-based (CmRDT — commutative). Instead of shipping whole state, replicas broadcast the individual operations (increment, add, remove) to every other replica, typically over a reliable causal-order broadcast channel. Correctness here doesn't require a join-semilattice; it requires that concurrent operations commute with each other, so applying them in any order produces the same result.

Both families exist to satisfy the same target correctness model: Strong Eventual Consistency (SEC). Shapiro et al.'s SEC adds a safety guarantee on top of plain eventual consistency's liveness guarantee. It requires two properties: eventual update — if an update is applied by a correct replica, all correct replicas will eventually apply it — and convergence — any two correct replicas that have applied the same set of updates end up in the same state, even if those updates were applied in a different order . That second clause is the whole trick: you don't need to agree on order, only on the final answer.

State-Based vs Operation-Based Propagation

Worked Example: the G-Counter

The simplest CRDT is the grow-only counter. Its internal state on n replicas is an n-length array of non-negative integers, and querying it returns the sum of every element in the array . Incrementing on replica i bumps only the i-th slot of that array — each node only ever writes to its own column, which is what makes concurrent increments safe. Merging two counters is a pairwise maximum of the two arrays , which is exactly the join operation a semilattice needs: order-independent, idempotent, and always produces a value at least as large as either input.

G-Counter Merge: Pairwise Max Converges Regardless of Path

Beyond Counters: Sets, Maps, and Text

Counters are easy because increment is naturally commutative. Sets are trickier because add and remove don't commute in general — if A adds an element and B concurrently removes it, who wins? The standard fix is the OR-Set (Observed-Remove Set), which tracks both additions and deletions of elements by tagging every add with a unique identifier and only letting a remove delete the specific tags it has actually observed. A concurrent add that the remover never saw survives — this "add-wins" bias is why the pattern is so common in shopping carts and collaborative lists.

OR-Set: Add-Wins Semantics Under Concurrency

The same tagging trick generalizes to richer structures: maps that nest CRDTs recursively, JSON-like documents (Automerge), and sequence CRDTs like RGA and WOOT for collaborative text, where every character insertion carries a globally unique, causally-ordered identifier so concurrent edits interleave deterministically without a central arbiter.

Delta-State: Trimming the Bandwidth Cost

Naively shipping the entire state on every sync round doesn't scale once documents get large. δ-state CRDTs address this by propagating only the small "delta" produced by a recent update or interval of updates rather than the full state, while preserving the same join-semilattice merge semantics so that updates can be bundled into intervals sent in a way that preserves causality . This is the same idea Riak, Redis Enterprise, and AntidoteDB rely on internally to keep multi-datacenter sync affordable.

State-based CvRDT

  • Ships full (or delta) state
  • Merge must be a semilattice join
  • Tolerant of duplicate/reordered messages
  • Simpler to implement correctly
  • Can be bandwidth-heavy without deltas

Operation-based CmRDT

  • Ships individual operations
  • Concurrent ops must commute
  • Needs reliable causal-order delivery
  • Lower bandwidth per update
  • Harder to get delivery guarantees right

CRDTs vs. Operational Transformation

For collaborative editors specifically, CRDTs compete with the older Operational Transformation (OT) approach used by Google Docs. CRDTs are designed so conflicts cannot occur mathematically, enabling decentralized collaboration without a central server, while OT modifies operations through a central coordinator . Figma is the widely cited case study here: Google Docs uses OT for centralized real-time editing with sub-millisecond latency, while Figma switched from OT to CRDTs in 2019 for offline-first capabilities .

Operational Transformation

  • Needs a central server to order ops
  • Great single-server latency
  • Harder to support true offline editing
  • Battle-tested (Google Docs)

CRDTs

  • No central coordinator required
  • Native offline / peer-to-peer support
  • Metadata (tombstones) can grow over time
  • Used by Figma, Apple Notes, Yjs, Automerge

Real-World Use Cases

CRDTs stopped being an academic curiosity around 2012–2013 when production databases began shipping them as first-class types.

Distributed Databases
Riak was one of the first databases to add CRDT support in 2013 , implementing counters, sets and maps natively.
Multi-Master Redis
Redis Enterprise uses CRDTs to enable multi-master replication between geographically distributed datacenters.
Cloud Databases
Azure Cosmos DB allows conflicting values to be merged using CRDTs or custom merge procedures.
Collaborative Editors
Yjs and Automerge power real-time document/canvas collaboration with automatic, server-optional conflict resolution.
Offline-First Mobile Apps
Apple Notes uses CRDTs for syncing offline edits between devices.
Design Tools
Figma moved from operational transformation to a CRDT-based sync engine to support resilient, offline-capable multiplayer editing.

Trade-offs to Know Before You Reach for One

CRDTs are not a free lunch. They favor availability and partition tolerance over strict ordering, so they are the wrong tool if you need linearizable reads or hard invariants like "never let the balance go negative" (that needs coordination, not CRDTs, or a hybrid escrow scheme). Metadata can also accumulate: sequence CRDTs used for text keep tombstones for deleted characters, and some counters keep one slot per replica forever unless you periodically compact and garbage-collect old identities. Choosing a CRDT means choosing exactly which operations you're willing to make commutative, and accepting the bookkeeping that requires.
