Caching Strategies: Cache-Aside, Write-Through, Write-Behind, and Stampede Protection

Where the cache sits on the read and write paths decides how fresh, fast, and fragile your system is.

October 15, 2026 · 5 min read

Summary

An application cache (Memcached, Redis, an in-process map) keeps hot copies of data that lives authoritatively in a slower store, usually a database. The hard part isn't storing bytes in RAM; it's choosing when the cache is filled, when it is updated or invalidated after a write, and what happens when a popular entry disappears. Four patterns cover most designs: cache-aside (lazy loading), read-through, write-through, and write-behind (write-back). On top of those, any high-traffic cache needs protection against two classic failure modes: stale sets that leave old data cached after a write, and stampedes (thundering herds) where many requests miss at once and pile onto the database.

Rule of thumb: the database stays the system of record and the cache holds derived, disposable copies. Every pattern below is a different answer to the question of how far behind that copy is allowed to fall, and who repairs it when it does. Microsoft's guidance puts it the same way: the application must be able to fall back to the original data store if the cache is unavailable (Azure caching guidance).

The four patterns

Cache-aside (lazy loading)

The application talks to both the cache and the database. On a read it checks the cache first; on a miss it reads the database, stores the result in the cache with a TTL, and returns it. On a write it updates the database and then deletes the cached key, so the next read repopulates it (Azure Cache-Aside pattern). AWS calls this the most common caching strategy: only requested data ends up in the cache, and a cache node failure is not fatal because the database still answers (AWS whitepaper). The cost is a slow first read after every miss and a window where readers may briefly see stale data or a miss right after a write.

Facebook's memcache tier is the canonical large-scale example: a demand-filled look-aside cache where web servers delete keys after a database write, preferring deletes to sets because deletes are idempotent (Nishtala et al., NSDI 2013).

Read-through

Same lazy fill, but the cache library or service owns the loader: the application only calls cache.get(key) and the cache fetches from the store on a miss. Commercial caches often provide read-through and write-through natively; cache-aside is how you emulate read-through when your cache only offers get/set (Azure).

Write-through

Every write updates the database and the cache in the same operation, and the write only reports success once both are done. Readers see the new value immediately after a successful write, at the price of higher write latency and more failure handling (what if the DB commits but the cache update fails?) (Azure caching guidance). AWS notes write-through is almost always paired with lazy loading so that expired or evicted keys still get refilled, and warns it can fill the cache with data nobody reads unless you also set TTLs (AWS whitepaper). Microsoft's reference architecture for Azure SQL plus Redis uses a dedicated write coordinator and a durable outbox to repair the cache when the second step fails (Azure write-through architecture).

Write-behind (write-back)

Writes land in the cache and are acknowledged right away; the cache flushes them to the database asynchronously after a delay, coalescing repeated updates to the same key and batching them. Oracle Coherence implements this with a configurable write-behind delay and batched storeAll calls (Oracle Coherence docs). Writes become very fast and the database sees far less traffic, but for that window the cache, not the database, holds the only copy of the newest data. A crash before flush loses writes unless the cache itself is replicated or persisted.

Read and write paths for each pattern

Lazy patterns (cache-aside, read-through)

  • Cache holds only data that was actually requested
  • Survives cache loss; database still answers
  • First read after a miss is slow
  • Brief staleness window after writes
  • Vulnerable to stampedes on hot keys

Eager patterns (write-through, write-behind)

  • Read-after-write freshness on cached paths
  • Write-through adds latency to every write
  • Write-behind gives the fastest writes, weakest durability
  • Can fill memory with data nobody reads
  • Still need lazy fill for evicted or expired keys

Deeper dive: where caches go wrong

Stale sets

Cache-aside has a subtle race. Reader A misses and reads value v1 from the database. Before A writes it into the cache, writer B updates the row to v2 and deletes the key. Then A's delayed set(v1) lands, and the cache now holds old data indefinitely, until the TTL expires. Facebook fixed this with leases: on a miss, memcached hands the client a 64-bit token bound to that key, and the later set must present it. A delete invalidates the token, so the late, stale set is rejected, much like load-link/store-conditional (NSDI 2013). The same paper describes tailing the MySQL commit log to issue invalidations, so caches can be resynchronized from committed transactions rather than trusting every web server to remember its deletes.

Stampedes (thundering herds)

When a hot key expires or is deleted, every concurrent request misses at the same instant and recomputes the same value against the database. Under load this can turn into congestion collapse: recomputation slows down, so more requests pile up behind it (Vattani et al., VLDB 2015). Three families of defenses are common, and they combine well:

1. One recompute per key. Make only one caller rebuild the value while others wait or get a slightly stale copy. Facebook's lease variant returns a token for a key at most once every 10 seconds; other requesters are told to wait briefly and retry, by which time the value is usually back. On keys prone to herds, peak database queries dropped from 17K/s to 1.3K/s (NSDI 2013). Inside one process, Go's singleflight.Group.Do does the same thing: only one execution is in flight per key, and duplicate callers wait and share the result (golang.org/x/sync/singleflight).

2. Refresh before expiry. XFetch (probabilistic early expiration) has each reader independently decide to recompute a little early, with probability rising as expiry nears: recompute if now - delta * beta * ln(rand()) >= expiry, where delta is how long the last recompute took and beta defaults to 1. The authors prove the exponential form is optimal and needs no tuning to the request rate (VLDB 2015). The Internet Archive's RedisConf 2017 benchmarks found that XFetch combined with a recompute lock performed best of the strategies tested, with no simultaneous recomputes (internetarchive/xfetch).

3. Serve stale while refreshing. HTTP formalized this with stale-while-revalidate (serve an expired response while revalidating in the background) and stale-if-error (serve stale if the origin returns a 5xx) in RFC 5861. Application caches borrow the idea by storing a soft expiry inside the value and a longer hard TTL on the key.

Hot key expiry: stampede versus single-flight refresh

TTLs, eviction, and memory pressure

TTLs bound staleness for anything invalidation misses; adding a little random jitter to TTLs keeps keys written together from all expiring together. When memory fills, the eviction policy decides what goes. Redis offers allkeys-lru, allkeys-lfu, the volatile-* variants that only evict keys with a TTL, and noeviction; its docs recommend allkeys-lru as a good default when a subset of keys is much hotter than the rest, and LFU (since Redis 4.0) when you want frequently read keys to survive bursts of cold reads (Redis key eviction).

Consistency caveat: cache-aside assumes the instance that fills the cache can read the latest committed data. With read replicas or an eventually consistent store, a miss can be filled from a lagging replica and re-cache an old value (Azure caching guidance). Facebook handles this across regions by setting a remote marker on write and sending reads for marked keys to the primary region (NSDI 2013).

Real-world use cases

Facebook memcache
Demand-filled look-aside cache handling over a billion requests per second, with leases against stale sets and herds and commit-log-driven invalidation (NSDI 2013).
Netflix EVCache
Memcached-based, zone-aware distributed cache with consistent-hash sharding and cross-zone replication for availability (EVCache docs).
Redis in front of SQL
AWS and Azure reference designs pair lazy loading with write-through on read-after-write-sensitive paths (AWS, Azure).
Data grids with write-behind
Oracle Coherence coalesces and batches cache updates to the backing store after a delay to absorb write bursts (Coherence docs).
Internet Archive
Engineers benchmarked plain fetch, locked recompute, and XFetch on Redis at RedisConf 2017 to tame stampedes (xfetch repo).
HTTP and CDN caches
stale-while-revalidate and stale-if-error let edges keep serving during refreshes and origin outages (RFC 5861).

Choosing a strategy

Start with cache-aside plus TTLs: it is simple, failure-tolerant, and good enough for most read-heavy data. Add write-through only on paths where users must see their own writes immediately and the data is read often after being written. Reach for write-behind when write throughput is the bottleneck and you can tolerate, or separately protect against, losing the last few seconds of writes. Whatever you pick, protect hot keys with single-flight recomputation or early refresh, invalidate by deleting rather than setting, and make sure a cache outage degrades to slower responses rather than an outage.
