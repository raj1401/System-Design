Message Queue Delivery Guarantees: At-Least-Once to Exactly-Once

Why brokers almost always duplicate, and how outbox plus idempotent consumers get you to effectively-once

September 24, 2026 · 5 min read

The Concept, Briefly

When a producer hands a message to a broker and a consumer processes it, three classic promises describe what happens under failure: at-most-once (deliver zero or one time; loss is allowed), at-least-once (deliver one or more times; duplicates are allowed), and exactly-once (deliver once; neither loss nor duplicates). Real systems almost never get true end-to-end exactly-once across databases, APIs, and brokers. What they get is a scoped guarantee inside the messaging fabric, plus application patterns that absorb duplicates so side effects happen effectively once.

Apache Kafka documents these three semantics explicitly for producers and consumers. Most managed queues (RabbitMQ, Amazon SQS, Azure Service Bus, Google Pub/Sub) default to at-least-once when you need durability: the broker redelivers until it sees an acknowledgment. That reliability is why payment workers, order pipelines, and event buses start from at-least-once and design consumers to tolerate repeats.

Why this matters: Choosing a delivery guarantee is choosing which failure mode you accept. Preferring “never lose” without an idempotent consumer quietly becomes “sometimes double-charge.” Preferring “never duplicate” without durable retries quietly becomes “sometimes drop the order.”

Underlying Ideas & Mechanisms

At-Most-Once: Fire, Forget, Accept Loss

At-most-once means a message is processed zero or one times. On the producer side that looks like fire-and-forget or acknowledging only the leader without retries. On the consumer side it looks like committing the offset (or acknowledging) before processing: if the process dies after the commit and before the side effect, that message is gone. Latency is low and bookkeeping is simple. The cost is silent loss under crashes, timeouts, and broker failovers. Use it for telemetry, metrics, or any stream where a missing sample is cheaper than a duplicate.

At-Least-Once: Retry Until Acknowledged

At-least-once is the workhorse of durable messaging. The producer retries until the broker confirms a durable write. The consumer processes first, then acknowledges (or commits its offset). If the ack is lost, the lock expires, or the worker crashes after writing to the database but before acknowledging, the broker redelivers. Microsoft’s Azure Architecture Center notes that Azure Service Bus, Event Hubs, Kafka, and RabbitMQ all provide at-least-once when durability matters, and that duplicates arise from producer retries, missing acknowledgments, and mid-processing crashes.

Kafka’s default consumer path is at-least-once when you process then commit. Producers that retry without idempotence can also write the same logical message twice into the log. The safety net is not “the broker will never duplicate”; it is “your handler must survive being called twice.”

Where Duplicates Come From Under At-Least-Once

Exactly-Once Inside the Broker Boundary

Kafka’s exactly-once story (from 0.11 onward) is precise about scope. An idempotent producer gets a producer ID and sequence numbers so broker-side deduplication prevents duplicate log entries on retry while preserving order. Transactional producers can atomically write to multiple partitions and commit consumer offsets in the same transaction. Kafka Streams with processing.guarantee=exactly_once_v2 and consumers with isolation.level=read_committed see only committed results. That is exactly-once for Kafka-to-Kafka pipelines, not a magic shield around your Postgres row or Stripe charge.

Chris Richardson and Microsoft both stress the fine print: even when the broker claims exactly-once for messaging, a handler that updates an external database can still run more than once if the process crashes between the DB commit and the offset commit. Broker EOS removes duplicate records in the log or duplicate Kafka outputs; it does not erase the need for idempotent side effects.

Effectively-Once: Outbox + Idempotent Consumer

The dual-write problem is the producer-side twin of consumer duplicates. Updating business state and publishing an event in two separate steps can leave you with a committed order and no event, or an event and a rolled-back order. Two-phase commit across the database and the broker is usually unavailable or undesirable. The transactional outbox pattern stores the outbound message in the same local transaction as the business write. A relay (polling publisher or change-data-capture / transaction-log tailing) publishes committed outbox rows to the broker. Publishing may still happen more than once if the relay crashes after send, so consumers must remain idempotent.

The idempotent consumer (inbox) pattern is the mirror image. On each delivery, extract a stable deduplication key (producer message ID, CloudEvents source+id, or a business idempotency key). Attempt to insert that key under a uniqueness constraint in the same transaction as the business effect. If the insert wins, process; if it conflicts, treat as a duplicate and acknowledge. Commit the marker and the side effects together so a crash cannot leave “effect applied, key missing.” For external APIs that cannot join the transaction, record in-progress, call with the idempotency key propagated, then mark completed.

Transactional Outbox and Idempotent Consumer

Design Comparison

At-Most-Once

  • Ack or commit before processing
  • Lowest latency; simplest code
  • Messages can be lost on crash
  • Fine for metrics and best-effort signals
  • Wrong default for money or inventory

At-Least-Once + Idempotency

  • Process then ack; broker retries freely
  • No silent loss if the broker is durable
  • Duplicates expected; inbox / unique keys required
  • Pairs with transactional outbox on produce
  • Practical default for business workflows

Broker Exactly-Once (e.g. Kafka EOS)

  • Idempotent producers + transactions
  • Strong for Kafka Streams / topic-to-topic
  • read_committed hides aborted writes
  • Does not cover external DB/API effects
  • Higher latency and operational complexity

Effectively-Once End-to-End

  • Outbox (or CDC) on the producer
  • At-least-once broker in the middle
  • Inbox / unique constraint on the consumer
  • Propagate idempotency keys downstream
  • The pattern most payments systems actually run

Real-World Use Cases

Kafka Streams EOS
Consume-transform-produce under one transaction; offsets and outputs commit together with read_committed consumers.
Order + Outbox
Insert order and OrderCreated row in one DB transaction; relay publishes to the broker so inventory never misses a commit.
Payment Worker Inbox
Dedupe on PaymentCaptured ID with a unique constraint so lock-timeout redelivery cannot double-post the ledger.
Metrics Firehose
At-most-once producers intentionally drop samples under overload rather than blocking the request path.

Trade-offs to Keep in Mind

Start from the failure you cannot accept. If loss is unacceptable, use at-least-once (or broker EOS inside Kafka) and invest in idempotency. If duplicates are catastrophic and you cannot make the operation idempotent, redesign the operation (event-carried state transfer, upserts, absolute values) before chasing mythical end-to-end exactly-once. Keep deduplication records at least as long as the broker can still redeliver, including dead-letter resubmits. Instrument duplicate rates: a spike often means undersized visibility timeouts or producer retries without stable message IDs.

Also separate delivery from ordering. Deduplication removes repeats; it does not restore order. Use partition keys, sessions, or version checks when sequence matters. And remember that broker-side duplicate detection (for example Service Bus MessageId windows) reduces send-side noise but does not replace an idempotent consumer after redelivery.
