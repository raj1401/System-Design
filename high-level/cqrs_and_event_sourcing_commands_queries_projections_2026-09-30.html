CQRS and Event Sourcing: Separate Reads, Writes, and History

Why one model for CRUD often fails at scale, and how commands, events, and projections fix it

September 30, 2026 · 5 min read

The Concept, Briefly

Most systems treat data as a single CRUD record: create, read, update, delete against one shape. That works until write rules and query shapes diverge—complex validation on the write path, denormalized dashboards on the read path, and a need to know why state changed, not only what it is now. CQRS (Command Query Responsibility Segregation) splits the update model from the query model. Event Sourcing stores every change as an immutable event in an append-only log, and reconstructs current state by replaying that history.

Greg Young popularized CQRS; Martin Fowler documented both patterns and warned that for most systems CQRS adds risky complexity. Microsoft’s Azure Architecture Center and AWS Prescriptive Guidance describe the same pairing: commands mutate through a write model, events land in an event store, and projections materialize read-optimized views. The two patterns are independent—you can CQRS without event sourcing, or event-source without a full read/write split—but they compose naturally when history, scale, and auditability matter together.

Apply selectively: Fowler and Microsoft both stress this: use CQRS/Event Sourcing on specific bounded contexts (ledgers, orders, bookings), not as a house style for every table. CRUD remains the right default for simple domains.

Underlying Ideas & Mechanisms

CQRS: Two Models, Two Jobs

A command expresses intent to change state (PlaceOrder, ReserveSeats). It is validated, may fail, and does not return a rich domain graph—often just success/failure and identifiers. A query returns data and must not change state. CQRS lets each side use its own object model, storage engine, and scaling strategy. Writes can go to a normalized transactional store (or an event store); reads can hit denormalized tables, documents, or caches shaped for specific screens.

When models share one database, the DB itself is the sync channel. When they use separate stores, the write side publishes events and the read side consumes them. That almost always means eventual consistency: a user may briefly see a stale projection after a successful command. AWS notes CQRS is a fit when read and write workloads have different throughput, latency, or consistency needs—and when eventual consistency on queries is acceptable.

CQRS Command Path vs Query Path

Event Sourcing: History as the Source of Truth

Instead of overwriting a row, Event Sourcing records facts: OrderPlaced, PaymentCaptured, OrderShipped. Fowler’s definition: every change to application state is captured as an event object, stored in sequence for the lifetime of the application. Current state is derived by replaying the stream (rehydration). Azure emphasizes append-only writes, intent-rich event design, and optimistic concurrency: append only if the stream version still matches what the command handler read.

Replay cost grows with stream length, so production systems take snapshots every N events and replay only the tail. Schema evolution uses tolerant deserialization, versioned event types, or upcasters that transform old payloads at read time—you do not rewrite history in place. Compensating events reverse effects without deleting the original record. Message brokers (Kafka and friends) can fan out events, but they are not a drop-in event store: per-aggregate streams and expected-version appends still need a true event store or a carefully designed table.

Event Stream, Snapshot, and Projection

Projections, Outbox, and Idempotency

Projections (read models) subscribe to the event stream and update denormalized stores. Inline projections keep strong consistency at the cost of write latency; async projections are the production default and accept lag. Because delivery is typically at-least-once, handlers must be idempotent—track last processed sequence per consumer, or use upserts that tolerate duplicates. When the write model is a traditional DB rather than a pure event store, the transactional outbox (or CDC) keeps “persist state + publish event” atomic so projections never miss or invent updates.

Design Comparison

CQRS Alone

  • Separate command and query models
  • Write side can still be CRUD tables
  • Scale reads and writes independently
  • No mandatory full history log
  • Simpler than full event sourcing

CQRS + Event Sourcing

  • Event store is the system of record
  • Natural feed for many projections
  • Audit, temporal queries, rebuild views
  • Schema evolution and upcasters required
  • Higher operational and team cost

When It Pays Off

  • Strong audit / regulatory history needs
  • Read/write load imbalance at scale
  • Complex domain with task-based UIs
  • Need to rebuild or add views later
  • Intent of each change must be preserved

When to Avoid

  • Simple CRUD bounded contexts
  • Team new to event-driven ops
  • Hard real-time read-after-write UX
  • Short-lived MVPs without audit needs
  • Mostly static reference data

Real-World Use Cases

Banking & Ledgers
Append deposits, withdrawals, and corrections as events; balances and statements are projections that can be rebuilt.
Seat Reservation
Azure’s classic example: reserve/cancel events with optimistic concurrency to avoid overselling under load.
Order Fulfillment
Place, pay, ship, deliver as intent events; separate boards for ops, customer status, and analytics.
Healthcare / Audit Trails
Who changed what and why matters as much as current chart state; immutable history supports compliance.

Trade-offs to Keep in Mind

CQRS and Event Sourcing buy independent scaling, rebuildable read models, and a first-class audit log. They cost mental overhead, eventual consistency UX, projection ops, and a lifelong commitment to event schema design. Prefer purpose-built event stores (or a disciplined append-only table with versioning) over treating a compacted log as your aggregate store. Make projections idempotent from day one. Plan for personal-data deletion (externalize PII or crypto-shred) before regulators ask.

Start with CQRS where read and write shapes already fight each other. Add Event Sourcing when history itself is a product requirement—not because it is fashionable. And keep Fowler’s caution visible on the whiteboard: applied to the wrong bounded context, this pattern can chop off more than it unlocks.
