MESI: The Cache Coherence Protocol Behind Every Multicore CPU

How dozens of private CPU caches agree on the value of a byte, without ever asking main memory to referee.

August 3, 2026 · 5 min read

The Concept

Every core in a modern CPU has its own private L1/L2 cache holding copies of memory it has recently touched. That is fantastic for speed, and a nightmare for correctness: if Core 0 and Core 1 both cache the same 64-byte line and Core 0 quietly changes its copy, Core 1 is now reading stale data. Cache coherence protocols exist to prevent exactly that — they are the hardware machinery that makes a multicore chip behave, from software's point of view, like it still has a single shared memory.

MESI (Modified, Exclusive, Shared, Invalid) is the canonical coherence protocol used across x86, ARM, and most other multicore designs. The MESI protocol defines four states for cache lines: Modified, Exclusive, Shared, and Invalid. Each cache line — not each byte, not each variable — carries one of these four states, and a small hardware state machine updates that state on every local access and every message it observes from other cores.

Why this matters: Coherence is invisible until it isn't. It is the hidden cost behind lock contention, the reason "sharing a counter across threads" tanks throughput, and the reason NUMA-aware software design exists at all. Understanding MESI is understanding why concurrent code that looks correct on paper can still run 10x slower on real silicon.

Underlying Mechanism: States, Transitions, and Snooping

The four states

StateMeaningCan read locally?Can write locally?
Modified (M)Only this cache has the line; it has been written and differs from memoryYesYes, freely
Exclusive (E)Only this cache has the line; it matches memoryYesYes, freely (silently → M)
Shared (S)Multiple caches may hold this line; all match memoryYesNo — must broadcast first
Invalid (I)This cache's copy is stale or absentNo — triggers a fetchNo — triggers a fetch

Exclusive (E) means the cache line is valid and matches the data in memory, but no other caches hold it. That distinction from Shared is the whole point of the E state: the cache can transition the data directly from Exclusive to Modified (M) if the processor writes to it, without issuing any bus requests. A line only needs to be Shared — and therefore needs an invalidation broadcast before it can be written — once a second cache actually asks for it.

What drives a transition

A line's state changes in response to exactly two kinds of stimulus, as formalized in Paul McKenney's treatment of the protocol for kernel developers. Coherence of caches is maintained by a variant of MESI protocol. Each cache line can be in one of four states: Modified (M), Exclusive (E), Shared (S) and Invalid (I). The rules that matter most in practice: upon reading, the state of the cache line changes from any state to S, and, if the state was I, then a read request is sent to the bus; upon writing, the state of the cache line becomes M, and, if the state was S or I, an invalidation request is sent to the bus.

Concretely, the state machine is driven by processor-side requests and bus-side snoop traffic. The MESI protocol is defined by a finite-state machine that transitions from one state to another based on 2 stimuli. The first stimulus is the processor specific Read and Write request. The second stimulus is given through the bus connecting the processors — bus side requests come from other processors that don't have the cache block or the updated data in their cache, and the bus requests are monitored with the help of snoopers, which monitor all the bus transactions. In practice a core can only write for free — no bus message at all — when it already owns the line exclusively: a write may only be performed freely if the cache line is in the Modified or Exclusive state.

McKenney's own state-diagram walkthrough describes the three transitions that matter most for intuition: a cache line is written back to memory, but the CPU retains it in its cache and further retains the right to modify it — this transition requires a "writeback" message ; the CPU writes to the cache line that it already had exclusive access to — this transition does not require any messages to be sent or received ; and, the expensive case, the CPU receives a "read invalidate" message for a cache line that it has modified — the CPU must invalidate its local copy, then respond with both a "read response" and an "invalidate acknowledge" message.

Snooping the bus

The mechanism that lets a core know it must invalidate is bus snooping: in a snooping system, all caches on a bus monitor all the transactions on that bus. Every cache has a copy of the sharing status of every block of physical memory it has stored. When a core wants exclusive write access to a line currently held elsewhere, it issues a bus transaction that every other cache controller observes and reacts to by invalidating its own copy — no central coordinator required.

Beyond plain MESI: MOESI and MESIF

Plain MESI has one wart: when a Shared line needs to be modified, or when a Modified line needs to be shared, someone has to write back to main memory first, on the critical path. Two industry extensions remove that stall by letting caches hand data directly to each other.

MOESI (AMD)

  • In addition to the four common MESI states, there is a fifth "Owned" state representing data that is both modified and shared, avoiding the need to write modified data back to main memory before sharing it.
  • The write-back may be deferred.
  • Direct cache-to-cache transfers of data must be possible, so a cache with the data in the modified state can supply that data to another reader without transferring it to memory.

MESIF (Intel)

  • The MESIF protocol was developed by Intel for cache coherent non-uniform memory architectures, and consists of five states: Modified (M), Exclusive (E), Shared (S), Invalid (I) and Forward (F).
  • The F state is a specialized form of the S state, and indicates that a cache should act as a designated responder for any requests for the given line.
  • The protocol ensures that, if any cache holds a line in the S state, at most one other cache holds it in the F state.

The classic pitfall: false sharing

Because coherence operates at the granularity of a whole cache line, not a variable, two threads can wreck each other's performance without ever touching the same logical data. False sharing occurs when two or more logically independent variables, frequently updated by different threads on different CPU cores, happen to reside within the same 64-byte cache line. More formally: false cache line sharing occurs when multiple cores access the same cache line while at least one is writing to it. Each write forces the line to ping-pong between Modified and Invalid across cores, even though the actual bytes each thread cares about never overlap. This is not a theoretical concern — false sharing slows MySQL by 50% in cases documented in patent literature on false-sharing detectors.

Real-World Use Cases

x86 & ARM multicore chips
MESI or a MOESI/MESIF variant is implemented directly in the L1/L2 cache controllers of virtually every modern multicore processor, enforced entirely in hardware and transparent to software.
Lock-free data structures
Compare-and-swap and other atomics rely on the coherence protocol to guarantee that an invalidated or exclusive line is visible consistently the instant a core commits a write.
NUMA-aware software design
MESIF was purpose-built by Intel for cache-coherent NUMA systems, where the Forward state reduces cross-socket snoop traffic on frequently-read shared lines.
Performance profiling tools
Profilers like Intel VTune and hardware performance-counter based detectors specifically hunt for cache-line bouncing to flag false sharing bugs in production concurrent code.
Why does this matter: ACCESS_ONCE() provides "cache coherence" for accesses from multiple CPUs to a single variable — but coherence alone does not guarantee ordering between different variables. That gap between per-line coherence (MESI's job) and cross-line ordering (memory barriers' job) is precisely why the Linux kernel's memory-barriers documentation treats them as related but distinct concerns.

Trade-offs at a Glance

Snooping (bus-based MESI)

  • Simple, low-latency for small core counts
  • Relies on bus snooping, where all cores must snoop every memory transaction — as core count grows, snooping traffic grows rapidly
  • Broadcast invalidations don't scale past dozens of cores

Directory-based coherence

  • Used in large ccNUMA and many-core systems instead of broadcast
  • A directory tracks exactly which caches hold a line, sending point-to-point invalidations instead of a broadcast
  • Higher metadata overhead, but scales to hundreds of cores/sockets
