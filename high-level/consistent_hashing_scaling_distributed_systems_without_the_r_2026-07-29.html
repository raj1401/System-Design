Consistent Hashing: Scaling Distributed Systems Without the Rebalancing Storm

How a 1997 MIT paper on web caching quietly became the load-distribution backbone of Dynamo, Cassandra, and modern CDNs.

July 29, 2026 · 5 min read

The concept, in a nutshell

Every distributed cache, database, or load balancer has the same basic problem: given a key and a set of N servers, decide which server owns that key. The naive answer, hash(key) % N, works fine until N changes. The moment you add or remove a single node, almost every key gets remapped to a different server, triggering a stampede of cache misses or data migrations across the whole cluster.

Consistent hashing is a special kind of hashing that changes minimally as the range of the function changes , introduced by David Karger and colleagues in 1997 to solve the problem of Web caching . Instead of hashing keys into a flat array of buckets, it hashes both servers and keys onto points on a shared circular space — a "ring" — so that adding or removing a server only disturbs the small slice of keys that were adjacent to it.

Why this matters: with 5 nodes, roughly 80% of keys are remapped when you add just one more node, and with 100 nodes, adding a single node remaps roughly 99% of keys under plain modulo hashing. At terabyte scale that's not a rebalance, it's an outage. Consistent hashing turns that into a localized, cheap operation.

The underlying mechanism

From modulo to the ring

Picture a circle representing every possible hash output, from 0 to 2^32 - 1 (or larger). Each server is hashed to one or more points on this circle. To find the owner of a key, hash the key, land on the circle, and walk clockwise until you hit the first server point — that server owns the key. Cassandra, for instance, maps every node to one or more tokens on this continuous ring and defines ownership by hashing a key onto the ring and then walking it in one direction, so that when the number of nodes changes, only a small fraction of the keys need to move . Compare that to naive hashing, where on average only k/n keys need to be remapped under consistent hashing, versus a near-total remap under modulo schemes .

Virtual nodes: smoothing the distribution

With only one point per physical server, the ring can be badly unbalanced — one server might end up owning a huge arc while another owns a sliver. The fix, used since the earliest production deployments, is virtual nodes: instead of mapping a node to a single point on the circle, each node gets assigned to multiple points in the ring, a concept Dynamo calls "virtual nodes" . Replication then follows naturally: nodes A, B, and C can form the preference list for a key, with the shaded arc indicating the key range for which those three nodes are responsible .

Apache Cassandra adopted the same idea: virtual nodes were introduced in Cassandra 1.2, inspired directly by Amazon Dynamo's approach, which had used virtual nodes from its inception . Cassandra's default partitioner then turns a row's partition key into a ring position: it uses the MurmurHash function to create a 64-bit hash of the partition key , which is fast and non-cryptographic — ideal since consistent hashing needs speed and uniformity, not collision resistance.

The four formal guarantees

Karger's original paper didn't just describe a ring diagram — it defined precise properties a consistent hash function must satisfy:

Balance

Keys distribute evenly across all nodes; no single node should be disproportionately loaded.

Monotonicity

When a new node joins, keys only move to the new node — keys never reshuffle between existing nodes.

Spread

Across different client views of the cluster, a key maps to a small number of distinct nodes.

Load

No node receives more than its fair share of keys, regardless of which subset of nodes a client sees.

Beyond the ring: jump hashing and bounded loads

The ring isn't the only way to achieve consistency. Google's jump consistent hash takes a different approach entirely: it is a fast, minimal-memory consistent hash algorithm expressible in about five lines of code that, compared to Karger's algorithm, requires no storage, is faster, and does a better job evenly dividing the key space . Its tradeoff is that buckets must be numbered sequentially, making it better suited to data storage than distributed web caching — you can't cleanly remove an arbitrary node from the middle of the range.

A separate problem is the "hot key": even a perfectly balanced ring can send disproportionate traffic to one node if that node's keys happen to be popular. Consistent hashing's load balancing is no better than a random assignment of clients to servers, so with n clients and n servers we'd expect some servers to be overloaded with far more than their share — Google's bounded-load variant instead guarantees a max load of only 2 while moving just a constant number of clients per update . This wasn't just theory: Vimeo implemented the algorithm in HAProxy and used it for load balancing, decreasing cache bandwidth by a factor of almost 8 , and Google itself deployed it in Cloud Pub/Sub, observing a substantial improvement in uniformity .

Modulo Hashing (hash % N)

  • Trivial to implement, O(1) lookup
  • With 5 nodes, ~80% of keys remap when adding just one node
  • With 100 nodes, ~99% of keys remap on a single addition
  • Fine only for fixed-size, rarely-resized clusters

Consistent Hashing (Ring)

  • Only ~k/n keys move on average when a node changes
  • Needs virtual nodes for good balance, adding memory overhead
  • O(log n) lookup via binary search over sorted node positions
  • Ideal for elastic, frequently-resized clusters

Real-world use cases

Amazon Dynamo / DynamoDB
Dynamo assigns each node to multiple points on the ring via "virtual nodes" , the pattern that inspired most modern implementations.
Apache Cassandra
Nodes are mapped to tokens on a continuous ring; ownership is found by walking clockwise from a key's hash , minimizing data movement on topology changes.
CDN Edge Routing
The original 1997 motivation for consistent hashing was Web caching — routing a URL request to the same edge cache consistently, even as cache servers come and go.
Google Cloud Pub/Sub & Vimeo/HAProxy
Google deployed bounded-load consistent hashing in Cloud Pub/Sub , while Vimeo used it in HAProxy to cut cache bandwidth by nearly 8x .
