Backpressure and Load Shedding: Staying Up Under Overload

Every service has a capacity limit. The design question is what happens one request past it.

October 27, 2026 · 5 min read

Summary

When offered load exceeds what a service can process, the excess has to go somewhere. Left alone, it piles up in queues: latency climbs past client timeouts, the server spends its CPU on requests nobody is waiting for anymore, clients retry, and throughput of useful work (goodput) collapses. Two complementary techniques prevent that fold-over. Backpressure pushes a "slow down" signal upstream so producers send less. Load shedding deliberately rejects the excess early and cheaply so the work that is accepted still finishes in time [1][2].

Key idea: the goal is not to serve every request; it is to keep goodput flat at capacity as offered load keeps rising. A fast, explicit rejection is far better for the whole system than a slow, implicit timeout [2].

Deeper dive

Why queues are the enemy under sustained overload

Queues absorb short bursts, which is good. But under sustained overload a queue only adds delay: if arrivals exceed service rate, the queue grows without bound and every request waits longer. Little's Law ties this together: the concurrency in a system equals throughput times latency, so once throughput is pinned at capacity, any extra concurrency shows up purely as added latency. Netflix's concurrency-limits library is built on exactly this observation and argues for limiting concurrent requests rather than a fixed requests-per-second number that goes stale as fleets autoscale [5]. Google's SRE book recommends small, bounded queues and notes that a server whose queue is full should reject rather than wait [1].

Backpressure: make the producer slow down

Backpressure works when the producer can actually pace itself. The cleanest form is pull-based demand: in the Reactive Streams specification a subscriber calls request(n) and the publisher may emit at most n items, so every buffer between asynchronous stages stays bounded [6]. TCP does the same thing on the wire with its receive window: the receiver advertises how much buffer it has, and the sender never exceeds it [7]. Across HTTP boundaries the signal becomes explicit: 429 Too Many Requests with an optional Retry-After header [8], which well-behaved clients honour with backoff instead of hammering [9].

The weak spot is any unbounded buffer in the middle of a pipeline: it swallows the signal, upstream looks healthy, and memory grows until something crashes. When pressure reaches a source that cannot slow down (user clicks, sensors), you need shedding at the edge instead [10].

Backpressure flows against the data

Load shedding: reject early, reject cheaply

Shedding is the server protecting itself. The simplest version, from the Google SRE book, is to return 503 whenever in-flight requests exceed a threshold, or to throttle per task on CPU, memory, or queue length [2]. Amazon's Builders' Library stresses that rejection must be much cheaper than real work, should happen as early as possible (ideally before parsing or authenticating an expensive request), and that services should also drop requests whose client has already timed out [3].

Facebook's "Fail at Scale" describes two queue disciplines that pair well. A CoDel variant gives queued requests a short timeout whenever the queue has not been empty recently, so a standing queue cannot form while short bursts are still absorbed. Adaptive LIFO switches from FIFO to LIFO once a queue builds, so the freshest requests, the ones most likely to still have a waiting user, are served first [4]. CoDel itself comes from network bufferbloat research and is specified in RFC 8289 [11].

Adaptive limits instead of hand-tuned ones

Static limits drift out of date. Netflix's library borrows TCP congestion control: the concurrency limit plays the role of the congestion window and is nudged up when latency is stable and cut when latency rises. Its Gradient2 algorithm computes gradient = max(0.5, min(1.0, longtermRtt / currentRtt)) every sampling window and sets the new limit to roughly gradient × limit + queueSize, smoothed [5]. Envoy's admission-control filter does something similar at the proxy layer, rejecting probabilistically as the observed success rate falls below a threshold [12].

Clients share the job

Rejections still cost the backend something, so Google has clients throttle themselves. Each client tracks requests and accepts over a trailing window and locally rejects new calls with probability max(0, (requests − K × accepts) / (requests + 1)); with K = 2 the backend sees at most about twice the traffic it is accepting [1]. Google also tags every RPC with a criticality (CRITICAL_PLUS, CRITICAL, SHEDDABLE_PLUS, SHEDDABLE), propagates it down the call graph, and sheds lower tiers first. Retries are capped with a per-request budget of three attempts and a per-client retry ratio of about 10% so a struggling backend is not buried by retry storms [1].

Layered overload defenses on one request path

Backpressure

  • Slows the producer; no work is lost
  • Needs a cooperating, pace-able source
  • Natural in pipelines, streams, TCP, Kafka-style pull consumers
  • Fails silently behind an unbounded buffer

Load shedding

  • Drops excess work to protect accepted work
  • Works even when clients cannot or will not slow down
  • Natural at RPC servers, proxies, and API edges
  • Must be cheaper than serving, or it cannot help
Graceful degradation goes one step further than shedding: instead of rejecting, serve a cheaper answer, such as searching only an in-memory subset or using a simpler ranking. Google warns that rarely used degraded paths tend to rot, so exercise them regularly on a few servers [2].

Real-world use cases

Google RPC stack
Client-side adaptive throttling, propagated criticality, and retry budgets keep shared backends from being buried during overload [1].
Facebook services
CoDel-style queue timeouts, adaptive LIFO, and client concurrency caps came out of postmortems where requests sat in queues too long [4].
Netflix microservices
concurrency-limits auto-discovers each service's safe in-flight limit with TCP-inspired algorithms like Vegas and Gradient2 [5].
Amazon services
Servers reject excess requests early and drop already-timed-out work so accepted requests answer before clients give up [3].
Envoy service mesh
The admission-control filter rejects probabilistically when the upstream success rate drops [12].
Cloud APIs
Throttled APIs return 429 with Retry-After, and Azure guidance tells clients to respect it, retry in an orderly way, and ramp traffic back gradually [9].

Design checklist

Bound every queue and pool. Limit concurrency, preferably adaptively. Propagate deadlines and drop work whose deadline has passed. Make rejections cheap and early, and classify traffic so the least important work goes first. Have clients throttle themselves, cap retries, and back off with jitter. Finally, load-test past capacity and confirm the goodput curve flattens rather than folds [2][10].
